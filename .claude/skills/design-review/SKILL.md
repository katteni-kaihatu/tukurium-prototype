# デザインを確認・更新する

## 1. 変更と関係する設計を読む

[構想・設計の入口](../../../docs/design/README.md)と、変更に関係するページを読む。用語は[用語ページ](../../../docs/design/glossary.md)で確かめる。必要な範囲のコード・テスト・ADRも調べ、目指す設計と現在の動作を区別する。

## 2. 大きな判断が変わるかを確かめる

次のどれかが変わるなら、デザインの確認・更新の対象にする。

- 目指す体験や、Tukuriumが受け持つ範囲。
- プロジェクト・セッション・出力などの意味や関係。
- 制作と遊び、基盤と公式ライブラリなどの役割分担。
- 保存・共有・適用など、利用者が頼る振る舞い。
- 複数の機能に関わる前提や、設計を選んだ理由。

設計どおりに直すバグ修正、意味を変えない内部整理、画面の余白調整、既存の仕組みで作れる作例の追加は、通常は更新不要。変更行数やファイル数だけで判断しない。記載がないことだけを理由に追記しない。

## 3. 食い違いを扱う

設計どおりに実装を直す場合は、そのまま進める。誤字やリンク切れなど、意味を変えない資料の修正も進めてよい。

設計を変える必要がある場合は、現在の記述、変更案、理由と影響を短くまとめて利用者に確認する。新しい大きな判断が必要な場合も同じ。設計変更を前提にした実装や資料の確定は回答を待ち、独立した調査や修正は進めてよい。

会話ですでに変更内容が了承されていれば、再確認せず反映する。実装が先に変わっていても、それだけを根拠に資料を追認させない。案や未決事項を確定事項として扱わない。

例：「編集だけでは遊びへ反映しない」を自動反映に変えるなら確認が必要。「適用」が一部の配置に届かない不具合を直すだけなら、設計の再確認は不要。

## 4. 必要な範囲で資料を更新する

了承された目的・仕組み・理由を、説明の中心になるページへ短く反映する。大きな考え方に影響する検証結果や未決事項だけを添える。実装の細部や不具合の追跡はコード・テスト・Issueへ置く。

関連する短い話は同じページへまとめ、分量と探しやすさから分割を判断する。制作を支えるライブラリ・作例は制作側に置く。共通する説明は一か所にまとめ、必要な箇所から参照する。用語のタグから資料の置き場所を決めない。

言葉の意味や呼び方が変われば用語ページも更新する。タグは複数付けられる。参照は、その説明を実際に裏付ける箇所へ付ける。

既存ADRは経緯として残し、関係する判断を参照する。新しいADRの作成は既存ルールに従う。designの更新とは別に扱い、ADRの運用自体をこのスキルで変更しない。

## 5. 読み直して報告する

目的・仕組み・理由がつながり、用語が一貫し、確定・検討中・実装との差が分かるかを読む。資料全体で矛盾や重複がないか、見出し・リンク・移動元への参照を確認する。

変更の報告には、設計への影響と更新した資料を短く添える。更新不要なら、その理由を一行でよい。資料だけの変更ではコードのテストは不要。実装の確認は既存のverify-changeスキルに従う。
