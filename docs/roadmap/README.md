# ロードマップ

テーマと原則を実現するために、計画して進める重い変更を扱う。小さな機能の追加・改善や画面の調整はロードマップに入れず、単発で進める。いまできることは [FEATURES.md](../FEATURES.md) にある。

## ロードマップにするかの目安

影響範囲と作業の重さで決める。次のどれかに当たれば、ロードマップの候補にする。

- 保存の形式・通信・実行の仕組みなど、土台をいくつもまたいで変える
- 一本の PR では終わらず、分けて進める
- 利用者の作り方そのものが変わる
- 手を付ける前に、方針をそろえる必要がある

どれにも当たらなければ、単発で進める。迷ったら、計画者に聞く。

例：コードの TypeScript 化、ノードプログラミング、公式ライブラリの計画的な整備はロードマップ。差分を戻す機能、パネルの位置の同期、思い付いた公式ライブラリの追加、デザインの変更は単発。

## 役割

| 役割 | 書くもの | すること |
| --- | --- | --- |
| 計画者 | 構想 | やりたいこと・範囲・完了の条件を決める |
| 設計者 | 実装計画 | 作り方の方針と段階を決める |
| 実装者 | 実装計画の「段階」の状態 | 作る |

設計者と実装者は、同じ人が兼ねてもよい。

## フォルダ

項目ごとにフォルダを作り、項目の状態のフォルダの間を移す。

```
docs/roadmap/
  計画/          構想だけがある
  進行中/        構想と実装計画がある
  完了/          終わった項目
  テンプレート/  構想と実装計画のテンプレート
```

項目のフォルダには `構想.md` と `実装計画.md` を置く。項目のフォルダ名は、何をしたいかが分かる日本語にする（例：「改変したホストからもほかの人の状態を守る」）。空白や `/` は入れない。移しても名前は変えない。

## 資料の状態

構想と実装計画には、それぞれ先頭に「状態：作成中／完了」を書く。

- 構想が完了：計画が固まり、設計に取りかかってよい。
- 実装計画が完了：設計が固まり、作り始めてよい。設計者と実装者が同じなら、作りながら固めてもよい。

完了にしたら、作成完了日を書く。

## 進め方

1. **計画者**が、`テンプレート/構想.md` をコピーして `計画/<名前>/構想.md` を書き、完了にしてマージする。作成中のまま残すことは、ふつうない。
2. **設計者**が、項目を `進行中/` へ移し、`テンプレート/実装計画.md` をコピーして実装計画を書き、完了にする。
3. **実装者**が作り、実装計画の「段階」の状態を直す。
4. 構想と違うことをしたくなったら、計画者に確認し、実装計画の「構想から変えたこと」に残す。
5. 終わったら、できることを [FEATURES.md](../FEATURES.md) に、設計の判断を ADR に反映し、項目を `完了/` へ移す。

`完了/` の資料は、終わったときの記録として残す。あとの変更に合わせて直さない。

## 書き方の決まり

- 項目のフォルダは状態に合わせて移るので、ほかの資料（ADR・FEATURES・コード）からは、項目へリンクせず名前で書く（例：ロードマップの「改変したホストからもほかの人の状態を守る」）。ロードマップの中の資料どうしも、名前で指す。
- 原則との関係は、構想の側から原則を指す。
