# ロードマップ

テーマと原則を実現するために、計画して進める重い変更を扱う。小さな機能の追加・改善や画面の調整はロードマップに入れず、単発で進める。いまできることは [FEATURES.md](../FEATURES.md) にある。

## ロードマップにするかの目安

影響範囲と作業の重さで決める。次のどれかに当たれば、ロードマップの候補にする。

- 保存の形式・通信・実行の仕組みなど、土台をいくつもまたいで変える
- 一本の PR では終わらず、分けて進める
- 利用者の作り方そのものが変わる
- 手を付ける前に、方針をそろえる必要がある

どれにも当たらなければ、単発で進める。迷ったら、計画する人に聞く。

例：コードの TypeScript 化、ノードプログラミング、公式ライブラリの計画的な整備はロードマップ。差分を戻す機能、パネルの位置の同期、思い付いた公式ライブラリの追加、デザインの変更は単発。

## フォルダと状態

項目ごとにフォルダを作り、状態のフォルダの間を移す。

```
docs/roadmap/
  planned/      計画。構想（vision.md）だけがある
  in-progress/  進行中。構想と実装計画（implementation.md）がある
  done/         完了
  templates/    構想と実装計画のテンプレート
```

項目のフォルダ名は、短い英語の名前にする（例：`typescript`）。移しても名前は変えない。

## 進め方

1. **計画する人**が、`templates/vision.md` をコピーして `planned/<名前>/vision.md` を書き、マージする。計画の途中の物は、ふつう残さない。
2. 計画する人が、構想の「着手」を OK にする。
3. **設計・実装する人**が、項目を `in-progress/` へ移し、構想の「着手」の行を消す。`templates/implementation.md` をコピーして実装計画を書き、作り始める。
4. 構想と違うことをしたくなったら、計画する人に確認し、実装計画の「構想から変えたこと」に残す。
5. 終わったら、できることを [FEATURES.md](../FEATURES.md) に、設計の判断を ADR に反映し、項目を `done/` へ移す。

`done/` の資料は、完了したときの記録として残す。あとの変更に合わせて直さない。

## 書き方の決まり

- どちらの資料にも、書き上げた日を入れる。
- 項目のフォルダは状態に合わせて移るので、ほかの資料（ADR・FEATURES・コード）からは、項目へリンクせず名前で書く（例：「ロードマップの typescript」）。ロードマップの中の資料どうしも、名前で指す。
- 原則との関係は、構想の側から原則を指す。
