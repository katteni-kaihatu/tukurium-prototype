## 作り方の方針

### 今の仕組み（調べた結果）

- **System の呼び出し**：`Simulation.runSystem()`（`packages/runtime/src/simulation.ts`）が、Query に合う Entity の値をまとめて JSON にし、`ScriptSandbox.run()`（`packages/script/src/sandbox.ts`）で QuickJS に送る。QuickJS の中の `__run` が Entity を順に回し、終わったら全部を返す。ホストは、渡す前の値と比べて、変わったフィールドだけを `writeNamed()` で World に書く。
  - そのため、呼び出しの途中に `world.get`・`world.getState`・`world.getField` で読むと、`e.get()` で書いた値はまだ届いていない。ホストが Host API で書いた値も、QuickJS の中の写し（あとで回す Entity の分）には届かない。
  - `world.destroy` で消した Entity も、同じ呼び出しのあとの順番でそのまま渡される（ホストが受け取るときに `world.has()` で捨てるだけ）。
- **デバッグ実行**（ADR 0080）：`runAsync()` と `runSystemDebug()` が同じ形で動く。一時停止の画面に、まだ返していない `e.get()` の変更を写すために `activeDebugApply` を使っている。
- **作る・消す**：`world.spawn` は名前と KokoState を文字で受け取り、呼んだ System の配置（`part.entities`）に足す。`world.destroy` は同じ配置の Entity なら、制作データに置いたものも消せる。配置ごとの Entity は、フレームに `partEntities` として入れて配り、ホストが替わったら `restore()` で戻す。
- **import**：`systemCompiler.ts`（repo-model）は、`.koko` の default import だけを受け付け、`const X = __koko(ID, 名前)` に書き換える。
- **型**：`packages/typecheck/src/declarations.ts` が、KokoState ごとの宣言ファイル（`/States/Gun.koko.d.ts`）と型の定義のファイルを作る。Host API の宣言は `hostApiDeclarations()`（`hostApiSpec.ts`）から作る。`strict: true` なので、関数の引数は反変で確かめられる。
- **フィールドの型**：`fieldSchema.ts`（typecheck）が、TypeScript の型から `ValueSchema`（`packages/eks/src/schema.ts`）を作る。参照は、Host の宣言の `__tukurium` の印（`EntityRef`・`MaterialRef` など）と、名前の付いた interface（`KokoStateRef`・`FieldRef`）で見分ける。
- **プレハブ**（ADR 0076）：`PrefabDef` は、いちばん上の Entity・System・「維持」の印を持つ。展開は `PrefabExpansionCache`（`prefab.ts`）。インスタンスの上書きのキーは「ルートからの ID」。今は、プレハブのいちばん上の Entity の `instanceOf` は展開で読まない（バリアントはまだない）。
- **権限**：Host API の Capability は `HOST_API_SPEC` と repo-model の `HOST_CAPABILITIES` にあり、作る・消すは `entity.spawn`・`entity.destroy`。セッションでは、配置のときにコードから読み取った Capability と、与えた権限で判定する（ADR 0012）。

### 方針

1. **書き込みは、Host API の境目で合わせて「すぐ届く」ようにする。**
   - 一度に動くのは一つの System だけなので、呼び出しの途中で、ほかから World を読めるのは Host API を通るときだけ。そこで、書くたびにホストへ送るのではなく、Host API を呼ぶ直前と、呼び出しの終わりに合わせる。利用者からは、書いたその場で届いたのと同じに見える。
   - QuickJS の側で、`e.get()` が返した値のオブジェクトを「触れたもの」（Entity と KokoState の組）として覚える。Host API を呼ぶ直前に、「前に合わせてから触れたもの」と「いま処理している Entity のもの」の値を一緒に送り、ホストは今と同じ `writeNamed()`（前の値と比べ、変わって型の合うものだけ）で World に書く。
     - 触れたものすべてを毎回送ると、Entity ごとに Host API を呼ぶ System では、送る量が Entity の数の二乗で増える。そのため、送るのは上の二つに限る。
     - その代わり、前の Entity の値を変数に持っておき、あとで書き換えたときは、呼び出しの終わりに届く（それまでの Host API からは、前に合わせたときの値が見える）。この扱いを ADR に残す。
   - **比べる相手は、最後に合わせた値にする。** 今の `writeNamed()` は、呼び出しの初めの値（`before`）と比べる。そのままでは、`f = 3` が途中で届いたあとに `f = 0`（初めの値）へ戻すと、終わりに「初めと同じ」とみなされて届かず、World が 3 のまま残る。合わせるたび（ホストから値を返したときも）に、比べる相手をその値に更新する。
   - ホストは、Host API の呼び出しの間に、この呼び出しで渡した Entity の値が変わったか（`writeNamed`・`setField`・`setState`・消す・KokoState を付ける）を記録し、戻り値に添えて返す。QuickJS の側は、持っている値のオブジェクトを、その場で書き換える（同じオブジェクトを書き換えるので、`const g = e.get(Gun)` で持っている値にも届く）。
   - Host API を呼ばない System は、今と同じ重さ。呼ぶ System は、触れたものの分だけ重くなる。P0 と P2a で `pnpm bench:sim` に、Entity 1000 個を回して 1 個ごとに Host API を呼ぶ System の計測を足して比べる。
     - 合格の条件：Host API を呼ばない System（今の `bench:sim` の計測）は、P2a の前と比べて、計るたびのばらつきの範囲に収まること。
     - Host API を呼ぶ System は、遅くなった分を数字で PR に書く。P2a の前の 1.5 倍を超えたら、マージする前に計画者に相談する（送る範囲を狭める・取らない案を見直すなど）。
     - P0 の試し作りでこの条件に届かないと分かったら、P2a に進む前に計画者に相談する。
   - 取らない案：`e.get()` の値を Proxy にして、書くたびにホストへ送る（書くたびに境界をまたぎ、読むのも遅くなる）。ADR に理由を残す。
2. **System に Entity を渡す前に、まだあるか・まだ Query に合うかを確かめる。**
   - Host API の戻り値に、その呼び出しで消えた Entity と、KokoState が変わって Query に合わなくなったかもしれない Entity を添える。QuickJS の側は「この呼び出しで消えた・合わなくなった Entity」の一覧を持ち、順に回すときに照らして飛ばす。Entity ごとに外へ問い合わせない。
   - 消した Entity の子も一覧に入れる。`Prefab.destroy` も `world.destroy` も子ごと消す（`World.destroy` は子もたどって消す）ので、ホストは消す前に子の ID を集める。入れないと、同じ呼び出しの並びにある子が、そのまま渡される。
   - 合わなくなったかの判定はホストが行い、一覧に入れるのは合わなくなったものだけにする。リストで切り替える（ロードマップの「プレハブのリストから子を組み立てる」）ときも、同じ口を使う。
   - **呼び出しの途中で作った Entity は、同じ System の、同じ呼び出しの中でも、すぐ扱える。**
     - 作った Entity は、ホストの World にすぐ入るので、作った直後から Host API（`world.getState` など）で読み書きできる。
     - 呼び出しの並びに足すのは、Query に合うものを全部回す `onUpdate` だけ。`onEvent`・`onCollision`・Contract は決まった相手一つに呼ぶもの、`onInput` は入力した人（装備）で相手を絞ったものなので、足さない（作った Entity は、次に合う出来事から受け取る）。
     - `onUpdate` で、作った Entity がいま動いている System の Query に合い、呼び出しの初めに使う `matches()` と同じ条件（セッションでは、その System を使う配置の Entity であること（`withinUsers()`）と、方針 8 の配置ごとの「動かす印」）にも合えば、ホストは Host API の戻り値に、その Entity の値を添える。QuickJS の側は、それを回している並びの後ろに足す。今の順番の Entity が終わったあと、同じ呼び出しの中で、作った Entity にもハンドラが呼ばれる（`onUpdate` で Bullet を作ると、その Bullet の `onUpdate` も同じフレームのその場で動く）。
     - 足した Entity が、さらに作ることもできる。止まらないときは、今と同じく呼び出しの時間制限で止まる。そのうえで、一つの呼び出しで足せる数に上限を設ける（数は、実装者が P0 で計って決め、ADR に残す）。上限を超えた分は、この呼び出しでは渡さず、次に呼ばれたときから渡す。ログで知らせる。
     - 同じフレームのあとの System には、呼び出しの初めに Query を引き直すので渡る。
   - 消えた Entity の値を、そのあと読み書きしたとき：書いた値は、ホストが受け取らず、問題（ログの警告）として出す。QuickJS の側では、消えたと分かった時点で、その Entity の値のオブジェクトのフィールドを、読むと問題を出して `undefined` を返す形に置き換える（消したときだけの手間で、ふだんの読み書きは重くならない）。
     - 消えた Entity の `e.get()` も、この置き換えたオブジェクトを返す（`undefined` を返すと、`e.get(X).y` が TypeError を投げ、System が止まるため）。System は止めない。
     - 消えた Entity は、合わせるときと、呼び出しの終わりの書き出しから外す。外さないと、書き出すときに置き換えたフィールドが読まれ、利用者が読んでいないのに問題が出る（ホストは、どのみち受け取らない）。
   - 今の `world.spawn`・`world.destroy` でも、同じ仕組みで働く。
3. **デバッグ実行も、同じ仕組みに合わせる。**
   - 非同期版の QuickJS でも、同じ前置き（PRELUDE）の同期を使う。
   - **一時停止の所も、合わせる境目にする。** 合わせるのが Host API の境目だけだと、最後の Host API のあとで `e.get()` に書いた値は、止まった時点でまだ World にない。止まるときに、Host API を呼ぶ直前と同じく World へ書く。停止中に利用者が変えた値は、ホストの変化を返すのと同じ口で QuickJS に返す。これで、一時停止の画面に「まだ返していない `e.get()` の変更」を写し、続ける前に戻す処理（`activeDebugApply`）を外せる。前の Entity の値を変数に持って書き換えた分は、止まった画面でも、前に合わせたときの値に見える（方針 1 と同じ扱い）。
   - 見張り（ADR 0080）で、`e.get()` の値の変化と Host API による変化を分ける記録は、World に書く口（QuickJS から合わせて届いた書き込みか、Host API の中の書き込みか）で分ける。
4. **プレハブの値は、プレハブの ID の文字にする。インスタンスの値は、いちばん上の Entity の参照にする。**
   - `import Bullet from "./Bullet.prefab"` は `const Bullet = "<プレハブの ID>"` に書き換える。フィールドに入れたプレハブの値も同じ文字なので、`Prefab.spawn(Bullet, …)` と `Prefab.spawn(e.get(Gun).bullet, …)` が同じに働き、比べることもできる。値の形式（ADR 0065）にも、そのまま乗る。マテリアル・3D モデルなどの import も、同じく ID の文字にする（型は `MaterialRef`・`ModelRef` など）。
   - インスタンスの値は、作ったいちばん上の Entity の ID（型の上では `EntityRef` の一種）。今の `world.getState` などにも、そのまま渡せる。
   - フィールドの型の `ValueSchema` に、`{ kind: "prefab", prefab }`（プレハブ型）と `{ kind: "prefabInstance", prefab }`（インスタンス型）を足す。保存の形は文字。
     - `packages/eks/src/schema.ts` で、値の種類ごとに分かれて働く関数すべてに、二つを足す：`validateValue`・参照をたどる `visitRefs`・`mapRefs`・`hasRefs`・`refTargetOf`・`isJsonSafe`・`acceptsUndefined`・`emptyValueOf`・`conformValue`。参照をたどる関数に足し忘れると、フィールドに入れたプレハブが、依存グラフ・抽出・ID の付け替え・指す先がないときの問題から漏れる。`isJsonSafe` に足し忘れると、値の形式で運ぶフィールドに入り、遅くなる（どちらも文字なので、JSON で表せる）。
     - 消したプレハブを指しているときは、今の `missing-resource` と同じく問題として出す。
     - `fieldSchema.ts` は、`__tukurium` の印を `REF_BRANDS` で読む。プレハブ型の印 `"Prefab"` を足す。インスタンス型は `EntityRef & …` なので印が `"EntityRef"` になり、そのままでは、ふつうの Entity の参照（`{ kind: "ref", target: "entity" }`）と読まれる。`__instance` があるかを先に見る。
     - **`ValueSchema` の `prefab` は、プレハブの ID を一つ持つ。** 型の印 `B`（方針 5）は、自分と元のプレハブの ID をすべて並べたものなので、型だけでは、どれが自分か分からない。`fieldSchema.ts` は印の ID の並びを読み、その並びとちょうど同じ「自分と元の並び」を持つプレハブを、当てはまりの判定（方針 6。repo-model）で引いて、その ID を入れる（元の並びはプレハブごとに違うので、一つに決まる）。見つからなければ、型の問題として出す。
     - **プレハブにも、仮の宣言を用意する。** フィールドの型は、本当の宣言を作る前に確かめている（型エラーのあるフィールドを unknown にするため。KokoState は `kokoStateStub()` の仮の宣言を使う）。プレハブの本当の宣言は、パラメータの型にフィールドの型を使うので、同じく仮の宣言（印 `B` だけを持ち、パラメータは何でも受ける）でフィールドの型を確かめ、そのあとに本当の宣言を作る。
   - **「なし」は `undefined`**（ADR 0065 の参照と同じ）。インスタンス型のフィールドは、制作データでは必ず「なし」なので、`InstanceOf<Koma> | undefined` と書く（`| undefined` がなければ、型の問題として出す）。制作データでは `undefined` だけを受け付ける（Inspector・エージェントの道具から値を入れても断る）。プレハブ型のフィールドは、初めの値を決めないなら `| undefined` を書く。
   - **プレハブ型のフィールドに実行中に書く値は、型に当てはまるか（方針 6 の判定）に加えて、その配置から依存でたどれるプレハブか（方針 8）も `accepts()` で確かめる。** たどれないプレハブを書けると、あとで `Prefab.spawn` に渡しても作れないため。
   - **インスタンス型のフィールドに入れられる値は、実行中に確かめる。** `world.setField` などで書くとき、その値が実行中に作ったインスタンスで、作った元のプレハブがフィールドの型に当てはまるか（方針 6 の判定）を `accepts()` で確かめる。合わなければ書かない。
     - 実行中に作ったインスタンスは、次の二つ（計画者に確認した）。
       - `Prefab.spawn` で作ったいちばん上の Entity（`spawnedFrom` にある）。
       - その中の、入れ子のプレハブのインスタンスのいちばん上の Entity（作った Bullet の中の Trail など）。どのプレハブのものかは、Entity の ID（`rt:5/…`）の、いちばん上を除いた道筋を、展開したひな形（方針 8）に照らして求める。`spawnedFrom` には足さない（通信の形を増やさない）。
     - 制作データに置いたインスタンスは入れられない（構想のとおり、インスタンス型のフィールドの値は、実行中に作ったインスタンスだけ）。
5. **型の書き方：プレハブ型とインスタンス型は、ID の印と、パラメータを受け取る関数の形で決める。**
   - Host の宣言に、次の形を足す（細かい書き方は P0 で、tsc の単体テストで確かめて決める）。
     ```ts
     // B：自分と元のプレハブの ID を並べた印（{ "id_駒": true; "id_赤い駒": true }）
     // P：パラメータ。I：インスタンス型
     type PrefabType<B, P, I> = string & {
       readonly __tukurium: "Prefab";
       readonly __prefab: B;
       readonly __create: (params: P) => I;
     };
     type PrefabInstance<B> = EntityRef & { readonly __instance: B };
     type InstanceOf<T> = T extends PrefabType<any, any, infer I> ? I : never;
     ```
   - 印のプロパティ（`__prefab`・`__create`・`__instance`）は、型のためだけのもので実行時にはないが、必須にする。省略できるプロパティにすると、それを持たない型（ふつうの `EntityRef` など）も当てはまってしまい、制作データの Entity を `Prefab.destroy` に渡しても型エラーにならないため。値はホストが返すもの（import・フィールドの値・`Prefab.spawn` の戻り値）だけなので、必須でも困らない。P0 のテストに、`e.id` を `Prefab.destroy` に渡すと型エラーになる場合を入れる。
   - 印 `B` は、自分と、たどれるすべての元のプレハブの ID を持つ。バリアントは元の ID も持つので元の印に当てはまり、同じ構造の別のプレハブは ID が違うので当てはまらない。
   - `__create` の引数は反変で確かめられるので、バリアントが必須のパラメータを足すと元のプレハブ型に当てはまらず、省略できるものだけなら当てはまる（TypeScript のクラスのコンストラクタと同じ）。
   - インスタンス型は印だけで決まり、バリアントのインスタンスはいつも元のインスタンス型に当てはまる。インスタンス型の中の KokoState と子の Entity の形は、宣言に型だけ持たせ、読み書きの書き方は、ロードマップの「実行中に現れるものをプレハブで決めて静的に安全にする」で足す。
   - プレハブごとに宣言ファイル（`/Bullet.prefab.d.ts`）を作り、`export default` で値と型の両方を出す（KokoState と同じ）。パラメータの型は、指すフィールドの型の文、説明は JSDoc にする。
   - **フィールドの型の文でプレハブを使うときは、import で指す**（計画者に確認した。構想の「KokoState と型の定義のリソースは、プレハブ型とインスタンス型を import して使える」のとおり）。
     - 今、フィールドの型の文は一つの型の式で、import を書く所がない。KokoState は名前で自動的に結び付けている（`KokoStateRef<Health>`。`kokoImports()`）。プレハブも名前で結び付けると、KokoState「Bullet」とプレハブ「Bullet」のような、よくある重なりで、どちらを指すか決まらない。
     - そこで、KokoState に「import するプレハブ」の並び（`prefabImports`）を持たせる。今の「使う型の定義」の並び（`KokoStateDef.typeDefs`）と同じ置き方で、一件は `{ prefab（プレハブの ID）, name（この KokoState の型の文で使う名前） }`。ID で持つので、プレハブの名前を変えたり動かしたりしても切れない。
     - 画面では、KokoState のフィールドを作る所に `import Koma from "./Koma.prefab"` の形で並べ、プレハブは候補から選ぶ。名前は、初めはプレハブの名前で、変えられる。足すときに、その名前が下の「重なり」に当たるなら、初めの名前を `BulletPrefab` のように、後ろに `Prefab` を付けたものにする（それも重なるなら、数字を付ける）。KokoState は、プロジェクトのどれも名前で自動的に指せるので、Bullet のプレハブと KokoState「Bullet」のような、いちばんよくある形で、足したとたんに問題が出ないようにするため（計画者に確認した）。
     - 型の文では、その名前で書く（`Koma`・`InstanceOf<Koma>`）。宣言ファイルには、この並びから `import type 名前 from "…"` を作る（`typeImports()` と同じ）。
     - 名前が、その KokoState の型の文から名前で指せるもの（KokoState・使う型の定義が公開している型・ほかの import）と重なったら、問題として出す（利用者が自分で重なる名前に変えたときと、あとから同じ名前の KokoState・型ができたときに起きる）。直すには、import の名前を変える（`import BulletPrefab from "./Bullet.prefab"`）。import していないプレハブの名前は、型の文で使えない（今の「名前が見つからない」型エラーになる）。
     - 型の定義のリソースは、今も import 文を書けるので、`import type Koma from "./Koma.prefab"` をそのまま書く。スクリプトも import のパスで指す。
   - `Prefab.spawn` は `spawn<T extends PrefabType<any, any, any>>(prefab: T, ...params: 必須があれば [P] なければ [P?]): InstanceOf<T> | undefined` の形にし、ないパラメータはオブジェクトの書き方の余分なプロパティとして型エラーにする。
   - **作れなかったときは `undefined` を返し、型にも `| undefined` を入れる**（計画者に確認した）。セッションで権限がない・依存でたどれない・配置ごとの作れる Entity の数の上限（方針 8）を超える、などで、作れないことがあるため。使う側は、使う前に確かめる（`const b = Prefab.spawn(Bullet, { Speed: 20 }); if (b) { … }`）。原則 5（安心して作れる）に合わせる。
6. **バリアントは、この項目では「いちばん上の Entity が別のプレハブのインスタンスになっているプレハブ」として、型と当てはまりだけを作る。**
   - 印 `B` の並びとパラメータの受け継ぎは、`instanceOf` をたどる関数（repo-model）で作り、手で作った制作データの単体テストで確かめる。バリアントの展開・作る画面は、ロードマップの「プレハブの一部を上書きしてバリアントを作る」で作る。
   - 「プレハブがプレハブ型に当てはまるか」（Inspector の候補・制作データの値の確かめ・実行中の `accepts()`）は、型の決まりと同じ判定を repo-model に一つ置き、どこからもそれを使う。
7. **パラメータは、プレハブの定義に持つ。**
   - `PrefabDef.params`：パラメータの ID → `{ name, entity（ルートからの ID。上書きのキーと同じ）, koko, field（フィールドの ID）, required, description, order }`。共同編集では、パラメータごとの `Y.Map`（ほかのプレハブの定義と同じく、フィールドごとの後勝ち）。Git には、プレハブの JSON に入れる。保存の形は変えてよい（プロトタイプ）。
   - 名前は、初めはフィールドの名前。一つのプレハブの中と、元のプレハブとの間で重ならない（重なったら問題として出す）。
   - 制作データに置いたインスタンスでは、パラメータの値は、今の上書き（`prefabOverrides`）そのもの。必須のパラメータに上書きがなければ、問題（エラー）として出す。
   - 必須のパラメータの問題は、次のように出す。
     - バリアントのいちばん上（元のプレハブのインスタンス）には出さない。バリアントは必須のパラメータを受け継ぎ、そのまま必須のままなので。
     - プレハブの中に置いたインスタンスでは、上書きで値を決めているか、外側のプレハブの**必須の**パラメータがそのフィールドを指していれば、埋まったものとする（外側のパラメータが省略できるものだと、外側を作るときに渡さなければ、内側の必須のパラメータが黙ってプレハブの値になるため）。埋まっていなければ、そのプレハブを相手に問題を出す。
   - ただし、いちばん上の Entity の Transform のフィールドを指すパラメータは、上書きではなく、インスタンスそのものの Transform に結び付ける（ADR 0076 で、インスタンスの場所・向き・大きさは、上書きに数えないため）。置いたインスタンスはいつも Transform を持つので、必須でも問題にしない。`Prefab.spawn` で渡したときは、作ったインスタンスの Transform に入れる。これで、弾を銃の位置に出すときは、Transform の位置をパラメータにして渡せる。
   - パラメータが指すフィールド・KokoState・Entity を消すときは、確認を出す。消したら、そのパラメータを問題（エラー）として出す。
8. **実行中に作る・消す。**
   - `Prefab.spawn(prefab, params?)`：呼んだ配置の制作データ（と依存のライブラリ）から、そのプレハブを展開した Entity の並びを作る関数（repo-model。今の展開の仕組みを、インスタンスを一つ持つ仮の制作データで使う）で中身を作り、パラメータの値を上書きとして重ねる。
     - 作るたびに展開し直すと、毎フレーム何十個も作るときに重い。プレハブごとの「展開したひな形」を、制作データの版ごとに取っておき、作るときは ID を付け替えてパラメータを重ねるだけにする。重さは `pnpm bench:prefab` に「1 フレームに 100 個作る」場合を足して測る。
     - ID は「新しく作るインスタンスの ID ＋ 中の Entity の ID」（ADR 0076 と同じ作り方）。親は `world.spawn` と同じく、配置の空間のいちばん上。
     - World に入れるときは、配置を作るとき（`instantiate()`）の Entity ごとの処理をそのまま通す：KokoState の ID に領域を付ける（`kid()`）、登録のない KokoState を飛ばす、値を型に合わせる（`conformValue`）、Mesh のマテリアルの ID を付け替える（`mid()`）、プレハブの中の Entity の参照を新しい ID に付け替える（`mapRefs`）。この処理を関数に出して、両方から使う。ただし、パラメータで渡した値は、すでに実行中の値（Entity の参照なら実行中の ID）なので、付け替えずに、型の確かめ（`accepts()`）だけを通して重ねる。
     - 名前は、プレハブの中の Entity の名前を、今の `world.spawn` と同じく `this.names` に入れる（実行中の画面とデバッグ実行が、ここから名前を出す。入れないと `rt:5` のような ID で出る）。ホストが替わったときの引き継ぎも、今の名前の引き継ぎと同じ。
     - 型の合わない値・ないパラメータ・足りない必須のパラメータが実行中に届いたら（型エラーを無視して再生したとき）、その値を使わず、問題（ログの警告）として出す。
   - **配置ごとに、実行中に作れる Entity の数の上限を設ける**（計画者に確認した）。バッグの `BAG_LIMIT` と同じく決まった数にし、数は、実装者が P0 で計って決め、ADR に残す（同梱のサンプルが今作っている数より十分大きくする）。プレハブの中の Entity も一つずつ数え、消せば減る。超えるときは、`Prefab.spawn` は何も作らず `undefined` を返し、ログで知らせる。今の `world.spawn` にも同じ上限をかける（超えたら作らない）。作り続けるスクリプトで、ホストのメモリと、セッションで毎フレーム配る状態が増え続けないようにする。数えるのは、配置の Entity（`part.entities`）のうち、ID が `rt:` で始まるもの（実行中に作った物。`World.newRuntimeId()` が付ける。プレハブの中の物も `rt:5/…`）。制作データに置いた物は数えない。配置の Entity はホストが替わっても引き継ぐので、数も同じになる。
   - **作れるのは、その配置から依存でたどれるプレハブだけ。** プレハブの値は ID の文字なので、型を外して書けば（`Prefab.spawn("…" as any)`）、どの ID でも渡せてしまう。ホストは、配置のときに求めた「依存でたどれるプレハブ」の一覧と照らし、ないものは作らずに拒んだときの値を返す（セッションの境界。ADR 0012）。権限を読み取る範囲・System を読み込む範囲と、同じ一覧を使う。
     - 「依存でたどれる」は、先までたどる（アウトプット → プレハブ → そのプレハブの System → その System が import するプレハブ、フィールドの値・型で指すプレハブ、入れ子のプレハブ）。
     - セッションでは、QuickJS が見る KokoState の ID は領域の中の ID（`kid(realm, key)`）。プレハブの ID は、これと違い、World の中でも QuickJS の中でも、制作データの ID のまま持つ（領域を付けない）。作るときに、ホストが、呼んだ配置の版（`part.realm`）の制作データで引く。
       - こうしてよい理由：System が触れるのは自分の配置の Entity だけで（`own()`）、フィールドの値を読む配置と、作る配置がいつも同じ。今も、フィールドの中の参照で配置のときに付け替えているのは Entity だけ（`instantiate()` の `mapRefs`）。
       - import した値とフィールドの値が同じ文字なので、そのまま比べられ、QuickJS との境目で付け替える手間もない。
       - 適用で版が変わっても、ID は変わらないので、フィールドの値を付け替えなくてよい（新しい版にそのプレハブがなければ、作れずに `undefined`）。
   - 作った Entity は、呼んだ配置に入れる。いちばん上の Entity → プレハブの ID の対応（`spawnedFrom`）を Simulation に持ち、次のすべてに入れる。
     - フレームと、ホストが替わったときの引き継ぎ（`protocol.ts` を変え、`PROTOCOL_VERSION` を上げる）
     - デバッグ実行の巻き戻しの点（`makeDebugCheckpoint()`・`restoreDebugCheckpoint()`）。入れないと、巻き戻したあとに `Prefab.destroy` で消せなくなる
   - **`spawnedFrom` からは、いちばん上の Entity がどの口で消えても外す。** `world.destroy` は自分の配置の Entity なら何でも消せるので、`Prefab.spawn` で作ったインスタンスも消せる。`Prefab.destroy` のときだけ外すと、消えたインスタンスが「残っている」と数えられ、プレハブの System が動き続け、上限の数え方ともずれる。World から Entity が消える所（`world.destroy`・`Prefab.destroy`・`clearEntities()`）で、まとめて外す。
   - `Prefab.destroy(instance)`：`spawnedFrom` にあり、呼んだ配置のものだけを、子ごと消す。ほかのものは何もせず `false` を返す。
     - 入れ子のインスタンス（作った Bullet の中の Trail）は、型の上では渡せるが、消さずに `false` を返し、ログで知らせる。消せるのは、自分で作ったいちばん上だけにする（中の一部だけを消すと、プレハブの形が崩れるため）。ADR に残す。
   - **プレハブの System は、配置のときに先に読み込んでおき、動かすかどうかは別に決める。**
     - `Prefab.spawn` は System の呼び出しの途中の Host API の中で動くが、`ScriptSandbox.loadSystem()` は実行中だと読み込めない（「実行中のスクリプトは読み込み直せません」）。そこで、配置のとき（`addPart`）に、依存でたどれるプレハブの System（入れ子の分も）を、アウトプットの System の後ろに読み込んでおく（ADR 0076 の足し合わせ：アウトプットのものが先）。その場で読み込む手間と、読み込みにかかる時間でフレームが止まることもなくなる。
     - 読み込んだだけでは動かさない。プレハブの System の Query が、アウトプットにある関係ない Entity にも合うことがある（例：Bullet の System の Query が `[Velocity]`）。今は、インスタンスを置いたときだけ足される（ADR 0076）ので、読み込んだらすぐ動かすと、動きが変わってしまう。
     - プレハブの System が動くのは、そのプレハブのインスタンスが、アウトプットに置いてあるか、実行中に作られて残っている（`spawnedFrom` にある）間だけ。この印は `spawnedFrom` と制作データから求めるので、通信の形は増えず、ホストが替わっても、デバッグ実行で巻き戻しても同じになる。
     - 求め方：Simulation が持つ配置の制作データは、展開したあとのもので、アウトプットの System の並びには、置いたインスタンスのプレハブの System が、もう足し合わされている（`PrefabExpansionCache` の `mergeSystems`）。この並びは、今のまま、いつも動かす。「置いてあるか」を別に求め直さなくてよい。これに、作って残っているインスタンスのプレハブ（入れ子も）の System を、同じ `mergeSystems` の決まりで足したものが、その配置で動かす System になる。「アウトプットが勝つ」を決めるために、展開する前のアウトプットの System の並びも、配置に持っておく。
     - **印は「System と配置の組」ごとに持つ。** セッションで同じアウトプットを二つ置くと、System は同じ領域で一つになる（`sys.users` に両方の配置が入る）。印が System に一つだけだと、配置 A で Bullet を作っただけで、Bullet のない配置 B の関係ない Entity でも動いてしまう。System が処理する Entity は、印の付いた配置のものだけにする（今の `withinUsers()` と同じ絞り方）。
     - **入れ子もたどる。** `spawnedFrom` に入るのは作ったいちばん上のプレハブだけなので、作ったプレハブが入れ子で含むプレハブ（Bullet の中の Trail など）も、たどって「作られて残っている」に数える。入れ子のインスタンスは `world.destroy` で消せるので、数えるのは、そのいちばん上の Entity が World に残っているものだけにする。
     - **「入・切」は ADR 0076 の足し合わせに従う。** どれかのプレハブで「入」なら「入」、アウトプットにもあれば、アウトプットが勝つ。実行中に作って動かすときも、同じ決まりで決める。
     - 呼び出しの途中で作って印が変わったら、同じフレームのあとの System の並びから動く（いま動いている System の並びは変えない）。
   - セッションでは、配置のときに読み取る Capability に、この先に読み込むプレハブの System の分も含める。すべて、配置のときに確かめた権限の中で動く。
   - 「適用」と「リセット」では、その配置で実行中に作ったインスタンス（`spawnedFrom` にあるもの）をすべて消す（リセットは構想にないが、今の `resetPart()` は `clearEntities()` で配置の Entity をすべて消して作り直すので、`world.spawn` で作った物も、今すでに消える。インスタンスも同じ所で消える。足すのは、その配置の `spawnedFrom` を空にすることだけ。適用の `clearEntities()` も同じ）。プレハブの System の動かすかどうかの印も、これに合わせて元に戻る。
   - 「適用」では、新しい版で、依存でたどれるプレハブの一覧・先に読み込む System・Capability を求め直す（今の `applyPart()` が読み直すのは、アウトプットの System だけ）。プレハブが増えた・減った・System のコードが変わった場合に合わせる。権限が増えたときは、今の適用と同じく、配置のときに確かめた権限の中で動く。
   - Host API は `Prefab.spawn`・`Prefab.destroy` の二つを `HOST_API_SPEC` と `HOST_CAPABILITIES` に足す（Capability は今の `entity.spawn`・`entity.destroy`）。名前空間の名前が大文字で始まるので、前置き・宣言・Capability の読み取りが `Prefab` を扱えるかを確かめる。
9. **import と依存。**
   - System は `.prefab`・`.material`・素材（`.model` など）を default import できる。KokoState のフィールドの型の文は、KokoState の「import するプレハブ」の並び（方針 5）で付けた名前で、プレハブ型と `InstanceOf<…>` を使える。型の定義のリソースは、`import type Koma from "./Koma.prefab"` で使える。
   - 依存グラフに、System → プレハブ（import）、KokoState（`prefabImports`）・型の定義（import） → プレハブ（型）、Entity・プレハブの中の値 → プレハブ（フィールドの値）の辺を足す。抽出・ライブラリ・リリースは依存グラフをたどるので、一緒に持っていく。
   - **フィールドの値や型で指すことによる輪は許す。** 例：Bullet のプレハブの中の KokoState が、フィールドの初めの値で Bullet 自身を指す（分かれて増える弾など）。これは「中に含む」ことではないので、入れ子の決まり（自分を含む形はできない。ADR 0076）の対象外。そのかわり、依存グラフ・抽出・ライブラリ・「依存でたどれるプレハブ」を求める所は、輪になっても止まらずにたどれるようにする（一度通ったものは飛ばす）。宣言ファイルどうしが互いに import し合うのは、TypeScript が扱える。
   - 名前の変更・移動での import の書き直し（ADR 0010）と、抽出での書き換えを `.prefab` などにも広げる。
   - **フィールドに入れたプレハブの ID も付け替える。** ライブラリを読み込むとき（`pkg:` の ID）と、抽出・フォークで ID が変わるときは、今、参照と上書きの ID を付け替えている（ADR 0076）。プレハブ型のフィールドの値（KokoState の初めの値・Entity とプレハブの中の値・上書き）も、スキーマを見て同じく付け替える。
   - エディタ（ADR 0079）：import のパスの候補に `.prefab` を出す。コードホバーは宣言ファイルから出る。定義へ移動でプレハブを開く（ADR 0076 の `editingPrefab`）。
10. **`Prefab` は予約語にする。** KokoState・プレハブ・型の定義・System などのリソースの名前が `Prefab` なら、問題として出す（`reserved-name`）。大文字・小文字は区別する（`prefab` はよい）。
11. **静的に危ない Host API と書き方に、先に `@deprecated` を付ける。**
    - `HOST_API_SPEC` の項目に、安定度 `deprecated` と理由（`deprecatedReason`）、代わりの書き方を持たせ、宣言に `@deprecated 理由` の JSDoc を書く。エディタの打ち消し線は TypeScript の候補・診断（`reportsDeprecated`）を CodeMirror に出す。
    - 打ち消し線とホバーの理由は、エディタの中だけに出す。問題の一覧（問題をまとめて確かめる所）には出さない。`world.get`・`world.set` などは公式ライブラリと同梱サンプルで多く使っていて、出すと問題だらけに見えるため。
    - ADR 0019 の `deprecated` は「後継があり、いずれ外す」なので、「後継がある、または追加予定で、いずれ外す」に直す。
    - `Prefab.spawn`・`Prefab.destroy` は P5a で作るので、P1 では `world.spawn`・`world.destroy` にも「代わりの書き方は追加予定」と書き、P5a で代わりの書き方に書き換える。
    - 付けるもの：`world.spawn`（代わりは、P5a から `Prefab.spawn`）・`world.destroy`（代わりは、P5a から `Prefab.destroy`）・`world.find`・Entity を ID の文字で受け取る・返す Host API すべて（`world.get`・`world.set`・`world.getState`・`world.setState`・`world.getField`・`world.setField`・`world.emit`・`audio.play` の Entity など。代わりは追加予定）。書き方では、KokoState を名前の文字で指すもの。
    - **作ったインスタンスを読み書きする Host API（`world.getState` など）にも付ける**（計画者に確認した）。この項目では、`Prefab.spawn` で作ったインスタンスの中を読み書きする書き方がこれしかないので、新しい書き方で書いたコードにも打ち消し線が出る。代わりの書き方（インスタンス型から読み書きする）は、ロードマップの「実行中に現れるものをプレハブで決めて静的に安全にする」で足すので、理由には「追加予定」と書く。
    - P1 では、`HOST_API_SPEC` を一件ずつ見て、上の決まり（Entity を ID の文字で受け取る・返す）に当てはまるものをすべて拾う。当てはまるか迷うものは、計画者に聞く。
12. **AI エージェントも、同じことができる。** パラメータを足す・直す・消す、インスタンスのパラメータの値を決める道具を MCP に足す（`apps/server/src/agent/tools.ts`）。KokoState の「import するプレハブ」を足す・名前を変える・外す道具も足す。フィールドの型の文そのものは、今のフィールドの道具で書ける。
13. **大きな判断は、新しい ADR に残す。** 型の書き方、プレハブとインスタンスの値の形、パラメータの持ち方、書き込みの合わせ方（送る範囲と、前の Entity の値が終わりに届く扱い）と Entity を渡す前の確かめ、比べる相手を最後に合わせた値にすること、一時停止も境目にすること、同じ呼び出しの中で作った Entity を渡すこと（`onUpdate` だけ）と上限、実行中に作ったものの持ち方と引き継ぎ、作れるプレハブの範囲、セッションでプレハブの ID を領域を付けずに持つこと、System を先に読み込むことと動かす印（System と配置の組ごと・入れ子・「入・切」）、展開したひな形を取っておくこと、`Prefab.spawn` が作れなかったときの `undefined`、配置ごとの作れる Entity の数の上限、権限、フィールドの型の文でプレハブを import で指すこと（`prefabImports`）、入れ子のインスタンスの扱い（フィールドに入れられる・`Prefab.destroy` では消せない）、重さの合格の条件、`@deprecated` を付ける範囲、予約語。番号は PR を出す直前に、最新の次を確かめて付ける。

## 確かめ方

- 単体テスト
  - 型（typecheck）：P0 の当てはまりと型エラー。`Prefab.spawn` の引数（必須・省略・ない・合わない）と、戻り値を確かめずに使うと型エラーになること。インスタンス型のフィールドに `| undefined` がないと問題になること。KokoState のフィールドにプレハブ型・インスタンス型を書けること（import したプレハブの名前で。import していない名前は型エラー、名前が KokoState と重なると問題。KokoState と同じ名前のプレハブを足すと、初めの名前に `Prefab` が付くこと）。バリアントのプレハブ型のフィールドの `ValueSchema` に、バリアント自身の ID が入ること。`ValueSchema` の読み取り
  - 当てはまりの判定（repo-model）：バリアントの印の並び、パラメータの受け継ぎ、名前の重なり、自分を含む形
  - パラメータ：保存と共同編集、必須が埋まっていない問題（バリアントのいちばん上には出ないこと、外側の必須のパラメータで埋まり、省略できるものでは埋まらないこと）、指すものが消えた問題、`Prefab` の予約語
  - 実行（runtime）：`e.get(X).y = 1` のあと `world.get` で読むと書いた値。Host API で書いた値が、同じ呼び出しのあとの Entity と、持っている値に届くこと。消したインスタンスが、同じ呼び出しのあとの順番で渡されないこと。作った Entity が Query に合えば、同じ呼び出しの中でハンドラが呼ばれ、上限を超えた分は次の呼び出しに回ること。消えた Entity への書き込みが届かず、問題が出ること。消えた Entity の `e.get(X).y` で System が止まらず、読んでいないのに問題が出ないこと。途中で届いた値を初めの値に戻すと、World も戻ること。`onEvent`・`onCollision`・`onInput`・Contract には、作った Entity が足されないこと。セッションで、ほかの配置・動かす印のない配置の、作った Entity が足されないこと。消した親の子が、同じ呼び出しのあとの順番で渡されないこと。デバッグ実行でも同じこと。一時停止の画面に、止まる前に `e.get()` に書いた値が出ること
  - 作る・消す：パラメータの重ね方（Speed は 20、Damage はプレハブの値）。アウトプットにインスタンスがなくても、作った Bullet でプレハブの System が動くこと。インスタンスがない間は、プレハブの System がアウトプットの関係ない Entity で動かないこと。セッションで同じアウトプットを二つ置き、片方で作っても、もう片方の関係ない Entity では動かないこと。作ったプレハブの中の入れ子のプレハブの System も動くこと。「入・切」の足し合わせ。適用で、新しく依存でたどれるようになったプレハブを作れること。作れなかったときに `undefined` が返ること。上限を超えると、`Prefab.spawn` は `undefined` を返し、`world.spawn` も作らず、消すとまた作れること。依存でたどれないプレハブを、プレハブ型のフィールドに書けないこと。インスタンス型のフィールドに、作ったインスタンスでない値や、当てはまらないプレハブのインスタンスを書けないこと。作ったインスタンスの中の入れ子のインスタンスは書けて、`Prefab.destroy` では消えず `false` が返ること。セッションで、import したプレハブの値と、フィールドから読んだプレハブの値が同じになること。制作データの Entity は `Prefab.destroy` で消えないこと。作ったインスタンスを `world.destroy` で消すと `spawnedFrom` から外れ、プレハブの System が止まり、上限の数も減ること。入れ子のインスタンスを `world.destroy` で消すと、そのプレハブの System が止まること。ホストが替わっても、デバッグ実行で巻き戻しても `spawnedFrom` が残ること。適用・リセットで消えること。セッションの権限。依存でたどれないプレハブの ID を渡しても作れないこと。いちばん上の Transform を指すパラメータで、作る場所を決められること
  - 依存：フィールドの値でプレハブ自身を指す輪があっても、依存グラフ・抽出・依存でたどれるプレハブの計算が止まること。System の import・フィールドの値・型からプレハブへ辺があり、抽出とライブラリで一緒に持っていくこと。フィールドに入れたプレハブの ID が付け替わること。消したプレハブを指すフィールドの値が問題になること
  - エージェントの道具
- 計測：`pnpm bench:sim`（P2a の前とあと。合格の条件は方針 1）。Entity 1000 個を回して 1 個ごとに Host API を呼ぶ System の計測を足す。`pnpm bench:prefab` に、1 フレームに 100 個作る場合を足す（P5a）。
- 背骨の E2E：通信と再生の流れに触れる P2a〜P2c・P5a〜P5c のマージのあと、`main` の E2E の結果を確かめる。背骨の流れは変えないので、E2E は直さない予定。
- 画面：「プレハブの設定」のパラメータ、目立つ印、消すときの確認、プレハブ型のフィールドの候補、KokoState の「import するプレハブ」、エディタの打ち消し線・ホバー・定義へ移動を、`verify-change` スキルの手順（使い捨てのスクリプトとスクリーンショット）で確かめる。

## 構想から変えたこと

- バリアントの項目より先に、この項目を作る（計画者に確認した）。バリアントに関わる完了の条件は、型の決まりを単体テストで確かめ、画面での確かめは、バリアントの項目のあと（P7）に行う。
- 構想の「作ったものは、同じフレームのあとの処理からも見える」は、同じ System の同じ呼び出しの中も含める（計画者に確認した）。`onUpdate` で作った Entity が、いま動いている System の Query に合えば、その呼び出しの中で `onUpdate` が呼ばれる（`onEvent`・`onCollision`・`onInput`・Contract には足さない）。止まらなくならないよう、一つの呼び出しで足せる数に上限を設ける。
- 配置ごとに、実行中に作れる Entity の数の上限を設け、`world.spawn` にもかける（計画者に確認した。構想にはない）。
- `Prefab.spawn` は、作れなかったときに `undefined` を返し、型にも `| undefined` を入れる（計画者に確認した）。構想の例（`Prefab.spawn(Bullet, { Speed: 20, Damage: 5 })`）のあとに、使う前の確かめが要る。
- `Prefab.spawn` で作ったインスタンスの中の、入れ子のプレハブのインスタンスも、インスタンス型のフィールドに入れられる（計画者に確認した）。ただし `Prefab.destroy` で消せるのは、自分で作ったいちばん上だけ。
- `@deprecated` は、作ったインスタンスを読み書きする Host API（`world.getState` など）にも付ける（計画者に確認した）。この項目の間は、新しい書き方のコードにも打ち消し線が出る。
- KokoState のフィールドの型の文でプレハブを使うために、KokoState に「import するプレハブ」の並びを足す。名前が重なるときは、初めの名前に `Prefab` を付ける（計画者に確認した。構想の「import して使える」を、型の文に import を書く所がない今の作りに合わせた形）。

## 分かったこと・残り

- 今は、プレハブのいちばん上の Entity の `instanceOf` を展開で読まない。バリアントの展開は、ロードマップの「プレハブの一部を上書きしてバリアントを作る」で作る。
- 場所・向き・大きさを決めて作りたいときは、いちばん上の Transform のフィールドをパラメータにする（パラメータのほかは渡せない、という構想の決まりのため）。使いにくければ、計画者に相談する。
- リセットで実行中に作ったインスタンスが消えることは、構想にはないが、今の `resetPart()` の動き（配置の Entity をすべて消して作り直す）のとおり。足すのは `spawnedFrom` の片付けだけ。
- 入れ子のインスタンスは `Prefab.destroy` で消せない（方針 8）。使いにくければ、計画者に相談する。
- P0 で決めた数：一つの呼び出しで足せる Entity は 256 個、配置ごとに実行中に作れる Entity は 1000 個（ADR 0082）。
- P0 で分かった型の書き方：パラメータのないプレハブの `P` は `{ [name: string]: never }` にする（`{}` は、どんなオブジェクトも受けてしまう）。
- P2a で、方針 1 から変えた作り方（どれも、利用者から見える動きは方針のとおり。ADR 0082）：
  - 合わせるのは、Entity の値を読み書きする Host API（`world.get`・`world.set` など）の直前だけ。時刻・音・バッグなどは Entity の値を見ないので、合わせない。
  - 送る範囲は、`e.get()` で触れたものではなく、回した順番で決める（前に合わせてから回した Entity と、いまの Entity）。`e.get()` のたびに覚える手間をなくし、Host API を呼ばない System を重くしないため。変わったかどうかは、QuickJS の中で文字にして比べる。
  - ホストから返すのは、Host API が書いたフィールドだけ。
  - Host API の引数と戻り値の読み書きも軽くした。
- P2a の重さ（Entity 1000 個。前 → あと）：Host API を呼ばない System は 15.8 → 16 ms 前後（変わらない）。書いてから `world.get` で読む System は 50.9 → 70 ms 前後（約 1.4 倍）。Entity ごとに自分へ `world.set` で書く System は 48.0 → 94 ms 前後（約 1.9 倍）で、目安の 1.5 倍を超える。計画者には PR で数字を伝え、「自己レビューで問題がなければマージしてよい」と任されたので、設計者の判断でマージした：自分へ `world.set` で書く形は `@deprecated` にする古い書き方で、`e.get()` に書けば重くならない。もっと軽くする必要があれば、計画者の判断で見直す。
- P2b：合わなくなった Entity を飛ばす口は作ったが、今は、呼び出しの途中で KokoState を付け外しする Host API がないので、飛ばすのは消えた Entity（子も含む）だけ。リスト（ロードマップの「プレハブのリストから子を組み立てる」）で切り替えるときに、同じ口（`RunChanges.gone`）を使う。消えた Entity の値を読み書きしたことは、System の注意（`entity-gone`）として出す。
- P1：`@deprecated` を付けたのは 11 個（`world.get`・`world.set`・`world.getState`・`world.setState`・`world.getField`・`world.setField`・`world.emit`・`world.find`・`world.spawn`・`world.destroy`・`audio.play`）。`world.raycast` は、結果が Entity の参照を持つが、引数に ID を取らず、代わりの形も決まっていないので、付けていない。付けるかは、計画者に聞く。「KokoState を名前の文字で指す書き方」は、名前を受け取る `world.get`・`world.set`・`world.spawn` に付けたことで出る。
