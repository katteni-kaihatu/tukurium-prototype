## 作り方の方針

### 今の仕組み（調べた結果）

- **実行中に作る**（ADR 0082 の 7）：`Simulation.spawnPrefab()`（`packages/runtime/src/simulation.ts`）が、プレハブごとのひな形（`SpawnTemplate`。仮のアウトプットにインスタンスを一つ置いて展開した Entity の並び）を、制作データ（配置の版）ごとに取っておく。作るときは、ID を `rt:N`（いちばん上）と `rt:N/中の ID` に付け替えて、`addEntities()` で World に入れ、パラメータを重ねる。作ったいちばん上の Entity とプレハブの対応は `spawnedFrom` に持つ。入れ子のインスタンスがどのプレハブのものかは、ひな形の `instances` から引く（`spawnedPrefabOf()`）。
- **プレハブの System**：依存でたどれるプレハブ（`reachablePrefabsOf()`）の System を、配置のときに先に読み込み、`spawnedFrom` から求めた「残っているインスタンスのプレハブ」（`alivePrefabsOf()`）にある間だけ動かす（`awake()`）。
- **書き込みと、渡す Entity の確かめ**（ADR 0082 の 1・2）：スクリプトが `e.get()` で書いた値は、Entity の値を読み書きする Host API（`SYNC_HOST_API`）の直前と、呼び出しの終わりに World へ書く。Host API が World にしたこと（書いた値・消した Entity・作った Entity）は `RunTrack` に集め、QuickJS の側へ返す。**Query に合わなくなった Entity を飛ばす所は、KokoState を付け外しする Host API がまだないので、作っていない。**
- **引き継ぎ・巻き戻し**：`spawnedFrom` は、再生のフレーム（`PlayFrame.spawned`）・セッションのフレーム（`SessionFrame.spawned`）・デバッグ実行の巻き戻しの点（`DebugCheckpoint.spawned`）に入る（`packages/shared/src/protocol.ts`）。
- **適用・リセット**：`applyPart()` は、配置の Entity をすべて消し（`clearEntities()`）、新しい制作データで作り直してから、「維持」の印の付いたフィールドの値を戻す。実行中に作ったインスタンスは消える。
- **フィールドの型**（ADR 0065・0082）：`packages/typecheck/src/fieldSchema.ts` が、型の文を `ValueSchema`（`packages/eks/src/schema.ts`）にする。プレハブ型・インスタンス型は、印（`__prefab`・`__instance`）で見分けて `ref` にする。Host の宣言にある interface（`KokoStateRef`・`FieldRef`）は、名前で見分ける。
- **World**（`packages/eks/src/world.ts`）：親と子の索引を持つが、親を付け替える口はない。兄弟の並びは、作った順（子の `Set` の順）しかない。
- **再生中の画面**：Play mode では、Hierarchy は `world.entityIds()` の順に出し、Inspector は見るだけ（`InspectorPanel.tsx`）。デバッグ実行の一時停止中だけ、値を直せる（`debugEdit`）。
- **エージェント**：再生中の World を見る道具はない。スクリプトと KokoState の型を書く道具（`update_system`・`update_kokostate`）で、人と同じものを作れる。
- **バリアント**：ロードマップの「プレハブの一部を上書きしてバリアントを作る」は、実装計画は完了していて、作るのはこれから（V1〜V5 は未着手）。バリアントの展開では、元のプレハブから来た Entity が、元のプレハブの中と同じ「ルートからの ID」で並ぶ（その実装計画の方針 2）。この項目の切り替えは、この決まりの上に作る。

### 方針

1. **書き方：Host が用意する型「プレハブ同期マネージャー」（`PrefabSyncManager<T>`）を、KokoState のフィールドの型にそのまま書く。子を組み立てるには、同期マネージャーの `sync()` にリストを渡す。**

   ```ts
   // Board の KokoState のフィールドの型。「import するプレハブ」に「駒」を Koma、「ガイド」を Guide の名前で足してある
   pieces: PrefabSyncManager<Koma>; // 盤の上の駒
   guides: PrefabSyncManager<Guide>; // 合法手のガイド
   ```

   KokoState のフィールドの型では、プレハブは「import するプレハブ」で付けた名前で指し、その名前がそのままプレハブ型になる（ADR 0082 の 5。`InstanceOf<Koma> | undefined` と同じ書き方）。System では、`import Koma from "./駒.prefab"` の `typeof Koma` が同じ型になる。

   ```ts
   // System
   const board = e.get(Board);
   board.pieces.sync(
     game.pieces.map((p) => ({
       key: p.id, // 駒ごとに変わらない文字
       prefab: p.promoted ? Queen : Pawn, // 替えると切り替わる
       params: { Color: p.color, Position: squareToPos(p.square) },
     })),
   );
   board.pieces = …; // 型エラー（直接は書けない）
   ```

   宣言（`hostApiSpec.ts` の型の宣言に足す）：

   ```ts
   /** プレハブ同期マネージャーに渡すリストの一つ。key で子を見分け、prefab で中身を決める */
   type PrefabSlot<T> = {
     /** 子を見分ける文字。リストの中で重ならない。同じキーの子は、プレハブを替えても同じ Entity のまま */
     readonly key: string;
     /** 使うプレハブ（T か、T に当てはまるバリアント） */
     readonly prefab: T;
   } & ({} extends PrefabParamsOf<T>
     ? { readonly params?: PrefabParamsOf<T> }
     : { readonly params: PrefabParamsOf<T> });
   /**
    * プレハブ同期マネージャー：このフィールドを持つ Entity の子を、渡したリストに合わせて組み立てる。
    * 子を足す・切り替える・消す・並べ直すのは、ここに渡すことでだけ行う
    */
   interface PrefabSyncManager<T> {
     /** リストに合わせて子を組み立てる。キーで今ある子と比べ、作る・切り替える・消す・並べ直す */
     sync(list: readonly PrefabSlot<T>[]): void;
   }
   ```

   **(1) 形の決まり**

   - **リストそのものではなく、同期マネージャーにする**（計画者に確認した）。フィールドの型は「プレハブから子を組み立てるもの」で、渡すのはいつもリスト。あとで、リストの一つずつに `children`（同じ形のリスト）を足せば、子の下にも組み立てるツリーになる（構想の「やらないこと」の仮想ツリー）。そのときも、初めに渡すのはリストのまま（計画者に確認した）。今は `children` を作らない。
   - **メソッドは `sync()` だけ**（計画者に確認した）。一つずつ足す・消す・並べ替えるメソッドも、今のリストや子を読むメソッドも持たない。いつも、そのときのリストをまるごと渡す。今ある子と比べるのは実行環境の仕事（方針 3）。読みたいリストは、`sync()` を呼ぶ System が自分の状態から作るもの。
   - **リストは並び（配列）にし、キーは一つずつに持つ**。マップ（`Record<string, …>`）にすると、`"1"`・`"2"` のような数のキーが先に並び替わってしまい、子の並びをリストで決められないため。キーが重なったときは、先のものを使い、あとのものは注意（`prefab-sync-duplicate-key`）として出して作らない。
   - **場所・向き・大きさは、リストに持たない**（計画者に確認した）。Transform は、ほかの KokoState と同じに扱う。リストから場所を決めたいときは、プレハブのパラメータに、いちばん上の Entity の Transform のフィールド（`position` など）を指定する。
   - **パラメータの型**は、フィールドの型のプレハブ（`T`）のもの。必須のパラメータがあれば `params` は必須になる（`Prefab.spawn` と同じ決まり）。バリアントで足した省略できるパラメータは、この型では渡せない。渡したくなったら、計画者に相談する。
   - **書ける所は、KokoState のフィールドの型のいちばん外だけ**。レコード・リスト・ユニオンの中に書いたら問題（`prefab-sync-nested`）にする。子は、そのフィールドを持つ Entity の下に作るので、一つのフィールドに一つの子の並びが決まる形にしておく。
   - **依存でたどれるプレハブ**：フィールドの型の `T` は、今のプレハブ型のフィールドと同じく、KokoState の「import するプレハブ」（`prefabImports`）からたどれる。バリアント（ポーン・クイーン）は、`sync()` を呼ぶ System が import するのでたどれる。たどれないプレハブを渡したら、注意（`prefab-not-reachable`）を出して、その一つは作らない・切り替えない。

   **(2) 値の持ち方**

   - **World の中の値は、最後に渡したリスト**（`{ key, prefab, params }[]`）。包まずに、ただのデータのまま持つ。フレーム・引き継ぎ・巻き戻し・「維持」での受け渡しは、この値で行う。`children` を足すときも、一つずつにキーが増えるだけで、値の形は変わらない。
   - `fieldSchema.ts` で、`PrefabSyncManager` を名前で見分け、`ValueSchema` に一つ種類を足す：`{ kind: "prefabSync"; prefab: string }`（`prefab` は `T` のプレハブの ID）。値の確かめ・型に合わせる・参照をたどる・付け替えるは、値を `{ key: string; prefab: プレハブ型; params?: … }` のリストとして扱う関数を一つ置き、それに任せる（`eks/src/schema.ts` の値の種類ごとの関数すべてに足す。P4b と同じ）。パラメータの値の中の参照は、パラメータが指すフィールドの型でたどる。
   - **制作データでは、いつも空**。構想の「やらないこと」（制作データに固定のリストを書いて、再生の初めに作る）のとおり。初めの値は `[]`。空でない値は問題（`prefab-sync-in-data`）にする。アウトプットの Entity だけでなく、プレハブの中の Entity（インスタンスの上書きも）にも出す。子はプレハブのひな形から作るので、プレハブの中で空でない値を持つと、作った子の値と子がずれるため。Inspector では、インスタンス型のフィールドと同じく「実行中に組み立てます」と出して、値を入れられないようにする。**「維持」の印は付けられる**（方針 5 の「適用」で、最後に渡したリストを残すため）。
   - **QuickJS の中では、包みにする**：このフィールドの値（リスト）を、QuickJS の中では、`sync()` だけを持つ、書き換えられないオブジェクト（`Object.freeze`。以下「包み」）にする。QuickJS の側で Entity の値を受け取る所を一つにまとめ、そこで包みにする。受け取る時は、呼び出しの初めに渡す Entity、呼び出しの途中で並びの後ろに足した Entity（作った子も）、切り替えで値をまるごと差し替えた Entity（方針 4）、デバッグ実行の一時停止から続けるときに返す値。どこかで包みにし忘れると、書き戻しで「包みそのものではない」と見なされ、何もしていないのに注意が出て、包みに戻すことを繰り返すため。Entity の値は JSON にして受け渡す（`packages/script/src/sandbox.ts`）ので、包みが壊れないようにする：
     - 包みは、JSON にすると、持っているリストになる（`toJSON`。Entity の参照の包みと同じ形）。
     - ホストが書いた値を返すとき（`sync()` のあと）は、フィールドの値を置き換えず、包みの中身だけを入れ替える。
     - 書き戻しで値を比べる所では、このフィールドは、値ではなく「渡した包みそのものか」で見る（方針 1 の (3)）。

   **(3) 直接書き換えさせない**（計画者に確認した）

   - **型**：宣言ファイルで `PrefabSyncManager` のフィールドを `readonly` にする（`board.pieces = …` が型エラー）。リストや配列を渡そうとしても、`sync()` を持たないので、`PrefabSyncManager` に当てはまらず型エラーになる（`world.setState(ref, { pieces: [] })` も型エラー）。型の上で抜けるのは、別の包み（ほかの盤の `pieces` など）を `world.setState` などに渡したときだけ。
   - **実行**：ホストは、`prefabSync` のフィールドへの書き込みを、`sync()` のほかのどの口からも受け付けず、注意（`prefab-sync-write`）を出す。
     - `e.get()` の書き出し：書き戻すときに、このフィールドの値が、渡した包みそのものでなければ（代入で置き換えた）、書き込みを断り、注意を出し、QuickJS の側に包みを戻す。包みそのものなら、書き換えはない（包みは書き換えられないため）ので、比べずに飛ばす。
     - `world.set`・`world.setField`・`world.setState`：このフィールドの分を書かずに、注意を出す（ほかのフィールドは書く）。
   - **プレハブのパラメータ**は、このフィールドを指せない。指すと、`Prefab.spawn` や `sync()` の `params` から値を書けてしまうため。「プレハブの設定」で選べないようにし、指していたら問題（`prefab-param-sync-target`）にする。
   - **デバッグ実行の一時停止中**の Inspector でも、このフィールドは直せない（見るだけ）。
   - **`world.getState` などで読んだ値**は、ただのリスト（包みではない）。型の上では `PrefabSyncManager` なので、`sync()` を呼ぶと実行中に例外になる。`world.getState` は `@deprecated` なので、型は直さない。

2. **子の持ち方：子（以下「同期で作った子」）は、実行中に作ったインスタンスとして作り、キーとの対応を `syncChildren` に持つ。**
   - 子のいちばん上の Entity は、`Prefab.spawn` と同じく `rt:N`（中は `rt:N/ルートからの ID`）。フィールドを持つ Entity の下に作る。`spawnedFrom` にも入れるので、プレハブの System が動き、インスタンス型のフィールドに入れられる。
   - 対応は、`(フィールドを持つ Entity, KokoState, フィールド, キー) → 子のいちばん上の Entity` として、`Simulation` に持つ（`syncChildren`）。どのプレハブかは `spawnedFrom` にある。
   - **World の中では、兄弟の並びを持たない**。実行中の World で、兄弟の並びを見るものはない（子の並びを読む Host API はなく、描画・物理・Query も並びに関わらない）。並びが見えるのは Play mode の Hierarchy だけなので、Hierarchy で、同期で作った子を、リストの順（`syncChildren` の順）に出す（方針 6）。一つの Entity に、同期マネージャーのフィールドがいくつかあれば、KokoState とフィールドの並び順、その中はリストの順。同期で作っていない子（制作データの子など）は、その前に出す。
   - **同期で作った子と、その中の Entity は、スクリプトから消せない**。`Prefab.destroy`・`world.destroy` は `false` を返し、注意（`prefab-sync-child`）を出す。消せると、渡したリストと子がずれ、切り替えの前提（元のプレハブにある Entity は、いつもある）が崩れるため。消したいときは、そのキーを外したリストを `sync()` に渡す。フィールドを持つ Entity ごと消すのは、今のまま（子も消え、対応からも外す）。
   - 上限は、今の「配置ごとに、実行中に作れる Entity は 1000 個まで」をそのまま使う。超える分は作らずに注意（`spawn-limit`）を出し、そのキーの子は作らない（World の値には、渡したリストをそのまま持つ。次に `sync()` を呼んだときに、もう一度作ろうとする。方針 3 のとおり、実際にある子と比べるため）。一つの呼び出しで並びに足せる 256 個の上限（ADR 0082 の 2）も、そのまま。

3. **組み立てる時：`sync()` を呼んだ、その瞬間に組み立てる。**
   - `sync()` は、Host API（`PrefabSyncManager.sync`）を呼ぶ。引数は、フィールドを持つ Entity・KokoState・フィールドと、渡したリスト。`HOST_API_SPEC` と `HOST_CAPABILITIES` に足す。
     - **Capability は `entity.spawn` と `entity.destroy` の両方を要る**（作ることも消すこともするため）。`HOST_API_SPEC` の一件が Capability を二つ持てるかを L2 で確かめ、持てなければ持てるようにする（`hostApiSpec.test.ts` の一致の検査も合わせる）。
     - **呼べるのは、呼んだ System の配置の Entity だけ**。包みを変数に取っておいて、あとで呼んでも、ホストが Entity の配置を確かめ、違えば何もせずに注意を出す（今の Host API と同じ決まり。ADR 0012）。
   - `SYNC_HOST_API` に入れる。呼ぶ直前にスクリプトの書いた値を World へ書き、ホストが子を組み立てる。返ったときには、もう子がある。構想の「リストが変わったその場ですぐ行う」を、この形で満たす。
   - 渡したリストは、ホストが World の値に書き、包みの中身も入れ替える（方針 1 の (2)）。
   - 組み立ては、**今ある子**（`syncChildren` と `spawnedFrom`）と、キーごとに比べて行う。前に渡したリスト（World の値）とは比べない。上限で作れなかった子・切り替えられなかった子があると、前に渡したリストと子がずれ、同じリストを渡しても直らなくなるため：
     - 新しいキー → 作る（`spawnPrefab()` の中身を、親を受け取れる形に分けて使う）。パラメータを重ねる。
     - なくなったキー → 子を消す。
     - 同じキーでプレハブが同じ → 何もしない。パラメータの値が変わっても、子には届けない（構想の「パラメータの値は、作るときと切り替えるときの初めの値」）。World の値は、新しいパラメータになる。そのため、あとで切り替えるときや、「適用」で作り直すときは、最後に渡したパラメータを使う。いま見えている子と、作り直した子の値が違うことがある。
     - 同じキーでプレハブが替わった → 切り替える（方針 4）。
     - 並びが変わった → `syncChildren` の順を直す（World には何もしない。Hierarchy がこの順で出す）。
   - 作った・消した・切り替えた Entity は `RunTrack` に入れ、今の仕組みで QuickJS へ返す（消えたものは飛ばし、作ったもので Query に合うものは `onUpdate` の並びの後ろに足す）。
   - 渡したプレハブが `T` に当てはまらない（`prefabFitsType()`）・たどれないときは、その一つを作らず・切り替えず、注意を出す。ほかの一つずつは組み立てる。

4. **切り替え：フィールドの型のプレハブ（`T`）との差分を入れ替える。**
   - **差分を求める関数を repo-model に置く**（`variantDelta(snapshot, kokostates, base, variant)`）。バリアントから `T` まで、いちばん上の `instanceOf` をたどり、段ごとに集めて一つにまとめる（`T` 自身なら空）：
     - 上書きしたフィールド：いちばん上の Entity `R` の `prefabOverrides` の `states`（キーはルートからの ID）と、`R.states` のうち `T` のいちばん上にもある KokoState のフィールド（Transform など）。
     - 足した KokoState：`prefabOverrides` の `addedStates` と、`R.states` のうち `T` のいちばん上にない KokoState。
     - 足した子の Entity：その段のプレハブの中の Entity（`R` を除く）と、その下に展開されるものすべて。
     - 名前・親の上書き：`prefabOverrides` の `name`・`parent`。並び順の上書き（`order`）は集めない（World が兄弟の並びを持たないため。方針 2）。
     - System は、ここでは集めない（方針 4 の終わり）。
     - 値は持たない。値は、ひな形（`T` のものと、切り替え先のもの）から取る。上書きのキーと、ひな形の中の ID は、バリアントの展開の決まりで同じになるので、そのまま引ける。
   - フィールドごとに、次の順で値を決める（構想のとおり。上ほど強い）：
     1. **パラメータ**：リストの `params` で渡しているフィールドは、リストの値。
     2. **「維持」**：`T` を展開したときの「維持」の印（`T` 自身の印と、`T` の元や入れ子から受け継いだ印）が付いたフィールドは、実行中の値。**切り替え先のバリアントで足した印は見ない**（構想の「元のプレハブで決まり、バリアントでは変えられない」。バリアントの実装計画の「分かったこと」で、この項目で確かめるとしたもの）。
     3. **切り替え先の差分にあるフィールド**：切り替え先のひな形の値。
     4. **前の差分にだけあるフィールド**：`T` のひな形の値。
     5. **どちらにもないフィールド**：実行中の値。Transform も同じ（計画者に確認した）。
   - **同期マネージャーのフィールドは、この決め方から外す**。「駒」自身が同期マネージャーのフィールド（駒ごとのガイドなど）を持つとき、差分にあってもひな形の値（いつも `[]`）にせず、実行中の値と、それで作った子を、いつもそのまま残す。値の決め方にかけると、World の値が空になり、子とずれるため。
     - 前の差分で足した KokoState を外すとき、その中の同期マネージャーで作った子も消す（`syncChildren` からも外す）。
     - 切り替え先の差分で足した KokoState の同期マネージャーは、空（`[]`）から始める。
   - 前の差分で足した KokoState は外し、切り替え先の差分で足した KokoState は、切り替え先のひな形の値で付ける。名前は、前の差分のものを `T` のものに戻してから、切り替え先のものにする。
   - **子と親は、次の順で入れ替える**。バリアントは、元のプレハブにある Entity を、自分で足した子の下へ動かせる（ポーンが、元からある「台座」を、ポーンで足した「飾り」の下へ動かすなど）。先に「飾り」を消すと、World は子ごと消すので、「台座」まで消え、「元のプレハブにある Entity は、いつもある」という前提が崩れる。逆向きも同じで、足した子の下へ動かすには、その子が先にないといけない。
     1. 前の差分で親を上書きした Entity を、`T` の親に戻す。
     2. 前の差分で足した子を消す。
     3. 切り替え先の差分で足した子を、ひな形から作る。
     4. 切り替え先の差分で親を上書きした Entity を、その親にする。親を付け替えるのは、World に足す内部の口 `setParent(id, parent)`（親を書き換え、子の索引を移す。Host API には出さず、スクリプトからは呼べない）で行う。消して作り直すと、その下の Entity まで消え、指していた参照も切れるため。親は親から見た Transform を持つので、付け替えると世界の中での位置が変わる（プレハブを展開したときと同じ見え方）。物理の当たり判定がついてくるかを確かめる。
   - ひな形から写す値の中の Entity の参照は、作るときと同じく、この子の ID に付け替える（`addEntities()` の付け替えを、フィールド一つでも使えるように分ける）。
   - **System**：`spawnedFrom` の子のいちばん上を、切り替え先のプレハブにし、`alivePrefabs` を捨てる。これで、切り替え先にしかない System が動き始め、前のプレハブのインスタンスがほかに残っていなければ、前のプレハブにしかなかった System は止まる（今の `awake()` のまま）。バリアントのインスタンスで、元のプレハブの System が動くこと（`alivePrefabsOf()` が元をたどること）は、バリアントの項目で作る。足りなければ、ここで直す。
   - **呼び出しの途中で切り替えたとき**：KokoState を外したことで、いま動いている System の Query に合わなくなった Entity を飛ばし、合うようになった Entity を並びの後ろに足す（ADR 0082 の 2 で作っていなかった「合わなくなった Entity」を、ここで作る）。値を書き換えた Entity は、QuickJS が持っている値をまるごと差し替える（`RunTrack` に「差し替えた Entity」を足す）。外した KokoState を `e.get()` で持っていたら、消えた Entity と同じく「読むと `undefined`・書いた値は捨てる」形にする。
   - 切り替え先のプレハブが、たどれない・`T` に当てはまらないときは、切り替えずに前のまま残し、注意を出す。
   - 切り替えで消えた子を指す参照は、壊れることがある。型で守るのは、ロードマップの「実行中に現れるものをプレハブで決めて静的に安全にする」で行う（構想のとおり）。インスタンス型のフィールドが、切り替えで型に当てはまらなくなった子を指すこと（KokoState のフィールドの型 `InstanceOf<Pawn> | undefined` が、クイーンになった子を指す）も、同じくそちらで扱う。

5. **引き継ぎ・巻き戻し・適用**
   - `syncChildren` を、再生のフレーム（`PlayFrame`）・セッションのフレーム（`SessionFrame`）・デバッグ実行の巻き戻しの点（`DebugCheckpoint` と、再生のフレームの `debugStart`）に入れる（`synced`。今の `spawned` が入っている所すべて）。組み立ては実際にある子と比べるので（方針 3）、前に渡したリストを別に持つ必要はない。
   - 引き継ぎの形が変わるので、`PROTOCOL_VERSION` を上げる。
   - **適用**：今の `applyPart()` が子を消す（構想のとおり）。「維持」の印で同期マネージャーのフィールドの値（最後に渡したリスト）を戻したあと、新しい制作データのひな形で、空から組み立てる。今の `applyPart()` は、戻す値を `accepts()` で確かめ、合わなければフィールドごと捨てるが、同期マネージャーのフィールドは `sync()` と同じく一つずつ確かめ、新しい制作データでたどれない・当てはまらないプレハブの一つだけを飛ばして注意を出す（一つのために、子が一つも戻らなくならないように）。World の値には、戻したリストをそのまま持つ（飛ばした一つも外さない。方針 2 の上限のときと同じ）。次に `sync()` を呼んだとき、今ある子と比べて、作れるようになっていれば作る。子のフィールドに付けた「維持」は効かない（構想のとおり。子は作り直すため）。
   - **リセット**：制作データの値は空なので、子はできない。今のままでよい。

6. **画面**
   - Hierarchy（Play mode）：同期で作った子の行に、印を付け、ホバーで「Board.pieces のキー e2 から作りました」と出す。同期で作った子は、リストの順（`syncChildren` の順）に並べて出す（方針 2）。ほかの Entity は、今のまま。
   - Inspector（Play mode）：同期で作った子とその中の Entity に「Board.pieces で作ったので、直せません」と出す。デバッグ実行の一時停止中でも、値を直せないようにする（今は、一時停止中なら直せる）。同期マネージャーのフィールドも、見るだけ（方針 1）。
   - `RuntimeView` に、Entity が同期で作った子か（とフィールドとキー）を引く口を足す。

7. **AI エージェント**
   - 新しい道具は足さない。KokoState の「import するプレハブ」に駒を足し（P6 の道具）、フィールドの型に `PrefabSyncManager<Koma>` を書き（`update_kokostate`）、System で `sync()` にリストを渡す（`update_system`）。人と同じ道具で作れる。
   - エージェントの使い方（`docs/AGENT_MCP.md` と、`mcp.ts` の道具の説明）に、プレハブ同期マネージャーの書き方と、渡すリストのキーの決まりを足す。

8. **チェスで確かめる作品**（計画者に確認した）：同梱サンプルには足さない。単体テストの中に、小さなチェス（盤、「駒」とバリアントの「ポーン」「クイーン」、合法手のガイド、成る System）を作り、画面の確認にも使う。

大きな判断（プレハブ同期マネージャーの形と、リストを渡すことでだけ変えられること、場所をリストに持たないこと、制作データでは空、組み立てる時、子を消せないこと、World は兄弟の並びを持たず Hierarchy でリストの順に出すこと、実際にある子と比べること、包みと値の受け渡し、差分の求め方と値の決め方、同期マネージャーのフィールドは切り替えの値の決め方から外すこと、「維持」は `T` のものだけ、引き継ぎ、「適用」では一つずつ確かめて使えないものだけを飛ばすこと）は、L0 で ADR に残す。番号は、書くときの次の番号（2026-11-19 の時点で 0084）。ほかの PR とぶつかったら、マージするときに付け直す。

## 確かめ方

- 単体テスト
  - 型（typecheck）：L0 の宣言の決まり。`fieldSchema.ts` が、KokoState のフィールドの型 `PrefabSyncManager<Koma>`（「import するプレハブ」の名前）を `prefabSync` にすること。ふつうのリスト・プレハブ型と取り違えないこと
  - 問題（repo-model）：入れ子に書いた・制作データで空でない（アウトプットの Entity・プレハブの中の Entity・インスタンスの上書き）・パラメータがこのフィールドを指す、の問題。このフィールドに「維持」の印を付けられること。依存グラフで `T` がたどれること。抽出・ライブラリで ID が付け替わること
  - 組み立て（runtime）：`sync()` で、キーの数だけ子ができ、フィールドを持つ Entity の下に、リストの順で並ぶこと。パラメータ（駒の色・Transform を指すもの）が渡ること。次の `sync()` で、キーを外すと消え、足すと増え、並べ替えると、Hierarchy に出す順（`RuntimeView` で引く順）が変わり、これらが一度にできること。同じキー・同じプレハブのまま、パラメータだけを変えて渡しても、子が変わらないこと。代入（型エラーを無視したもの）・`world.setField` などでこのフィールドに書くと、断って注意が出ること。`Prefab.destroy`・`world.destroy` で子を消せないこと。重なったキー・たどれないプレハブ・上限。`sync()` から返ったときに、もう子があり、World の値と QuickJS が持っている値が合い、`board.pieces.sync` がまだ呼べること。何もしない System の書き戻しで、`prefab-sync-write` の注意が出ないこと。型エラーを無視して代入すると、断って注意が出て、次の `sync()` が呼べること。別の配置の Entity の包みで `sync()` を呼ぶと、何もしないこと。呼び出しの途中で並びに足した子・切り替えで値を差し替えた Entity・一時停止から続けたあとでも、このフィールドが包みのままで、書き戻しで注意が出ないこと。上限で作れなかったキーが、同じリストを次に渡したときに作られること。切り替えられなかったキーが、次に渡したときに切り替わること。同じ呼び出しの並びの後ろと、あとの System に、作った子が渡ること。フィールドを持つ Entity を消すと、子も対応も消えること
  - 切り替え（runtime・repo-model）：`variantDelta()` が、2 段・3 段のバリアントで、上書き・足した KokoState・足した子・名前・親を集め（並び順は集めない）、`T` 自身なら空なこと。ポーンからクイーンに替えると、ID とキーが残り、「駒」のままのフィールド（Transform・「動いた回数」）は実行中の値、ポーンが上書きした見た目は「駒」の値を経てクイーンの値、クイーンで足した KokoState と子は初めの値で足され、ポーンで足したものは消えること。「駒」で「維持」を付けたフィールドは実行中の値で、クイーンで足した「維持」の印は効かないこと。パラメータがいちばん強いこと。親が入れ替わり、Entity の ID が変わらないこと。前のバリアントで足した子の下へ動かしていた元の Entity が、切り替えで消えずに `T` の親へ戻ること。切り替え先のバリアントで足した子の下へ、元の Entity が動くこと。クイーンにしかない System が動き始め、ポーンが残っていなければポーンにしかない System が止まること。呼び出しの途中で切り替えたとき、合わなくなった Entity を飛ばし、値が差し替わること。残った参照が、元のプレハブにある Entity を指したままのこと。「駒」の同期マネージャーのフィールドと、それで作った子が、切り替えても残ること。前のバリアントで足した KokoState の同期マネージャーで作った子が、切り替えで消えること。ホストが引き継いだあとも、切り替えられること
  - 引き継ぎ・巻き戻し・適用（L2）：別のホストが引き継いでも、キーと子の対応が残り、同じリストを渡しても子が二重にならないこと。巻き戻すと対応も戻ること。適用で子がすべて作り直され、「維持」を付けたフィールドからは同じ子ができ、付けていなければ子がなくなること。新しい制作データで使えなくなったプレハブの一つだけが飛ばされ、ほかの子はできること

## 構想から変えたこと

- リストの一つずつに、置く場所・向き・大きさを持たせない（計画者に確認した）。構想では、一つずつが「置く場所・向き・大きさ」を持ち、作るときと切り替えるときの初めの値にするとしていた。Transform は、ほかの KokoState と同じに扱い、切り替えでも、差分になければ実行中の値を残す。リストから場所を決めたいときは、パラメータにする。
- フィールドの型をリストではなく、プレハブ同期マネージャー（`PrefabSyncManager<T>`）にし、リストはそれに `sync()` で渡す（計画者に確認した）。あとで、リストの一つずつに `children` を足してツリーにできるようにするため（渡すのは、そのときもリスト）。一つずつ足す・消す・並べ替えるメソッドは持たない。フィールドは直接書き換えられず、`sync()` を呼んだ瞬間に子を組み立てる。構想では「KokoState のフィールドの値（リスト）から子を足す・直す・消す」としていて、書き方は設計者に任されていた。
- 実行中の並び順を、完了の条件から外す（計画者に任された）。構想の完了の条件は「バリアントで変えた並び順と親も入れ替わる」としていたが、実行中の World で兄弟の並びを見るものはない。同期で作った子は、Hierarchy でリストの順に出す。バリアントの並び順の上書きは、切り替えで入れ替えない。親は入れ替える。
- 同梱サンプルにチェスは足さず、テスト用の作品だけで完了の条件を確かめる（計画者に確認した。構想には書いていない）。

## 分かったこと・残り

- バリアントの実装計画は、ADR を 0083 として書いているが、0083 は「ワークスペースの開き方」に使われた。バリアントの V1 で ADR を書くときに、次の番号にする。この項目の ADR と番号がぶつかったら、マージするときに付け直す（計画者に確認した）。

- 同期マネージャーから、キーで子を引く口（`get(key)` など）は持たない（計画者の「細かい操作は要らない」に合わせた）。子を読みたい場面が出たら、足すかを計画者に相談する。
