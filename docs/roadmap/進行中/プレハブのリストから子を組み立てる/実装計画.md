## 作り方の方針

### 今の仕組み（調べた結果）

- **実行中に作る**（ADR 0082 の 7）：`Simulation.spawnPrefab()`（`packages/runtime/src/simulation.ts`）が、プレハブごとのひな形（`SpawnTemplate`。仮のアウトプットにインスタンスを一つ置いて展開した Entity の並び）を、制作データ（配置の版）ごとに取っておく。作るときは、ID を `rt:N`（いちばん上）と `rt:N/中の ID` に付け替えて、`addEntities()` で World に入れ、パラメータを重ねる。作ったいちばん上の Entity とプレハブの対応は `spawnedFrom` に持つ。入れ子のインスタンスがどのプレハブのものかは、ひな形の `instances` から引く（`spawnedPrefabOf()`）。
- **プレハブの System**：依存でたどれるプレハブ（`reachablePrefabsOf()`）の System を、配置のときに先に読み込み、`spawnedFrom` から求めた「残っているインスタンスのプレハブ」（`alivePrefabsOf()`）にある間だけ動かす（`awake()`）。
- **書き込みと、渡す Entity の確かめ**（ADR 0082 の 1・2）：スクリプトが `e.get()` で書いた値は、Entity の値を読み書きする Host API（`SYNC_HOST_API`）の直前と、呼び出しの終わりに World へ書く。Host API が World にしたこと（書いた値・消した Entity・作った Entity）は `RunTrack` に集め、QuickJS の側へ返す。**Query に合わなくなった Entity を飛ばす所は、KokoState を付け外しする Host API がまだないので、作っていない。**
- **引き継ぎ・巻き戻し**：`spawnedFrom` は、再生のフレーム（`PlayFrame.spawned`）・セッションのフレーム（`SessionFrame.spawned`）・デバッグ実行の巻き戻しの点（`DebugCheckpoint.spawned`）に入る（`packages/shared/src/protocol.ts`）。
- **適用・リセット**：`applyPart()` は、配置の Entity をすべて消し（`clearEntities()`）、新しい制作データで作り直してから、「維持」の印の付いたフィールドの値を戻す。実行中に作ったインスタンスは消える。
- **フィールドの型**（ADR 0065・0082）：`packages/typecheck/src/fieldSchema.ts` が、型の文を `ValueSchema`（`packages/eks/src/schema.ts`）にする。プレハブ型・インスタンス型は、印（`__prefab`・`__instance`）で見分けて `ref` にする。Host の宣言にある interface（`KokoStateRef`・`FieldRef`）は、名前で見分ける。
- **World**（`packages/eks/src/world.ts`）：親と子の索引を持つが、親を付け替える口はない。兄弟の並びは、作った順（子の `Set` の順）しかない。
- **再生中の画面**：Play mode では、Hierarchy は `world.entityIds()` の順に出し、Inspector は見るだけ（`InspectorPanel.tsx`）。デバッグ実行の一時停止中だけ、値を直せる（`debugEdit`）。
- **エージェント**：再生中の World を見る道具はない。スクリプトと KokoState の型を書く道具（`update_system`・`update_kokostate`）で、人と同じものを作れる。
- **バリアント**：ロードマップの「プレハブの一部を上書きしてバリアントを作る」は、実装計画は完了していて、作るのはこれから（V1〜V5 は未着手）。バリアントの展開では、元のプレハブから来た Entity が、元のプレハブの中と同じ「ルートからの ID」で並ぶ（その実装計画の方針 2）。この項目の切り替えは、この決まりの上に作る。

### 方針

1. **リストの書き方：Host が用意する型 `PrefabList<T>` を、KokoState のフィールドの型にそのまま書く。中身は、リストのメソッドでだけ変えられる。**

   ```ts
   import Koma from "./駒.prefab";
   // Board の KokoState
   type Fields = {
     /** 盤の上の駒。キーはマスの名前など、駒ごとに変わらない文字 */
     pieces: PrefabList<typeof Koma>;
     guides: PrefabList<typeof Guide>;
   };
   ```

   ```ts
   // System
   const board = e.get(Board);
   const pawn = board.pieces.set("p1", Pawn, { Color: "white", Position: [0, 0, 1] }); // 作る
   board.pieces.set("p1", Queen, { Color: "white", Position: [0, 0, 7] }); // 同じキーで替える → 切り替え
   board.pieces.remove("p1"); // 消す
   board.pieces.replace(next); // 並びごと置き換える（キーで比べて、作る・切り替える・消す・並べ直す）
   board.pieces = [];          // 型エラー（直接は書けない）
   ```

   宣言（`hostApiSpec.ts` の型の宣言に足す）：

   ```ts
   /** プレハブのリストの一つ。key で子を見分け、prefab で中身を決める */
   type PrefabSlot<T> = {
     /** 子を見分ける文字。リストの中で重ならない。同じキーの子は、プレハブを替えても同じ Entity のまま */
     readonly key: string;
     /** 使うプレハブ（T か、T に当てはまるバリアント） */
     readonly prefab: T;
   } & PrefabSlotParams<T>;
   type PrefabSlotParams<T> = {} extends PrefabParamsOf<T>
     ? { readonly params?: PrefabParamsOf<T> }
     : { readonly params: PrefabParamsOf<T> };
   /** プレハブのリスト：このフィールドを持つ Entity の子を、リストから組み立てる。中身はメソッドでだけ変えられる */
   interface PrefabList<T> extends Iterable<PrefabSlot<T>> {
     readonly length: number;
     /** キーの一つ。なければ undefined */
     slot(key: string): PrefabSlot<T> | undefined;
     /** キーの子（作ったインスタンス）。まだ作っていなければ undefined */
     get(key: string): InstanceOf<T> | undefined;
     has(key: string): boolean;
     /** 足す（後ろに並ぶ）か、同じキーのプレハブを替える。作れなかったら undefined */
     set(key: string, prefab: T, ...params: ParamsArg<T>): InstanceOf<T> | undefined;
     /** キーの子を消す。なかったら false */
     remove(key: string): boolean;
     /** 並びごと置き換える */
     replace(slots: readonly PrefabSlot<T>[]): void;
     /** 並びの中の位置を変える */
     move(key: string, index: number): boolean;
   }
   ```

   （`ParamsArg<T>` は、`Prefab.spawn` の第二引数と同じ決まり：必須のパラメータがあれば要り、なければ省略できる。）

   - **直接書き換えさせない**（計画者に確認した）。
     - 型の上では、宣言ファイルで `PrefabList` のフィールドを `readonly` にする（`board.pieces = …` が型エラー）。`PrefabList` に、並びを書き換える口（添え字への代入・`push` など）はない。`slot()` で返す一つずつも `readonly`。
     - 実行の上でも、QuickJS の中の `board.pieces` は、メソッドを持つ読むだけのオブジェクトにする（`Object.freeze` した中身と、メソッド）。型エラーを無視して代入しても、ホストは `prefabList` のフィールドへの書き込みを、どの口（`e.get()` の書き出し・`world.set`・`world.setField`・`world.setState`）からも受け付けず、注意（`prefab-list-write`）を出す。`world.getState` などで読んだ値は、ただのデータ（`{ key, prefab, params }` の並び）。
     - デバッグ実行の一時停止中の Inspector でも、リストのフィールドは直せない（見るだけ）。
   - **World の中の値は、ただのデータ**（`{ key, prefab, params }` の並び）。フレーム・引き継ぎ・巻き戻し・「維持」での受け渡しは、この値で行う。QuickJS へ渡すときに、メソッドを持つオブジェクトに包む。
   - **並び（配列）にし、キーは一つずつに持つ**。マップ（`Record<string, …>`）にすると、`"1"`・`"2"` のような数のキーが先に並び替わってしまい、子の並びをリストで決められないため。`replace()` でキーが重なったときは、先のものを使い、あとのものは注意（`prefab-list-duplicate-key`）として出して作らない。
   - **場所・向き・大きさは、リストに持たない**（計画者に確認した）。Transform は、ほかの KokoState と同じに扱う。リストから場所を決めたいときは、プレハブのパラメータに、いちばん上の Entity の Transform のフィールド（`position` など）を指定する。
   - パラメータの型は、リストの型のプレハブ（`T`）のもの。必須のパラメータがあれば `params` は必須になる（`Prefab.spawn` と同じ決まり）。バリアントで足した省略できるパラメータは、この型では渡せない。渡したくなったら、計画者に相談する。
   - `fieldSchema.ts` で、`PrefabList` を名前で見分け、`ValueSchema` に一つ種類を足す：`{ kind: "prefabList"; prefab: string }`（`prefab` は `T` のプレハブの ID）。値の確かめ・型に合わせる・参照をたどる・付け替えるは、一つずつを `{ key: string; prefab: プレハブ型; params?: … }` のレコードとして扱う関数を一つ置き、それに任せる（`eks/src/schema.ts` の値の種類ごとの関数すべてに足す。P4b と同じ）。パラメータの値の中の参照は、パラメータが指すフィールドの型でたどる。
   - **書ける所は、KokoState のフィールドの型のいちばん外だけ**。レコード・リスト・ユニオンの中に書いたら問題（`prefab-list-nested`）にする。子は、そのフィールドを持つ Entity の下に作るので、一つのフィールドに一つの子の並びが決まる形にしておく。
   - **制作データでは、いつも空**。構想の「やらないこと」（制作データに固定のリストを書いて、再生の初めに作る）のとおり。空でない値は問題（`prefab-list-in-data`）にし、Inspector では、インスタンス型のフィールドと同じく「実行中に組み立てます」と出して、値を入れられないようにする。初めの値は `[]`。
   - 依存でたどれるプレハブ：リストの型の `T` は、今のプレハブ型のフィールドと同じく、型の印からたどれる（KokoState の `prefabImports`）。バリアント（ポーン・クイーン）は、リストを書く System が import するのでたどれる。たどれないプレハブを渡したら、注意（`prefab-not-reachable`）を出して、その一つは作らない・切り替えない。

2. **子の持ち方：子は、実行中に作ったインスタンスとして作り、キーとの対応を `listChildren` に持つ。**
   - 子のいちばん上の Entity は、`Prefab.spawn` と同じく `rt:N`（中は `rt:N/ルートからの ID`）。リストを持つ Entity の下に作る。`spawnedFrom` にも入れるので、プレハブの System が動き、インスタンス型のフィールドに入れられる。
   - 対応は、`(リストを持つ Entity, KokoState, フィールド, キー) → 子のいちばん上の Entity` として、`Simulation` に持つ（`listChildren`）。どのプレハブかは `spawnedFrom` にある。
   - 兄弟の並びは、リストの順にそろえる。一つの Entity に、リストのフィールドがいくつかあれば、KokoState とフィールドの並び順、その中はリストの順。リストで作っていない子（制作データの子など）は、その前に置く。World に、親を付け替える口と、兄弟の中の位置を決める口（`setParent(id, parent, index?)`）を足し、スナップショットと復元で兄弟の並びが保たれるかを確かめる（保たれなければ、スナップショットに並びを入れる）。
   - **リストから作った子と、その中の Entity は、スクリプトから消せない**。`Prefab.destroy`・`world.destroy` は `false` を返し、注意（`prefab-list-child`）を出す。消せると、リストと子がずれ、切り替えの前提（元のプレハブにある Entity は、いつもある）が崩れるため。消したいときは、リストからキーを外す。リストを持つ Entity ごと消すのは、今のまま（子も消え、対応からも外す）。
   - 上限は、今の「配置ごとに、実行中に作れる Entity は 1000 個まで」をそのまま使う。超える分は作らずに注意（`spawn-limit`）を出し、そのキーはリストに入れない（`set()` は `undefined` を返す。`replace()` では、作れた所までを入れる）。一つの呼び出しで並びに足せる 256 個の上限（ADR 0082 の 2）も、そのまま。

3. **組み立てる時：メソッドを呼んだ、その瞬間に組み立てる。**
   - リストのメソッド（`set`・`remove`・`replace`・`move`）は、Host API（`PrefabList.set` など。`HOST_API_SPEC` と `HOST_CAPABILITIES` に足す。Capability は `entity.spawn`・`entity.destroy`）を呼ぶ。引数は、リストを持つ Entity・KokoState・フィールドと、メソッドの引数。
   - これらは `SYNC_HOST_API` に入れる。呼ぶ直前にスクリプトの書いた値を World へ書き、ホストが子を作る・切り替える・消す・並べ直す。返るときには、もう子がある（`set()` の戻り値が、作った子そのもの）。構想の「リストが変わったその場ですぐ行う」を、この形で満たす。
   - 新しいリストの値（データ）は、ホストが World に書き、今の「ホストが書いた値を返す」仕組みで、QuickJS が持っている `board.pieces` の中身にも届ける。
   - 一つずつの動き：
     - `set()`：新しいキー → 作る（`spawnPrefab()` の中身を、親を受け取れる形に分けて使う）。パラメータを重ねる。同じキーでプレハブが同じ → 何もしない（パラメータの値が違っても、子には届けない。構想の「パラメータの値は、作るときと切り替えるときの初めの値」）。リストの値のパラメータは、渡したものに替わる。同じキーでプレハブが替わった → 切り替える（方針 4）。
     - `remove()`：子を消す。
     - `replace()`：前の並びとキーで比べ、上の `set()` と `remove()` を順に行い、並びを直す。
     - `move()`：兄弟の並びを直す。
   - 作った・消した・切り替えた Entity は `RunTrack` に入れ、今の仕組みで QuickJS へ返す（消えたものは飛ばし、作ったもので Query に合うものは `onUpdate` の並びの後ろに足す）。
   - 渡したプレハブが `T` に当てはまらない（`prefabFitsType()`）・たどれないときは、その一つを作らず・切り替えず、注意を出す（`set()` は `undefined` を返す）。

4. **切り替え：リストの型のプレハブ（`T`）との差分を入れ替える。**
   - **差分を求める関数を repo-model に置く**（`variantDelta(snapshot, kokostates, base, variant)`）。バリアントから `T` まで、いちばん上の `instanceOf` をたどり、段ごとに集めて一つにまとめる（`T` 自身なら空）：
     - 上書きしたフィールド：いちばん上の Entity `R` の `prefabOverrides` の `states`（キーはルートからの ID）と、`R.states` のうち `T` のいちばん上にもある KokoState のフィールド（Transform など）。
     - 足した KokoState：`prefabOverrides` の `addedStates` と、`R.states` のうち `T` のいちばん上にない KokoState。
     - 足した子の Entity：その段のプレハブの中の Entity（`R` を除く）と、その下に展開されるものすべて。
     - 名前・親・並び順の上書き：`prefabOverrides` の `name`・`parent`・`order`。
     - System は、ここでは集めない（方針 4 の終わり）。
     - 値は持たない。値は、ひな形（`T` のものと、切り替え先のもの）から取る。上書きのキーと、ひな形の中の ID は、バリアントの展開の決まりで同じになるので、そのまま引ける。
   - フィールドごとに、次の順で値を決める（構想のとおり。上ほど強い）：
     1. **パラメータ**：リストの `params` で渡しているフィールドは、リストの値。
     2. **「維持」**：`T` を展開したときの「維持」の印（`T` 自身の印と、`T` の元や入れ子から受け継いだ印）が付いたフィールドは、実行中の値。**切り替え先のバリアントで足した印は見ない**（構想の「元のプレハブで決まり、バリアントでは変えられない」。バリアントの実装計画の「分かったこと」で、この項目で確かめるとしたもの）。
     3. **切り替え先の差分にあるフィールド**：切り替え先のひな形の値。
     4. **前の差分にだけあるフィールド**：`T` のひな形の値。
     5. **どちらにもないフィールド**：実行中の値。Transform も同じ（計画者に確認した）。
   - 前の差分で足した KokoState は外し、切り替え先の差分で足した KokoState は、切り替え先のひな形の値で付ける。前の差分で足した子は消し、切り替え先の差分で足した子を、ひな形から作る。名前・親・並び順は、前の差分のものを `T` のものに戻してから、切り替え先のものにする。
   - ひな形から写す値の中の Entity の参照は、作るときと同じく、この子の ID に付け替える（`addEntities()` の付け替えを、フィールド一つでも使えるように分ける）。
   - **System**：`spawnedFrom` の子のいちばん上を、切り替え先のプレハブにし、`alivePrefabs` を捨てる。これで、切り替え先にしかない System が動き始め、前のプレハブのインスタンスがほかに残っていなければ、前のプレハブにしかなかった System は止まる（今の `awake()` のまま）。バリアントのインスタンスで、元のプレハブの System が動くこと（`alivePrefabsOf()` が元をたどること）は、バリアントの項目で作る。足りなければ、ここで直す。
   - **呼び出しの途中で切り替えたとき**：KokoState を外したことで、いま動いている System の Query に合わなくなった Entity を飛ばし、合うようになった Entity を並びの後ろに足す（ADR 0082 の 2 で作っていなかった「合わなくなった Entity」を、ここで作る）。値を書き換えた Entity は、QuickJS が持っている値をまるごと差し替える（`RunTrack` に「差し替えた Entity」を足す）。外した KokoState を `e.get()` で持っていたら、消えた Entity と同じく「読むと `undefined`・書いた値は捨てる」形にする。
   - 切り替え先のプレハブが、たどれない・`T` に当てはまらないときは、切り替えずに前のまま残し、注意を出す。
   - 切り替えで消えた子を指す参照は、壊れることがある。型で守るのは、ロードマップの「実行中に現れるものをプレハブで決めて静的に安全にする」で行う（構想のとおり）。インスタンス型のフィールドが、切り替えで型に当てはまらなくなった子を指すこと（`InstanceOf<typeof ポーン>` が、クイーンになった子を指す）も、同じくそちらで扱う。

5. **引き継ぎ・巻き戻し・適用**
   - `listChildren` を、再生のフレーム・セッションのフレーム・デバッグ実行の巻き戻しの点に入れる（`lists`）。前に組み立てたときのリストは、World のフィールドの値から作り直せる（書いたらその場で組み立てるので、フレームの時には、フィールドの値と子が合っている）。持たない。
   - 引き継ぎの形が変わるので、`PROTOCOL_VERSION` を上げる。
   - **適用**：今の `applyPart()` が子を消す（構想のとおり）。「維持」の印でリストのフィールドの値を戻したあと、新しい制作データのひな形で、空から組み立てる。子のフィールドに付けた「維持」は効かない（構想のとおり。子は作り直すため）。
   - **リセット**：制作データの値は空なので、子はできない。今のままでよい。

6. **画面**
   - Hierarchy（Play mode）：リストから作った子の行に、印（リストの形）を付け、ホバーで「Board.pieces のキー e2 から作りました」と出す。並びは、World の兄弟の並び（方針 2）。
   - Inspector（Play mode）：リストから作った子とその中の Entity に「リストから作ったので、直せません」と出す。デバッグ実行の一時停止中でも、値を直せないようにする（今は、一時停止中なら直せる）。リストを持つ Entity の、リストのフィールドも、見るだけ（方針 1）。
   - `RuntimeView` に、Entity がリストから作った子か（とキー）を引く口を足す。

7. **AI エージェント**
   - 新しい道具は足さない。KokoState の型に `PrefabList<typeof 駒>` を書き（`update_kokostate`。「import するプレハブ」は P6 の道具）、System でリストのメソッドを呼ぶ（`update_system`）。人と同じ道具で作れる。
   - エージェントの使い方（`docs/AGENT_MCP.md` と、`mcp.ts` の道具の説明）に、リストの書き方とキーの決まりを足す。

8. **チェスで確かめる作品**（計画者に確認した）：同梱サンプルには足さない。単体テストの中に、小さなチェス（盤、「駒」とバリアントの「ポーン」「クイーン」、合法手のガイド、成る System）を作り、画面の確認にも使う。

## 確かめ方

- 単体テスト
  - 型（typecheck）：L0 の宣言の決まり。`fieldSchema.ts` が `PrefabList<typeof 駒>` を `prefabList` にすること。ふつうのリスト・プレハブ型と取り違えないこと
  - 問題（repo-model）：入れ子に書いた・制作データで空でない、の問題。依存グラフで `T` がたどれること。抽出・ライブラリで ID が付け替わること
  - 組み立て（runtime）：`set()`・`replace()` で、キーの数だけ子ができ、リストを持つ Entity の下に、リストの順で並び、`set()` が作った子を返すこと。パラメータ（駒の色・Transform を指すもの）が渡ること。`remove()` で消え、`replace()` で足す・消す・並べ替えが一度にでき、`move()` で並びが変わること。同じキー・同じプレハブで `set()` しても、子が変わらないこと。代入（型エラーを無視したもの）・`world.setField` などでリストのフィールドに書くと、断って注意が出ること。`Prefab.destroy`・`world.destroy` で子を消せないこと。重なったキー・たどれないプレハブ・上限。メソッドから返ったときに、もう子があり、World の値と QuickJS の `board.pieces` の中身が合っていること。同じ呼び出しの並びの後ろと、あとの System に、作った子が渡ること。リストを持つ Entity を消すと、子も対応も消えること
  - 切り替え（runtime・repo-model）：`variantDelta()` が、2 段・3 段のバリアントで、上書き・足した KokoState・足した子・名前・親・並び順を集め、`T` 自身なら空なこと。ポーンからクイーンに替えると、ID とキーが残り、「駒」のままのフィールド（Transform・「動いた回数」）は実行中の値、ポーンが上書きした見た目は「駒」の値を経てクイーンの値、クイーンで足した KokoState と子は初めの値で足され、ポーンで足したものは消えること。「駒」で「維持」を付けたフィールドは実行中の値で、クイーンで足した「維持」の印は効かないこと。パラメータがいちばん強いこと。親と並び順が入れ替わること。クイーンにしかない System が動き始め、ポーンが残っていなければポーンにしかない System が止まること。呼び出しの途中で切り替えたとき、合わなくなった Entity を飛ばし、値が差し替わること。残った参照が、元のプレハブにある Entity を指したままのこと
  - 引き継ぎ・巻き戻し・適用：別のホストが引き継いでも、キーと子の対応が残り、切り替えられること。巻き戻すと対応も戻ること。適用で子がすべて作り直され、「維持」を付けたリストからは同じ子ができ、付けていなければ子がなくなること
- 計測：`pnpm bench:prefab` に、64 個のリストを組み立てる・並べ替える（L2）と、毎フレーム 8 個を切り替える（L3）計測を足す。切り替え 1 個が、`Prefab.spawn` で 1 個作り直すより重くならないことを目安にする（届かなければ、計画者に相談する）。
- 背骨の E2E：流れは変えないので直さない。L2・L3 のマージのあと、`main` の E2E の結果を確かめる。
- 画面：チェスのテスト用の作品で、Play mode の Hierarchy の印とホバー、Inspector の「直せません」、一時停止中に子を直せないこと、成ったときの見た目の切り替えを、`verify-change` スキルの手順（使い捨てのスクリプトとスクリーンショット）で確かめる。

## 構想から変えたこと

- リストの一つずつに、置く場所・向き・大きさを持たせない（計画者に確認した）。構想では、一つずつが「置く場所・向き・大きさ」を持ち、作るときと切り替えるときの初めの値にするとしていた。Transform は、ほかの KokoState と同じに扱い、切り替えでも、差分になければ実行中の値を残す。リストから場所を決めたいときは、パラメータにする。
- リストの中身は、メソッド（`set`・`remove`・`replace`・`move`）でだけ変えられ、直接は書き換えられない。呼んだ瞬間に子を組み立てる（計画者に確認した）。構想では「KokoState のフィールドの値（リスト）から子を足す・直す・消す」としていて、書き方は設計者に任されていた。値は今までどおりフィールドに持つ。
- 同梱サンプルにチェスは足さず、テスト用の作品だけで完了の条件を確かめる（計画者に確認した。構想には書いていない）。
