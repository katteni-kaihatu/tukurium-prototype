# デバッグ実行で一時停止して確かめながら原因を探す（実装計画）

- 状態：完了
- 設計者：れにうむ
- 実装者：れにうむ

## 作り方の方針

### 今の仕組み（調べた結果）

- **System の実行**：QuickJS の同期版（`@jitl/quickjs-wasmfile-release-sync`）で動かしている（`packages/script/src/sandbox.ts`）。
  - `Simulation`（`packages/runtime/src/simulation.ts`）が、フレームごとに `runSystem()` で、`onUpdate`・`onInput`・`onEvent`・`onCollision` などを順に呼ぶ。
  - 一つの呼び出しは、最後まで止まらずに走る。行の途中で止めて、あとから続ける仕組みはない。
- **スクリプトの書き換え**：スクリプトは、型を消したあと、行の数を保ったまま書き換えて読み込んでいる（ADR 0058）。実行時の誤りの行が、そのまま TypeScript の行になる。
- **ワークスペースの再生**：再生は、ホスト（参加者の一人のブラウザ）が動かし、結果を参加者で共有する。
  - 一時停止・続ける・止めるは、すでにある（`store.ts` の `pause`・`resume`）。
  - ホストが抜けたら、別の管理者が引き継ぐ。
- **ログ**：スクリプトの `log()` は、「ログ・保存」のパネルに出る。

### 方針

1. **デバッグ実行のときだけ、別の作りで動かす。**
   - ふつうの再生は、今の同期版の QuickJS と、今の書き換えのまま。速さは変えない。
   - デバッグ実行では、次の二つを使う。
     - QuickJS の非同期版（asyncify）
     - 一時停止のための書き換え（下の 2）

     ホストの関数が「待つ」ことができるので、スクリプトを行の途中で一時停止して、あとから続けられる。
   - デバッグ実行の間は遅くなってよい（構想で決めたこと）。どれくらい遅くなるかは D0 で測る。
   - 非同期版の QuickJS は同期版とは別のファイルなので、デバッグ実行を始めたときに初めて読み込む。ふつうの再生と最初の画面では読み込まない。
   - **1 フレームを「待てる」作りにする。** 今の `Simulation` は、1 フレームを最後まで一気に進める（`step()` は待たない）。デバッグ実行では、System の呼び出し・フレームの進め方・物理の順番を、途中で待てる作りにした 1 フレームを別に用意する。ふつうの再生は、今の一気に進める作りのまま。これが D2 のいちばん大きな作業になる。
   - ほかの案として、実行を Worker に移して `Atomics.wait` で待たせる方法もある。ただ、`SharedArrayBuffer` を使うにはページ全体の配信の設定（COOP・COEP）を変える必要があり、素材や埋め込みに影響する。そのため、非同期版を第一の案にし、D0 で試して決める。
   - D0 で、どちらの案も使えないと分かったとき、またはもっとよいやり方が見つかったときは、計画者に確かめてから、そのやり方で進める。
2. **一時停止のための書き換え**：デバッグ実行で読み込むスクリプトは、行の数を保ったまま、次のものを書き足す。
   - 文ごとに、行番号と、その場で見える変数を読み書きする関数を渡す呼び出し（`__dbg(行, 変数を読む関数, 変数を書く関数)`）。
   - 関数の入口と出口に、呼び出しの順を記録する呼び出し。
   - 見える変数は、構文を読んで決める（今の書き換えと同じ道具）。
   - 書き足すのは、型を消して import を書き換えたあと（今の読み込みの最後）。利用者のスクリプトだけに書き足し、Host API の下ごしらえ（prelude）には `__dbg` を書き足さない。
   - ただし、フィールドの書き換えを見つける所（下の 3 の「フィールドの変化」）だけは、prelude に足す。`e.get(Gun).ammo -= 1` のような書き込みを受け取るのは prelude なので。

   `__dbg` は、一時停止の条件やステップ実行に当てはまるときに、ホスト側で「待つ」。

   **一時停止の間は、QuickJS の中の関数を呼べない**（非同期版では、待っている間に呼び直すことができない）。そのため、値は次のように扱う。
   - **見る**：関数ごとに「最後に渡された変数を読む関数」を覚えておく。`__dbg` が一時停止する直前に、呼び出しの順のすべての関数について、その読む関数をその場で呼び、値を写し取る。呼び出しの順で外側の関数を選んでも、その値が見られる。パネルとコードホバーには、写し取った値を出す。
   - **変える**：変える値を、`__dbg` が待っていた答えとしてスクリプトに返す。再開した直後に、スクリプトの側で変数を書く関数を呼んで変える。
3. **一時停止の条件の確かめ方**
   - **コードの行**：`__dbg` に来たとき、行で当てはまるかを見る。空の行やコメントの行など、一時停止できる所のない行に付けたブレイクポイントは、その次の一時停止できる行に付く。
   - **Entity**：今処理している Entity（今も実行環境が持っている）で絞る。
   - **式**：一時停止の条件の式とログポイントの式は、書き換えのときにスクリプトに組み込み、その場の変数で計算する。
     - 条件が変わったら、デバッグ実行中でも組み込み直す。一時停止の最中には読み込み直せないので、組み込み直したものは、次のフレームの初めから使う。
     - 式で値を書き換えないように、書き換えになる式（代入や関数の呼び出し）は断る。細かな決まりは D5 で決める。
   - **フィールドの変化**：フィールドを書き換える所で、前の値と新しい値を比べ、見張っているフィールドが本当に変わったら一時停止する。
     - 書き換える所は、`e.get()` の書き込み・`world.set()`・`world.setField()` など。`e.get()` の書き込みは prelude で受け取るので、見つける処理を prelude に足す（上の 2）。
     - 一時停止する場所は、書き換えた行のすぐあと。
     - 物理など、スクリプト以外が書き換えたときは、そのフレームの切れ目で一時停止し、出どころ（例：「物理」）を出す。
   - **実行中のエラー**：エラーが起きたら、その行で一時停止し、エラーが起きた時点の値を出す。
     - 関数ごとに、エラーを受け止める書き足し（`try`・`catch`）を入れる。
     - 受け止めたら、その関数で最後に渡された「変数を読む関数」を、その場で呼ぶ。読む関数は変数そのものを読むので、直前の文の値ではなく、エラーが起きた時点の値になる。
     - 一時停止のあとで続けると、エラーは今と同じように扱われる（「エラー」パネルに出て、その System の呼び出しはそこで終わる）。
4. **ステップ実行は、同じフレームの次の一時停止できる所まで進む。**
   - 「次の行へ」「関数から出る」で、System の呼び出しの終わりを越えたら、同じフレームの、次に一時停止できる所で一時停止する。たとえば、同じ System の次の Entity の呼び出しの最初の文や、次の System の最初の文。
   - そのフレームに、もう一時停止できる所がなければ、次のフレームの最初の一時停止できる所で一時停止する。
   - ブレイクポイントで一時停止してから、処理を一つずつ追っていく使い方を前にする。
5. **一時停止は、再生まるごと。**
   - ホストが一時停止したら、ほかの参加者には次のものを通信で配る。
     - 一時停止した所（スクリプト・行・どの条件か）
     - 呼び出しの順
     - 変数と KokoState の値
     - 処理中の Entity
   - 通信の形が変わるので、`PROTOCOL_VERSION` を上げる。
   - ほかの参加者の画面には、一時停止した時点の世界（フレームの途中の状態）を出す。ステップ実行や値の変更で変わるたびに、全員に配る。
   - 一時停止したら、全員の画面でデバッグ用のパネルを開く。
   - 進める操作（続ける・ステップ実行・次のフレームまで・値を変える）は、共同編集か管理の権限がある人の操作として、ホストに送る。
6. **共有する状態の置き場所**
   - デバッグモードの「入・切」、一時停止の条件、ログポイント、見張るフィールドと Entity は、ワークスペースの上で全員が共有する。
   - 保存の履歴やリリースには入れない。
   - 共同編集の文書（Yjs）の中の、保存しない所に置く。どこに置くかは D0 で決める。
   - ブレイクポイントとログポイントは、行番号ではなく、スクリプトの文字の位置（Yjs の相対位置）に結び付ける。スクリプトを書き換えても（ほかの人が書き換えても）、付けた所に付いたまま動く。付けた行を消したら、そのブレイクポイントとログポイントも消す。
7. **ホストの引き継ぎ**
   - 一時停止している間にホストが抜けたら、引き継いだホストは、そのフレームの初めから、一時停止した状態で再生を受け継ぐ。
   - 行の途中の状態（QuickJS の中）は引き継げないので、フレームの切れ目に戻る。そのため、ほかの人に見えていたフレームの途中の世界は、引き継いだときにフレームの初めの状態に戻る。
8. **画面**
   - **デバッグ用のパネル**：新しいパネル。いつでも開け、いちばん上にデバッグモードのトグルを置く。
   - **再生の操作のそば**：「デバッグモード」の表示を出す。
   - **エディタ**：行番号の横に、ブレイクポイントとログポイントの印を出す（デバッグモードのときだけ）。
   - **3D 空間**：処理中の Entity を光らせる。
   - **コードホバー**：一時停止しているときは、重ねた変数の今の値も出す（ロードマップの「型と説明を見ながらスクリプトを書く」のコードホバーに足す）。
   - **値の見せ方と変え方**：`Date`・`Map`・`Set` などの値も、フィールドと同じ値の形式（ADR 0065）で見せ、直す。
9. **大きな判断は ADR に残す。**
   - 新しい ADR に、次のことを書く。
     - デバッグ実行の作り（非同期版の QuickJS と書き換え）
     - 一時停止の条件の確かめ方
     - ステップ実行の進み方
     - 共有する状態の置き場所
     - 通信
     - ホストの引き継ぎ
   - 番号は、PR を出す直前に、最新の次の番号を確かめて付ける。

## 確かめ方

- 単体テスト
  - 書き換えても行の数が変わらないこと。一時停止の直前に値を写し取れること（呼び出しの順の外側の関数の分も）、再開した直後に値を変えられること
  - 一時停止できる所のない行に付けたブレイクポイントが、次の一時停止できる行で働くこと
  - 条件を変えると、次のフレームの初めから新しい条件で一時停止すること
  - ふつうの再生では、非同期版を読み込まないこと
  - コードの行・Entity・式・フィールドの変化・実行中のエラーで一時停止すること。休ませた条件では一時停止しないこと
  - デバッグモードを切ると一時停止せず、ログポイントも書き出さないこと
  - ステップ実行の 3 つと、次のフレームまで。呼び出しの終わりを越えると、同じフレームの次の一時停止できる所で一時停止し、なければ次のフレームへ進むこと
  - スクリプトを書き換えても、ブレイクポイントが付けた所から動かないこと。付けた行を消すと、ブレイクポイントも消えること
  - 値を変えて続けると、変えた値で動くこと
  - 同じ値を書いたときは一時停止しないこと
  - 実行中のエラーで一時停止したとき、同じ文の中でエラーの前に変わった値も見えること
  - 式で値を書き換えようとすると断ること
- 計測：デバッグモードにしない再生の速さが変わらないことを、`pnpm bench:sim` で確かめる（D2 と D8）。
- 背骨の E2E：D2 と D8 のあとに流す（再生の流れに触れるため）。
- 画面：2 人で、一人が置いたブレイクポイントで両方の再生が一時停止し、全員の画面でパネルが開き、どちらからも進められることを、使い捨てのスクリプトのスクリーンショットで確かめる。
