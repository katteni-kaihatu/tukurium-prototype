## 作り方の方針

### 今の仕組み（調べた結果）

- **展開**（ADR 0076）：`Expander.build()`（`packages/repo-model/src/prefab.ts`）が、プレハブを入れ子まで開いた形（`Template`）を作る。入れ子のインスタンスは、その Entity の ID を頭に付けた ID（`N/中の ID`）で中身を足し、その Entity の `prefabOverrides` を最後に重ねる。ただし、**いちばん上の Entity の `instanceOf` は読まない**（`const link = e.id === root.id ? undefined : e.instanceOf`）。
- **編集用の展開**：`expandPrefabForEdit()` も、いちばん上の Entity の `instanceOf` を外してから展開する。
- **問題**：`prefabProblems()` と `prefabUsePath()`（`prefabNesting.ts`）は、いちばん上の Entity の `instanceOf` を数えない。元がない・自分を含む、はバリアントでは出ない。
- **型**（ADR 0082）：`prefabChain()`・`prefabTypeInfo()`（`prefabTypes.ts`）は、いちばん上の `instanceOf` をたどって、印の並びとパラメータの受け継ぎを作る。必須のパラメータの問題も、いちばん上には出さない（`prefabParams.ts`）。依存でたどれるプレハブ（`reachablePrefabs()`）・依存グラフ・抽出・ライブラリの読み込み（`packagePrefabs.ts`）は、いちばん上の `instanceOf` も、ほかの Entity と同じに扱う。実行中の `alivePrefabsOf()`（`simulation.ts`）も同じ。
- **適用・戻す**（ADR 0076 の 11）：`planApplyPrefabInstance()`・`planUnpackPrefabInstance()`（`prefabInstance.ts`）は、プレハブの中のインスタンス（入れ子）にも使える。プレハブの中で ID が変わるときは、`mappingsForOwner()` が、そのプレハブを使うインスタンスへ付け替えを広げる。ここでも、いちばん上の Entity のインスタンスは飛ばしている。
- **「維持」の印**：入れ子から来た印は、Inspector で「プレハブで付けた維持の印」として外せない（`inherited`）。それ以外は、開いているプレハブの `keep` に付けられる。
- **画面**：プレハブの詳細は `DefinitionProperties.tsx` の `PrefabProperties`。インスタンスの「プレハブに適用」「ふつうの Entity に戻す」は `InspectorPanel.tsx` と `PrefabInstanceAsk.tsx`。エージェントの道具は `apps/server/src/agent/mcp.ts`・`tools.ts`。

まとめると、**バリアントの型の決まりはできていて、展開・編集・作る・書き戻す画面がない**。バリアントの中身は「いちばん上が元のプレハブの入れ子のインスタンスになっているプレハブ」なので、入れ子の仕組みを、いちばん上にも効かせればよい。

### 方針

1. **バリアントの保存の形は、今のプレハブのまま**（新しいキーを足さない）。
   - バリアント `V` は、ふつうの `PrefabDef`。いちばん上の Entity `R` が `instanceOf: { prefab: 元 }` を持つ。
   - 上書きは `R.prefabOverrides`（キーは元のプレハブの「ルートからの ID」）。バリアントで足した KokoState は `R.states`（いちばん上）と `addedStates`（中）、足した子の Entity は `V` のふつうの中の Entity、足した System は `V.systems` と `R.instanceSystems`（方針 6）。
   - 保存の形と通信の形は変わらないので、`PROTOCOL_VERSION` は上げない。

2. **展開では、いちばん上の `instanceOf` を、ID の頭を空にした入れ子として開く。**
   - `build()` で、いちばん上の Entity にも入れ子と同じ処理を通す。頭が空なので、元の Entity は**元のプレハブの中と同じ「ルートからの ID」**で並ぶ（`join("", rel) === rel`）。
   - そのため、**バリアントのインスタンスの上書きのキーは、元のプレハブのインスタンスのキーと同じ**になる。インスタンスで変えたことを、そのままバリアントの上書きへ移せる（方針 5）。パラメータの `entity` も、元から受け継いだものとバリアントで足したもので同じ書き方になる。
   - `R.prefabOverrides` は、「外側のインスタンスの分を最後に重ねる」所で、いちばん上の分も重ねる（今は飛ばしている）。重ね方は入れ子と同じで、内側から順に、外側が勝つ：元の値 → バリアントの上書き → インスタンスの上書き。
     - 入れ子では、上書きを当てる Entity を `join(e.id, 道)` で探し、親の上書きが `null` なら `e.id` に付ける。いちばん上では、頭を空にして `道` そのもので探し、`null` なら `""`（いちばん上）に付ける。
   - System と「維持」の印は、入れ子と同じく足し合わせる（元 → バリアント）。
   - **いちばん上の場所・向き・大きさ（Transform）は、ほかのフィールドと同じに扱う**（計画者に確認した）。
     - `R` には、作るときに Transform を持たせない。持たなければ、元のいちばん上の Transform がそのまま見える（元で大きさを変えると、バリアントにも届く）。
     - バリアントで変えたら `R.states` に持ち、上書きとして数える：`△`・一つずつ戻す（`R.states` から Transform を外す）・書き戻す（方針 7）。今の `getPrefabOverride()` は、いちばん上の Transform を上書きから外している（置いたインスタンスでは置き方なので）。バリアントのいちばん上（持ち主がプレハブで、そのプレハブの `root` である Entity）だけは外さないようにする。
     - 置いたインスタンス・プレハブの中に置いた入れ子のインスタンスでは、今までどおり、Transform は置き方で、上書きに数えない。`Prefab.spawn` で作るときは、バリアントの Transform（なければ元の Transform）が効く。
     - 置くとき（`addInstance()`）に、置くプレハブのいちばん上から向きと大きさを写す所は、`R.states` ではなく、展開したあとのいちばん上（バリアントの Transform、なければ元の Transform）から写す。`R` が Transform を持たないことがあるため。
     - 元がないとき（方針 3）は、`R` が Transform を持たないことがある。そのときは Transform の初めの値で補う。
   - **由来（`origin`）**：いちばん上の Entity の由来は、バリアント（`{ prefab: V, entity: R }`）にする。入れ子のように内側（元のいちばん上）にすると、「入れ子のインスタンスがどのプレハブのものか」を由来で決める所（`simulation.ts` の `SpawnTemplate.instances` など）で、バリアントのインスタンスが元のインスタンスに見えてしまう。元から来たほかの Entity の由来は、今までどおり内側のプレハブ。
     - 由来の Entity の `states` を「プレハブの値」として読む所がある（`InspectorPanel.tsx` の `sourceEntity`。KokoState の `元`・`追加` の札と、外せるかを決める。同じファイルの Hierarchy の行の `△` を決める所も、由来の Entity の `states` と比べる）。バリアントのいちばん上では、由来の `R.states` にはバリアントで変えた分しかなく、元から来た KokoState は入っていない。V2 で、バリアントのインスタンスのいちばん上で札・外せるか・Hierarchy の `△` が正しいかを確かめ、足りなければ展開した値と比べるようにする。
   - 取っておく入れ物（`PrefabExpansionCache`）は、読んだプレハブの鍵に元のプレハブが入るので、元を直せばバリアントも作り直される。入れ子と同じなので、手を入れる所はない見込み。`bench:prefab` に、3 段のバリアントを置く計測を足して確かめる。

3. **元がない・自分を含む、の問題を、いちばん上にも出す。**
   - `prefabProblems()`・`prefabUsePath()`・`addInstance()`・`addPrefabEntity()` の輪の確かめで、いちばん上の `instanceOf` も辺に数える。`V → 的 → V` も、`的` の中に `V` のインスタンスを置く形も、輪として断る・問題にする。
   - 元のプレハブを消したら、バリアントは残す。展開では、`R` を、自分の `states` と足した子だけを持つふつうの Entity として出し（入れ子で元がないときと同じ。Transform がなければ初めの値で補う）、「元のプレハブがありません」の問題を出す。消すときの確認に、残るバリアントの数を出す。
   - 必須のパラメータの問題を、いちばん上に出さないのは今のまま（受け継いで、そのまま必須のまま）。

4. **プレハブから作る（「バリアントを作る」）**
   - `ProjectDoc.createVariant(base)`：いちばん上の Entity が `instanceOf: base` だけを持つプレハブを作る。名前は「<元の名前>のバリアント」（重なれば番号を付ける。今のプレハブの名前の付け方に合わせる）。フォルダは元と同じ所。作ったら、プレハブの詳細を出して名前を直せるようにする。
   - 出す所：Resources のプレハブの右クリック、プレハブの詳細のボタン。
   - **ライブラリのプレハブからも作れる**（計画者に確認した）。手元にバリアントを作り、ライブラリのプレハブには書き戻せない（今の入れ子と同じ判定）。

5. **インスタンスで変えたことから作る（「バリアントとして保存」）**
   - 「プレハブに適用」の隣に出す。アウトプットのインスタンスにも、プレハブの中のインスタンス（入れ子）にも出す。
   - ただし、バリアントを開いたときのいちばん上の Entity には出さない（計画者に確認した）。押すと、開いているバリアントと元の間に一段を差し込む動きになり、分かりにくいため。段を差し込みたいときは、元から「バリアントを作る」で作り、つなぎ替えはしない。
   - 中身は三つの手順を、一つの確認と一つの transaction で行う：(1) 方針 4 のとおり空のバリアントを作る、(2) インスタンスの `instanceOf` をバリアントにつなぎ替える（方針 2 のとおり上書きのキーは同じなので、見た目は変わらない）、(3) そのインスタンスを、バリアントへ適用する（今の `planApplyPrefabInstance()` の計画を、つなぎ替えたあとの制作データで作る）。
   - (3) の適用先（新しいバリアント）は、いちばん上が元のプレハブのインスタンス（頭のない入れ子）になっている。今の適用は、入れ子の中への変更を、適用先が持つ入れ子のインスタンス `N` の上書き（キーは `N/x` の形）へ移す。いちばん上が入れ子のときは、キーに頭がなく `x` のまま `R.prefabOverrides` へ移し、いちばん上の Entity への変更は `R.prefabOverrides[""]`（足した KokoState は `R.states`）へ移す。この「適用先のいちばん上が入れ子」の扱いを、V3 で `planApplyPrefabInstance()` に足す（V4 の書き戻しも、この上に作る）。
   - こうすると、追加した Entity の移し方・参照の付け替え・「維持」の印の移し方・効いていない上書きを残すことは、今の適用と同じ動きになる。確認の画面も、今の適用の確認に名前の入力を足したものにする。
   - 保存したあと、インスタンスは上書きのないバリアントのインスタンスになる。場所・向き・大きさといちばん上の名前は、インスタンスに残る。
   - 名前の初めの値は、インスタンスの名前（利用者が付け直していれば、その名前を使える）。ほかのプレハブと名前が重なるとき（名前を変えずに置いたインスタンスは、元と同じ名前なので重なる）は、方針 4 の「<元の名前>のバリアント」にする。

6. **バリアントを開いて直す**
   - `expandPrefabForEdit()` で、いちばん上の `instanceOf` を外さずに展開する。元から来た Entity は、入れ子と同じく `R/ルートからの ID` で出て、`元` の札・`△`・一つずつ戻す・消せない、が今の仕組みのまま効く。
   - いちばん上の Entity の行と Inspector に「「的」のバリアント」と出し、元を開けるようにする。
   - **「維持」の印**（計画者に確認した）：元で付けた印は固定（外せない。今の `inherited` のまま）。元で付けていないフィールドには、元から来たものでも、バリアントで印を付けられ、`V.keep` に持つ。
   - **System**：プレハブの詳細の System の並びに、元の System を「元」として出し、外せない・「入・切」も変えられないようにする（足し合わせは「どれかが入なら入」なので、バリアントでは切れない）。バリアントで足した System は、今のプレハブと同じく足す・外す・並べ替えられる。
     - バリアントで足した System の置き場所は、`V.systems`（プレハブの詳細で足したもの）と `R.instanceSystems`（開いたときに、いちばん上の Entity の Inspector で足したもの）の二つがありうる。どちらも今の仕組みで足し合わされるので、両方を許し、書き戻す・つながりを切るときは両方を扱う（方針 7）。プレハブの詳細の並びには、二つを合わせて出す。
   - **パラメータの指す Entity**：バリアントを開いたとき、元から来た Entity の ID は `R/x` になる。一方、パラメータの `entity` と上書きのキーは、ルートからの ID の `x`（方針 2）。今の `paramEntityPath()`・`paramEntityId()`（`prefabParams.ts`）は、いちばん上の ID を空にするだけなので、バリアントでは `R/` を外す・付ける変換を足す。「維持」の印の Entity は、展開の `relOf()` が `R/x` を `x` にするので、今のまま `R/x` で持ってよい。
   - **パラメータ**：「プレハブの設定」に、元から受け継いだパラメータを先に（名前・必須は変えられない形で）出し、そのあとに足せる。元と同じ名前は、足す前に断る（今は問題として出すだけ）。省略したときの値は、元のフィールドをバリアントで上書きすれば変わる（今の上書きそのもの）。
   - **見分け方**：Resources では、プレハブの印に、バリアントの印（小さな枝分かれの形）を重ね、ホバーで「「的」のバリアント」と出す。プレハブの詳細の上に「元：的」を出し、押すと元の詳細へ移る。
7. **元へ書き戻す・つながりを切る**
   - バリアントを開き、いちばん上の Entity で「プレハブに適用」を押すと、元のプレハブへ書き戻す。今の `planApplyPrefabInstance()` を、持ち主がバリアントで、インスタンスがいちばん上（道が空）の形にも効かせる。
     - 上書き → 元の Entity へ。いちばん上の Transform（`R.states` に持っていれば）→ 元のいちばん上へ（方針 2。今の適用では、いちばん上の Transform はインスタンスに残すが、バリアントのいちばん上だけは書き戻す）。足した KokoState → 元へ。足した子の Entity → 新しい ID で元へ移す（バリアントの中の子は、すべていちばん上の下にあるので、すべて移る）。バリアントで足した System（`R.instanceSystems` は今の適用のとおり、`V.systems` も）→ 元の System の並びの後ろへ。バリアントで付けた「維持」の印 → 元へ。
     - 書き戻したあと、バリアントには差が残らない（パラメータを除く）。
     - **バリアントのパラメータは、バリアントに残す**（元に移すと、元のプレハブ型が変わり、元を使うコードに型エラーが出るため）。指している Entity が元へ移ったら、新しい ID に付け替える（方針 2 のとおり、ルートからの ID のままで指せる）。
     - ID の付け替えを、元のインスタンスと、バリアントとそのインスタンスへ広げる（`mappingsForOwner()` で、いちばん上のインスタンスを飛ばさないようにする）。
     - ライブラリのプレハブには書き戻さない。
     - **確認の画面に、書き戻しが届く所を出す。** 書き戻すと、元を使っているすべての所に届く：元のインスタンス、元のほかのバリアント（何段先も）とそのインスタンス。バリアントで足した子や System も、そこへ入る。今の適用の確認は「ほかのインスタンスにも反映します」と書くだけで、どこに届くかが分からない。
       - 届く所を求める関数（`prefabUsers()`。repo-model）を一つ置く：元を `instanceOf` で指す Entity を、アウトプットとプレハブの中から集め、いちばん上で指すもの（バリアント）は、そのバリアントを使う所までたどる（輪は止める）。書き戻す元のバリアント自身と、そのインスタンスは数えない。
       - 出し方：「「的」を使っている所に反映します：インスタンス 5 個、バリアント 2 個（「赤い的」「青い的」）」。バリアントは名前を並べ（多ければ先頭の数個と「ほか N 個」）、インスタンスは数だけ。
       - ほかのバリアントで上書きしているフィールドには届かない（上書きが勝つ）。ここは数えず、文で「上書きしている所は、そのまま」と添える。フィールドごとに数えると、計画を作るたびに展開をし直すことになり重いため。
       - ふつうのインスタンスの「プレハブに適用」の確認も、同じ出し方にする（同じ関数を使う。バリアントがあると、ふつうの適用もバリアントに届くため）。
   - **V3・V4 で直すまでは、バリアントが関わる「プレハブに適用」を断る**（V1 で入れる）。V1 で展開がいちばん上のつながりを読むようになると、手直しの前の `planApplyPrefabInstance()` で動いてしまい、壊れるため。
     - 置いたバリアントのインスタンスで押す形：元から来た Entity への上書きのキーには頭がない（`x`）が、今の適用は入れ子の上書きのキーを `N/x` の形だと思っているので、当て先がバリアントの中に見つからない。V3 で「適用先のいちばん上が入れ子」の扱いを足したら外す。
     - バリアントのいちばん上で押す形（書き戻し）：中の Entity の ID が変わっても、`mappingsForOwner()` がいちばん上のインスタンスを飛ばすので、バリアントを置いたインスタンスの上書きのキーが合わなくなる。V4 で外す。
   - **「ふつうの Entity に戻す」は、今の決まり（ADR 0076 の 11）どおり、一段だけ中身を実体にする**（計画者に確認した）。バリアントが関わる形は二つある。
     - **バリアントのいちばん上で切る**（計画者に確認した）：今の `planUnpackPrefabInstance()` で、元の中身をバリアントの中の Entity に写す。元がふつうのプレハブなら、`R` の `instanceOf` を外し、バリアントは元と関係のないふつうのプレハブになる。元もバリアント（「赤い的」→「固い的」→「的」で、「赤い的」を切る）なら、`R` は元の元（「的」）のインスタンスになり、上書きは「固い的」のいちばん上の上書きに「赤い的」の上書きを重ねたものになる。「赤い的」は「的」のバリアントになる。
     - **置いたバリアントのインスタンスを戻す**（「固い的」のインスタンスで押す）：インスタンスは、元（「的」）のインスタンスになる。上書きは、バリアントのいちばん上の上書きにインスタンスの上書きを重ねたもの。バリアントで足した子は、持ち主の中のふつうの Entity になり、バリアントで足した KokoState・System も持ち主に移る。見た目は変わらない。
       - 今の `planUnpackPrefabInstance()` は、プレハブのいちばん上を写したあと `instanceOf` を消し、プレハブ自身の中の Entity だけを写す。そのままでは、元から来た中身と、元の Entity を指す上書きが消える。V1 で展開がいちばん上のつながりを読むようになると、画面に出ていた中身が消えてしまう。
       - プレハブの中に置いたバリアントのインスタンス（入れ子）を戻すときも、同じ。
     - **V4 で直すまでは、バリアントが関わる「ふつうの Entity に戻す」を、二つとも断る**（V1 で入れる）。いちばん上で切る形も、V1 のあとは今の入れ子の処理で動いてしまう。中の Entity に新しい ID が付くのに、`mappingsForOwner()` がいちばん上のインスタンスを飛ばすので、バリアントを置いたインスタンスの上書きのキーが合わなくなるため。
     - **一段分のパラメータは、写して残す**（計画者に確認した）：切ったプレハブ（またはインスタンスの持ち主）が受け継がなくなるのは、実体にした一段（元が自分で持っていたパラメータ）だけ。いちばん上で切るときは、それをバリアントに写し、指す先を写した Entity の新しい ID に付け替える（名前・必須・説明・並び順はそのまま）。それより上の段のパラメータは、今までどおり受け継ぐ。これで、バリアントのパラメータの名前と型は変わらず、`Prefab.spawn(固い的, { Speed: 20 })` のようなコードはそのまま通る。置いたインスタンスを戻すときは、インスタンスはパラメータを持たないので、写すものはない。
     - いちばん上で切るときの確認の画面に、「元のプレハブ型・インスタンス型に当てはまらなくなる」こと（元もバリアントなら、元の元の型には当てはまったまま）と、あとで問題・型エラーになりうる所の数を出す：そのバリアントを元の型のフィールドに入れている所の数と、そのバリアントを import している System の数（依存グラフの System → プレハブの辺で数える。元の型として使っているかまでは調べない）。
     - 中の Entity の ID が変わるので、バリアントのインスタンスの上書きのキーも付け替える（今の仕組みのとおり）。

8. **実行中に作る・型**
   - `Prefab.spawn` は、仮の制作データを展開してひな形を作るので、方針 2 ができればバリアントも作れる。いちばん上の由来（方針 2）で、作ったものがバリアントのインスタンスとして記録されることを確かめる。
   - 型の決まりと当てはまり（ADR 0082）は、今のまま使う。「プレハブを型で扱ってコードからインスタンスを作る」の P7（画面で作ったバリアントで、型・Inspector の候補・`Prefab.spawn`・パラメータの受け継ぎを確かめる）は、この項目の V2 のあとに進められる。ライブラリの中のバリアント（ライブラリの印が自分の ID だけの件）も、そこで見る。

9. **AI エージェント**
   - 道具を二つ足す：`create_variant`（元のプレハブから作る。名前を渡せる）、`save_instance_as_variant`（インスタンスで変えたことから作る）。
   - 今の `apply_prefab_instance`・`unpack_prefab_instance` は、もうプレハブの中の Entity を受け取れる（`tools.ts` の `applyPrefabInstance()`）。バリアントのいちばん上の Entity で、書き戻す・つながりを切るが動くことを確かめる。`prefab_detail` に、元のプレハブ（`variantOf`）と、受け継いだパラメータ・System の区別を足す。

大きな判断（バリアントの持ち方、展開での ID の頭、いちばん上の Transform と由来、作る・書き戻す・切る、「維持」・System・パラメータの決まり）は、V1 で ADR 0083 に残す。

## 確かめ方

- 単体テスト（repo-model が中心）
  - 展開：「固い的」のインスタンスの hp が 300。「的」の別のフィールド・中の Entity・System を変えると、「固い的」とそのインスタンスに届く。上書きした hp は「的」を直しても 300 のまま。重ね方（元 → バリアント → インスタンス）。3 段のバリアント。いちばん上の Transform（持たなければ元のもの、持てば持ったもの、置いたインスタンスではインスタンスのもの、元がなければ初めの値）。いちばん上の親の上書きが `null` のとき、いちばん上に付くこと。由来。取っておく入れ物で、元を直すとバリアントが作り直され、関係ないプレハブは作り直されないこと。近道と `thorough` の結果が同じこと（今のテストの形）
  - 問題：元がない（展開で `R` と足した子が残る）、自分を含む（`V → 的 → V`、`的` の中に `V` を置く）、輪を作る置き方を断る
  - 作る・開いて直す（V2）：`createVariant()` の名前とフォルダ。ライブラリのプレハブから作れ、書き戻せないこと。バリアントを開いて、いちばん上の Transform を変えると `△` が出て、一つずつ戻せること。置いたインスタンス・入れ子のインスタンスの Transform は、今までどおり上書きに数えないこと。バリアントを置くと、展開したいちばん上（バリアントの Transform、なければ元の Transform）から向きと大きさを写すこと。バリアントのインスタンスのいちばん上で、元から来た KokoState・バリアントで足した KokoState・インスタンスで足した KokoState の札と外せるかが正しく、Hierarchy の行の `△` が、インスタンスで変えたときだけ出ること
  - インスタンスから作る：適用先のいちばん上が入れ子のとき、上書きが頭のないキーで `R.prefabOverrides` へ移ること。上書き・足した KokoState・足した Entity・追加 System・「維持」の印がバリアントへ移り、インスタンスが上書きのないバリアントのインスタンスになり、展開の結果が前と同じこと。効いていない上書きがインスタンスに残ること。プレハブの中のインスタンスからも作れ、バリアントのいちばん上では断ること。確認中に制作データが変わっても同じ ID を使うこと
  - 書き戻す：上書き・いちばん上の Transform・足した子・System（`V.systems` と `R.instanceSystems`）・「維持」が元へ移り、バリアントに差がなくなること。パラメータがバリアントに残り、指す先が付け替わること。元のインスタンス・ほかのバリアント・バリアントのインスタンスの上書きのキーが付け替わること。3 段（元自身がバリアント）のとき、書き戻した上書きが、元のいちばん上の上書き（`R.prefabOverrides`）に入ること。`prefabUsers()` が、アウトプットとプレハブの中のインスタンス・何段先のバリアントとそのインスタンスを数え、書き戻す元のバリアント自身とそのインスタンスを数えず、輪で止まること
  - つながりを切る：バリアントがふつうのプレハブになり、見た目が変わらないこと。印の並びから元が消えること。元から受け継いだパラメータが写され、新しい ID を指し、パラメータの名前と型が変わらないこと。3 段で切ると、元の元のバリアントになり、印の並びから元だけが消え、元の元のパラメータは受け継いだままのこと。確認に出す数

## 構想から変えたこと

- 「維持」の印は、元で付けた印だけを固定にし、元で付けていないフィールドには、元から来たものでも、バリアントで付けられるようにする（計画者に確認した。構想の「付け外しは変えられない」を、元で付けた印のことと読んだ）。
- ライブラリのプレハブからもバリアントを作れる。書き戻しはできない（計画者に確認した。構想には書いていない）。
- バリアントのいちばん上の Transform は、置いたインスタンスと違って、ほかのフィールドと同じく上書きに数え、書き戻す（計画者に確認した。構想には書いていない）。
- バリアントのいちばん上にも「ふつうの Entity に戻す」を出し、つながりを切れる（計画者に確認した。構想には書いていない）。今の決まりどおり一段だけ実体にするので、元がふつうのプレハブなら元と関係のないふつうのプレハブに、元もバリアントなら元の元のバリアントになる（計画者に確認した）。実体にした一段分のパラメータは、バリアントに写して残す（計画者に確認した）。
- 「バリアントとして保存」は、バリアントを開いたときのいちばん上には出さない（計画者に確認した。構想には書いていない）。

## 分かったこと・残り

- 構想の「リストで切り替えるとき、値を残すかどうかは、元のプレハブの「維持」で決まる」は、そのまま。バリアントで足した「維持」の印は、置いたインスタンスへの適用（再生中の作品の差し替え）では効くが、リストでの切り替えでは見ない。ロードマップの「プレハブのリストから子を組み立てる」の設計で、この扱いを確かめる。
- 書き戻しで、バリアントのパラメータを元へ移す道は作らない。必要になったら、計画者に相談する。
- ライブラリのプレハブを元にしたバリアントを、ライブラリとして配る・抽出するときの扱いは、この項目では作らない。ライブラリが別のライブラリのプレハブに頼る形になるため。ロードマップの「利用者が作ったライブラリを配って選んで使える」などで扱う。
