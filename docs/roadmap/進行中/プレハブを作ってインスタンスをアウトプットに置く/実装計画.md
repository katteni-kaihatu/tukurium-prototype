## 作り方の方針

### 今の仕組み（調べた結果）

- Entity は、どれか一つのアウトプットに属する（`EntityDef.output`。`packages/repo-model/src/schema.ts`）。値は KokoState ごと・フィールドごとに持つ。
- アウトプットは、動かす System の並び（`OutputDef.systems`）を持つ。
- 再生では、`buildWorld()`（`packages/runtime/src/buildWorld.ts`）が、そのアウトプットの Entity をそのまま World に並べる。
- 共同編集（Yjs）では、Entity の値はフィールドごとの `Y.Map` で、フィールドごとの後勝ち（`packages/repo-model/src/projectDoc.ts`）。
- Git には、1 要素 1 ファイルの JSON で保存する（`packages/repo-model/src/files.ts`）。
- リソースの種類（KokoState・System・マテリアル・素材・フォルダ）は、論理パスで表す（`resourcePath.ts`。ADR 0010）。
- ワールドは、離れた空間で編集する。置き場所は `apps/client/src/workspace/anchor.ts` で決めている。
- 次の所は、どれも「アウトプットの Entity」を直接読んでいる。
  - 依存グラフ・抽出・参照の診断
  - 変化の印と戻す
  - Hierarchy・Inspector
- ライブラリは Entity を持たず、含めるリソース（`OutputDef.resources`）だけを配る。

### 方針

1. **プレハブは新しいリソースの種類にする。**
   - 中身は、プレハブの中の Entity の並び（子と KokoState の値を含む）・System の並び・編集する場所の設定。
   - Git には `prefabs/<ID>.json`（Entity は `prefabs/<ID>/entities/<Entity の ID>.json`）で保存する。
   - 論理パスと ID はほかのリソースと同じ扱い（ADR 0010）。拡張子は `.prefab`。
2. **インスタンスは、アウトプットの中の一つの Entity として持つ。**
   - インスタンスは「どのプレハブか」（リソース ID）と、インスタンスで変えた所を持つ。
     - フィールドの値
     - 足した Entity・KokoState・System
   - 場所・向き・大きさは、インスタンスそのものの Transform に持つ。
3. **使う所の手前で「展開」する。**
   - 制作データから、インスタンスをプレハブの中身に置き換えた Entity の並びを作る関数（`expandPrefabs()`）を、repo-model に置く。
     - インスタンスで変えた所は、上に重ねる。
     - 入れ子のプレハブも、たどって展開する。
     - 自分を含むプレハブ（循環）は、展開せずに問題として出す。
   - 再生（`buildWorld()`）・依存グラフ・抽出・参照の診断・Hierarchy は、展開した並びを読む。
   - アウトプットを公開したリリースと、セッションに出した配置でも、同じように展開して動かす。リリースには、使っているプレハブも入れる。
   - こうすると、今の「アウトプットの Entity」を前にした作りを、そのまま使い続けられる。
4. **展開した Entity の ID は、決まった作り方にする。**
   - 「インスタンスの ID ＋ プレハブの中の Entity の ID」から作る。開き直しても、別の人の画面でも同じ ID になる。
   - そのため、展開した Entity を指す参照（`EntityRef` など）が切れない。
   - 入れ子のときは、ID をつなげる。
5. **System は、アウトプットの System の並びに足し合わせる。**
   - アウトプットで動かす System は、アウトプットのものと、中のインスタンスのプレハブのもの（インスタンスで足したものを含む）を合わせたものにする。
   - 同じ System は一つにまとめる。
   - 並び順は、アウトプットのものを先にし、プレハブのものはあとに足す。細かな決まりは P0 で決める。
6. **プレハブの編集は、アウトプットの編集と同じ画面で行う。**
   - Hierarchy でプレハブを開くと、プレハブの中の Entity の並びが出る。Inspector で直す。
   - 編集する場所の設定は、次の 2 つ。
     - 「その場」：選んだインスタンスの位置か、今の区画に出す
     - 「離れた空間」：ワールドと同じ置き場所の決め方（`anchor.ts`）を使う
7. **インスタンスで変えた所の印と戻すは、今の「変化の印」と「戻す」の仕組みを使う。**
   - 比べる相手を、「最後の保存」から「プレハブの中身」に替える。
   - プレハブから来たものと、インスタンスで足したものも、この比べ方で見分ける。
8. **共同編集は、今と同じくフィールドごとの後勝ちにする。**
   - プレハブの中の Entity の値も、インスタンスで変えたフィールドの値も、フィールドごとの `Y.Map` で持つ。
9. **大きな判断は ADR に残す。**
   - 新しい ADR に、次のことを書く。
     - プレハブの保存の形
     - インスタンスの持ち方
     - 展開と ID の作り方
     - System の足し合わせ
     - 編集する場所
   - 番号は、PR を出すときの最新の次の番号にする（ほかの作業と重ならないように、出す直前に確かめる）。

## 確かめ方

- 単体テスト
  - 展開：インスタンスがプレハブの中身になること、変えた所が重なること、ID が決まった作り方になること、入れ子と循環
  - System の足し合わせ（同じ System を一つにまとめる、並び順）
  - 再生で、3 つのインスタンスがプレハブの System で動くこと
  - プレハブを直すと、すべてのインスタンスに反映されること
  - Entity からプレハブを作っても、参照が切れないこと
  - プレハブから来たものを消せないこと、変えた所を戻せること
  - プレハブに適用すると、ほかのインスタンスに反映されること
  - ふつうの Entity に戻したあとは反映されないこと
  - プレハブを消したときの問題
  - ライブラリのプレハブのバージョン
  - 名前の変更と移動で、インスタンスとのつながりが切れないこと
- 背骨の E2E：P1 と P8 のあとに流す（再生と保存の流れに触れるため）。
- 画面：Hierarchy・Inspector での見分け方と印、編集する場所の切り替えを、使い捨てのスクリプトのスクリーンショットで確かめる。
