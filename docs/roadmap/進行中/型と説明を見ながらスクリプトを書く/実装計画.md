## 作り方の方針

### 今の仕組み（調べた結果）

- 型の確かめは、ブラウザの裏側の Worker（`apps/client/src/workspace/typecheck.worker.ts`）で、TypeScript の Language Service を持つ `TypeChecker`（`packages/typecheck/src/checker.ts`）が行っている。
  - Worker への頼みは「制作データまるごとを渡して、型エラーとスキーマを返す」の一種類だけ。
  - 頼むのは `useTypeCheck()`（`useProblems.ts`）。
- 型の確かめでは、System のスクリプトを、仮想のファイルにそのまま入れている（`virtualProject()`）。
  - エディタの文字の位置と、TypeScript の中の位置は同じ。
  - KokoState は、論理パスに合わせた宣言ファイル（`kokoStateDeclaration()`）。
- Host API の宣言には、`HOST_API_SPEC` の説明（`doc`）が JSDoc として入っている。TypeScript の Quick Info や入力の候補に、そのまま出せる。
- エディタは CodeMirror。今の入力の候補は自前の 2 つで、型は使っていない。
  - Host API の候補（`hostApiCompletionSource`）
  - import のパスの候補（`importCompletionSource`）
- 空間に置いたパネルでは、エディタの座標を直す仕組み（`apps/client/src/panels/editorCoords.ts`）がある。
- KokoState とフィールドには、説明を書く場所がない（`FieldDef` は `id`・`name`・`type`・`default`）。

### 方針

1. **Worker に、場所を聞く頼みを足す。**
   - 今の「型を確かめる」頼みに、次の 4 つを足す。
     - ある場所の型と説明（Quick Info）
     - 入力の候補
     - 候補の詳しい説明
     - 定義の場所
   - どれも、すでにある Language Service の働き（`getQuickInfoAtPosition`・`getCompletionsAtPosition`・`getCompletionEntryDetails`・`getDefinitionAtPosition`）をそのまま使う。
   - 処理は `packages/typecheck` の `TypeChecker` に足す。Worker でもテストでも同じものを使う。
2. **古い内容の答えを出さない。**
   - 頼むときに、そのスクリプトの今の文字（エディタの中身）と、その版を送る。
   - Worker は、その文字で該当のファイルだけを差し替えてから答える（制作データまるごとは送り直さない）。
   - Worker は一つなので、場所を聞く頼みは、型の確かめより先に答える。型の確かめが終わっていなくても、前に読み込んだ制作データと、今の一つのファイルで答える。
   - 答えが返る前に文字が変わっていたら、画面はその答えを捨てる。共同編集でほかの人が書き換えたときも同じ。
3. **コードホバーは CodeMirror の `hoverTooltip` で出す。**
   - 中身は、型（TypeScript の書き方のまま）・説明（JSDoc）・その場所の型エラーの文。この順に、一つの枠に出す。
   - 今のエディタの誤りの枠（lint）は、コードホバーにまとめる。同じ場所に枠を二つ出さない。
   - TypeScript の読み込み中は「読み込み中」と出し、読み込めたら中身に替える。
4. **入力の候補は、TypeScript の候補に替える。**
   - 今の Host API の候補（自前）はやめ、TypeScript の候補にまとめる（Host API の説明は JSDoc から出る）。
   - import のパスの候補（自前）は残す。import の文字の中では自前の候補だけを出し、ほかの所では TypeScript の候補を出す（同じ候補を二重に出さない）。
   - 候補には型と説明を添える。詳しい説明は、選んでいる候補の分だけを後から聞く。
5. **定義へ移動**
   - 定義の場所が、どのファイルかで行き先を決める。

     | 定義の場所 | 行き先 |
     | --- | --- |
     | KokoState の宣言ファイル | その KokoState の「リソースの詳細」を開く |
     | 同じスクリプト | その行へ |
     | 型の定義のリソース | そのエディタを開く |
     | Built-in・ライブラリの KokoState | 見るだけの「リソースの詳細」を開く（ライブラリの KokoState に見るだけの画面がなければ、H4 で作る） |
     | Host API の宣言 | 移らない（コードホバーで説明を見る） |

   - 操作は二つ。
     - コードホバーの中の「定義へ移動」を押す。キーを使わないので、どのブラウザでも、空間に置いたパネルでも使える。
     - Ctrl（Mac では Cmd）を押しながらのクリック。慣れた人向けの近道。Mac の Ctrl ＋ クリックは右クリックと同じ扱いなので、Mac では Cmd にする。
   - F12 は使わない（Chrome や Edge では開発者ツールが開き、ページの側で止められないことが多いため）。
6. **KokoState とフィールドに説明を持たせる。**
   - `KokoStateDef` と `FieldDef` に、説明（`description`。なくてもよい）を足す。
   - 共同編集では、フィールドごとの後勝ちのまま（フィールドの説明も、そのフィールドの `Y.Map` に入れる）。
   - KokoState の宣言ファイルを作るとき、説明を JSDoc として書き出す。これで、コードホバーと入力の候補に、そのまま出る。説明の文の中の `*/` は、JSDoc が途中で終わらないように置き換える。
   - `e.get(Gun)` の型は、宣言の型を `FieldsOf<K>` で取り出して作っている。取り出したあとのフィールドにも JSDoc が残るかを H0 で試し、残らなければ宣言の書き方を変える。
   - ライブラリでは、KokoState の定義と一緒に配られるので、説明も付いていく。
   - 「リソースの詳細」で、KokoState とフィールドの説明を書ける。
   - 公式ライブラリと同梱サンプルの KokoState に、説明を書く。
   - AI エージェントの、KokoState を作る・変える道具（`create_kokostate`・`update_kokostate`）に、KokoState とフィールドの説明を足す。
7. **空間に置いたパネルでも、コードホバーと候補を、重ねた文字の所に出す。** CodeMirror の枠の置き方と、`editorCoords.ts` の座標の直し方を合わせる。H0 で確かめる。
8. **大きな判断は ADR に残す。**
   - 新しい ADR に、次のことを書く。
     - Worker への頼みの形と、古い答えを捨てる決まり
     - 自前の Host API の候補をやめること
     - 定義へ移動の行き先
     - 説明の持ち方
   - 番号は、PR を出す直前に、最新の次の番号を確かめて付ける。

## 確かめ方

- 単体テスト
  - `TypeChecker` が、変数・Host API・KokoState のフィールドの場所で、型と説明を返すこと
  - `e.get(Gun).` の場所で、Gun のフィールドを候補として返すこと
  - `Gun` の定義の場所が、Gun の宣言ファイルになること
  - 一つのファイルを差し替えたあとに、新しい内容で答えること
  - 型の確かめの途中でも、場所を聞く頼みに答えること
  - 説明に `*/` が入っていても、宣言ファイルが壊れないこと
  - KokoState とフィールドの説明が、宣言ファイルの JSDoc になり、Quick Info に出ること
- 背骨の E2E：H3 と H6 のあとに流す（m1 はエディタでスクリプトを書くため）。
- 画面：画面に出したパネルと空間に置いたパネルで、コードホバー・候補・定義へ移動を、使い捨てのスクリプトのスクリーンショットで確かめる。2 人で同じスクリプトを書き換えている最中に、古い答えが出ないことも確かめる。

## 構想から変えたこと

- 計画者と相談して、AI エージェントも、今ある KokoState を作る・変える道具で、KokoState とフィールドの説明を書けるようにした（型を聞く新しい道具は、構想のとおり渡さない）。
- 計画者と相談して、定義へ移動の操作を、コードホバーの中の「定義へ移動」と Ctrl・Cmd ＋ クリックにした。F12 はブラウザの開発者ツールとぶつかるので使わない。

## 分かったこと・残り

- 2026-11-14：ADR 0079 に実装方針を記録した。フィールドの JSDoc は `FieldsOf<K>` を通しても残るため、型の取り出し方は変えなかった。
- ライブラリの KokoState にも既存の詳細画面を使える。ただし編集可能と判定される箇所があったため、閲覧専用に直した。ライブラリの型の定義も閲覧専用のコードエディタで開く。
- 3D パネルのエディタ本体とスクロール枠で座標の原点が違うと、候補の上側が切れたり、枠が画面外に隠れたりする。ホバー・候補と同じ原点で測るようにした。
- Chrome・Edge・Firefox で、2D と 3D のホバー、説明の編集反映、候補の表示とクリック選択、Ctrl＋クリックを確認した。3D のホバーはパネルを斜めにした場合も確認した。
- Safari・Mac 実機での Cmd＋クリックは未確認。Windows 版 Playwright の WebKit は既存の `AudioContext` 初期化で画面を開けず、代わりの検証にも使えなかった。H0 はこの確認を残している。
- 背骨の E2E は 4 本とも成功した。H3 の候補変更に伴う既存シナリオの修正は不要だった。
- 初回の Worker 読み込みを遅らせて「読み込み中」の表示を確認した。2 人が同じスクリプトを開き、片方が型を変えると、もう片方の古いホバーが消えて、新しい型を表示することも確認した。
