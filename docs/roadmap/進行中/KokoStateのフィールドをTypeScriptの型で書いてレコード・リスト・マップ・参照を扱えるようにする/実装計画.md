## 作り方の方針

### 今の仕組み（調べた結果）

- フィールドの型は、決まった名前の一覧（`FieldType`。`number`・`boolean`・`string`・`vec3`・`color`・`entity`・`texture`・`material`・`model`・`audio`）から選ぶ。型と値の対応は `packages/eks/src/types.ts` の `FieldValueMap` にある。参照の「なし」は `null`。
- 型の一覧から、次のものがそれぞれ型ごとの `switch` や `if` で作られている。
  - スクリプトの型の宣言（`packages/typecheck/src/declarations.ts` の `fieldTsType()`）
  - 実行で値を受け入れるかの確かめ（`packages/runtime/src/simulation.ts` の `accepts()`）
  - Inspector の入力（`apps/client/src/workspace/FieldInput.tsx`）
  - エージェントの値の確かめと説明（`apps/server/src/agent/tools.ts`）
  - 依存グラフ・抽出・参照の診断で、フィールドが指すマテリアル・素材・Entity をたどる所（`packages/repo-model/src/dependencyGraph.ts` など。ADR 0051）
- 値は、どこでもふつうの JSON として扱っている。
  - Git：1 要素 1 ファイルの JSON（`packages/repo-model/src/files.ts`）
  - 共同編集：Yjs。Entity の値はフィールドごとの `Y.Map` に入っていて、フィールドごとの後勝ちになっている。KokoState の定義は、定義まるごとが一つの値（`kokostates: Y.Map<KokoStateDef>`）
  - 通信：`JSON.stringify` した WebSocket
  - スクリプトの実行環境（QuickJS）との受け渡し：`JSON.stringify` と `JSON.parse`（`packages/script/src/sandbox.ts`）

### 方針

1. **値の形を先に広げる。** `undefined`・`Date`・`Map`・`Set`・`bigint`・`NaN`・`Infinity`・`-Infinity` を表せる「値」の形と、その書き出し・読み込みを一つ作り、Git・共同編集・通信・スクリプトの実行環境との受け渡しのすべてで使う。
   - 形式は T0 で決める。候補は superjson・devalue・独自の形式。決めるときに見ること：
     - QuickJS の中でも同じ書き出し・読み込みが要るので、小さく、依存なしで動くか
     - Yjs に入れられる形にできるか
   - 今の参照の「なし」（`null`）は `undefined` にする（プロトタイプなので、保存の形は変えてよい）。
2. **フィールドの型を「TypeScript の型の文」にする。**
   - `FieldDef.type` を、決まった名前から TypeScript の型の文（例：`Card[]`、`Record<string, Piece>`）に変える。
   - 今の型は、Tukurium が用意する型の名前で表す（例：`number`、`Vec3`、`Color`、`EntityRef`、`TextureRef`）。名前は T0 で決める。
   - 型の宣言は、フィールドの型の文をつないで作る（`fieldTsType()` の代わり）。
   - Built-in の KokoState・公式ライブラリ・同梱サンプルの定義も、新しい形に書き直す。
   - 初期値は、型とは別にフィールドに持ち、値の形式で書く。スキーマで型に合うかを確かめる。
3. **型は TypeScript で読み解き、値の確かめは「値の形の決まり」で行う。**
   - TypeScript の本体で、フィールドの型の文を読み解く。結果は、値の形の決まり（数・文字・選択肢・レコード・リスト・マップ・参照などを入れ子で表したもの。スキーマ）に変える。
   - 値の確かめ（保存・読み込み・実行での書き込み・Inspector・エージェント）は、このスキーマで行う。値ごとに TypeScript を動かすと重すぎるため。
   - 保存できない型（関数・クラスなど）は、スキーマに変えられないので、型エラーにする。
   - スキーマを作る所（ブラウザの裏側の Worker とサーバー）と、使う所（実行のホスト・Inspector）の間の受け渡しは、T0 で確かめて決める。TypeScript の本体は大きく、ブラウザでは使うときに読み込むので、再生を始める速さが落ちない受け渡しにする（例：作ったスキーマを制作データと一緒に持つ）。
   - フィールドの型に型エラーがあって、スキーマを作れないときも、再生は止めない（ADR 0010）。そのフィールドの値をどう扱うか（確かめずに通す、初期値を使う、など）は T0 で決める。
   - 依存グラフ・抽出・参照の診断は、スキーマを使って、入れ子の中の参照もたどる。
4. **型エラーの場所はフィールドにする。** フィールドの型の文の型エラーは、問題の場所を「KokoState のフィールド」（今の `property` の場所）にして、そのフィールドに出す。ほかのフィールドは使える。
5. **KokoState の定義もフィールドごとの後勝ちにする。** 共同編集の形を、定義まるごとの値から、フィールドごとの `Y.Map` に変える。フィールドの並びの持ち方も決める。
6. **型の定義は新しいリソースの種類にする。**
   - `.d.ts` の形で書き、Git には `types/<ID>.d.ts` で保存する。
   - 論理パスと ID はほかのリソースと同じ扱い（ADR 0010）。型の確かめでは、論理パスに合わせた仮想のファイルにする。
   - フィールドの型の文から、型の定義の型を使えるようにする。どの型の定義を使うかは KokoState が ID で持ち、名前の変更や移動に合わせて宣言を作り直す。
7. **参照は Tukurium が用意する型にする。**
   - Entity についた KokoState の参照（例：`KokoStateRef<Health>`）と、フィールドの参照（例：`FieldRef<number>`）を足す。
   - 参照先から読み書きする Host API を足す。そのときは `HOST_API_SPEC` と `HOST_CAPABILITIES` にも足す（ADR 0012）。
   - 参照先が消えたら、参照の問題として出す。
8. **大きな判断は ADR に残す。** 新しい ADR（0061 の予定）に、次のことを書く。
   - 値の形式
   - 型の文とスキーマの分け方
   - Tukurium が用意する型の名前
   - `null` をやめること
   - 型の定義のリソース
   - 定義のフィールドごとの後勝ち
   - ADR 0051（リソースを指すフィールドの型）を、どう置き換えるか
9. **通信の形が変わる。** 値の形を広げると、ワークスペースとセッションの通信も変わるので、`PROTOCOL_VERSION` を上げる。

## 確かめ方

- 単体テスト
  - 広げた値（`undefined`・`Date`・`Map`・`Set`・`bigint`・`NaN`・`Infinity`）が、次のそれぞれで元どおりに戻る：Git のファイル、Yjs、通信、QuickJS との受け渡し
  - 型の文からスキーマを作れる。保存できない型が型エラーになる
  - スキーマで値を確かめ、合わない値が問題になる
  - 型の定義の名前を変えても、使っている所が切れない
  - 型の定義を変えたときに、すでにある値が決まりどおりに合わせられる
  - 参照から読み書きでき、参照先が消えると問題になる
  - 定義の別のフィールドを同時に変えても、両方残る
- 背骨の E2E：T1・T2・T7 のあとに流す（値の形と型の持ち方が変わるため）。
- 画面：Inspector で入れ子の値と参照を直す様子を、使い捨てのスクリプトのスクリーンショットで確かめる。
