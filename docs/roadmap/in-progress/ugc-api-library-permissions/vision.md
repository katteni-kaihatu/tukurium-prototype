# UGC API・権限・Library Package

- 計画する人：れにうむ
- 書き上げた日：2026-11-05

## やりたいこと

別々の作者が作った Item・World・Player が、互いの中身を壊さずにやり取りできる。公式のものも利用者のものも、同じライブラリの仕組みで部品として使える。

- KokoState を、入力・一度の出来事・ホストの機能の受け渡しの万能な手段にしない。
- System から物理・入力・音・効果・World の操作に触れる Host API を、型・検証・権限のある一つの入口にまとめる。
- 呼ぶ側の権限と、相手の Item・World が外へ公開する操作を分ける。
- 相手の中の Entity・KokoState は見せず、当たり判定・表面・一時的な効果・公開 Contract だけを使えるようにする。
- 安定した ID・バージョン・依存・要る権限を持つ、最小の Library Package を作る。
- 権限が足りない、依存が見つからない、API のバージョンが合わない、といったことを問題として知らせる。

## 原則とのつながり

- 原則 4（一度作ったものを、何度でも、誰とでも使える）：中身を知らなくても、ほかの人の作ったものを部品として組み合わせられる。公式も同じ仕組み。
- 原則 5（安心して作れる）：ほかの人の作品が、自分の作品の中身を勝手に変えられない。
- 原則 3（作品を通じて一緒に作れる）：ライブラリを通じて、その場にいない人の作ったものを使える。

## やること

実装計画の U0〜U5。

## やらないこと

- ライブラリのマーケットのランキング・評価・コメント・収益化・自動推薦
- npm のパッケージをそのまま動かすこと
- UGC から DOM・`fetch`・Three.js・Rapier・ブラウザの API に直接触れること
- 自動で最新のバージョンへ追従する依存
- どんなジャンルも覆う、巨大な公式 KokoState の集まり
- 別の World の中の状態へ、暗黙に届く検索の API
- サーバーでの判定（ロードマップの server-authority）
- 利用者の間でライブラリを配ること（ロードマップの library-sharing）
- API を preview・stable に上げる判断（ADR 0019）

## 完了の条件

実装計画の「元の計画」8 節（最初の受け入れ条件）を満たす。

## 決まっていること・決まっていないこと

- 決まっていること：権限は置いた物（Placement）に与える。今は協調セッションに限る。境界はセッションに置いた World ごと。非公開の対象は「見つからない」。
- 実装する人に任せること：U5 の画面の細部。
- 計画する人に聞くこと：特になし。
