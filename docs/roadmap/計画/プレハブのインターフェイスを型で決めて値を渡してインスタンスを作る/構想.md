# プレハブのインターフェイスを型で決めて値を渡してインスタンスを作る

- 状態：作成中
- 計画者：れにうむ
- 作成完了日：

## やりたいこと

プレハブが持つ形（いちばん上の Entity と子の Entity が、どの KokoState とフィールドを持つか）を、TypeScript の型（インターフェイス）で決められる。そのうえで、プレハブそのものを、インターフェイスで型の付いた値として受け取れる。

- KokoState のフィールドや System の中で、「駒のインターフェイスを満たすプレハブ」を、型の付いた値として持てる（例：`Prefab<Piece>`）。ポーンもクイーンも、同じ型の値として入れられる。
- そのプレハブから、実行中にインスタンスを作れる。作るときに、初めの値を上書きするデータを、型の付いた形で渡せる（例：`world.spawn(弾, { 向き, 速さ })`）。

ロードマップの「プレハブのリストから子を組み立てる」は、この型と、値を渡す形を使って、リストの中のプレハブを切り替える。

プレハブには、二つの役割がある。

- 編集中：同じものを楽に管理する（置いて使い回し、まとめて直す）。
- 実行中：動的に変わるもの（作る・消す・切り替える）を、安全に扱う。

この項目は、実行中の役割の土台になる。

## 原則とのつながり

- 原則 4（一度作ったものを、何度でも、誰とでも使える）：同じインターフェイスを満たすプレハブを、入れ替えて使える。
- 原則 5（安心して作れる）：どのプレハブが入るか、どの値を渡せるかが、型で確かめられる。

## やること

- **プレハブのインターフェイス**：TypeScript の型で、プレハブが持つ KokoState とフィールドの形を書ける。いちばん上の Entity だけでなく、子の Entity の形も含める。インターフェイスは、どのプレハブも指さずに、構造だけを書く。
- **プレハブを型として受け取る**：プレハブを、インターフェイスで型の付いた値として扱える（例：`Prefab<Piece>`）。KokoState のフィールドの型にも書ける。プレハブがインターフェイスを満たしているかは、型で確かめる。
- **import**：
  - KokoState と型の定義のリソースは、プレハブの型（インターフェイスや、プレハブの形）を import して使える。
  - System は、プレハブ・マテリアル・3D モデルなどのリソースの参照を、値として import できる（例：`import 弾 from "./弾.prefab"` のあとに `world.spawn(弾, …)`）。
  - フィールドの値や import で指したプレハブも、マテリアルや素材の参照と同じく、依存グラフ・抽出・ライブラリで一緒にたどる。
- **値を渡してインスタンスを作る**：スクリプトから、プレハブのインスタンスを実行中に作れる（例：`world.spawn(弾, 上書きの値)`）。
  - 第二引数に、プレハブの形に合った「上書きの値」を渡すと、初めの値を上書きして作る。
  - 上書きの値の形は、プレハブ（またはインターフェイス）の形から型で決まる。合わない値は型エラーになる。
  - 上書きの値のデータの形は、ロードマップの「プレハブのリストから子を組み立てる」でも使う。
- 作ったインスタンスは、すぐに現れる。同じフレームのあとの処理からも見える。
- 実行中に作ったインスタンスは、どのプレハブから作ったかを、実行中も持ち続ける（リストで切り替えるため）。
- 実行中に作ったプレハブが System を持っていて、その System がまだ動いていなければ、動いている再生に足す（プレハブの System は、アウトプットの System に足し合わせる。ADR 0076）。セッションでは、足した System の権限も、今と同じくコードから読み取って確かめる（ADR 0012）。
- AI エージェントも、人と同じく、インターフェイスを書き、プレハブを型の付いた値として扱える。

## やらないこと

- 制作データに置いたインスタンスを、別のプレハブに切り替えること（プレハブを使い回すだけの使い方で、参照に制限がかからないように）。切り替えは、リストで実行中に作ったインスタンスだけ（ロードマップの「プレハブのリストから子を組み立てる」）。
- プレハブに振る舞い（そのインスタンスだけに働く System）を持たせること。
- スクリプトから、インターフェイスを使って Entity を探したり読み書きしたりすること（例：`query: { prefab: Piece }`、`e.child("見た目").get(Mesh)`）。必要になったら、別のロードマップの項目にする。
- 名前と KokoState を文字で指定して作る、今の `world.spawn` をやめること（ロードマップの「実行中に現れるものをプレハブで決めて静的に安全にする」で扱う）。この項目の始めに、静的に危ない Host API と書き方すべてに `@deprecated` と理由を付ける（代わりの書き方がまだないものは「追加予定」と書く。ロードマップの「実行中に現れるものをプレハブで決めて静的に安全にする」の「危ないものに印を付ける」）。今の書き方は、並べて使えるまま残す。

## 完了の条件

- 弾のプレハブと、そのインターフェイスを書き、`world.spawn(弾, { 向き, 速さ })` で、値を上書きしてインスタンスを作れる。形に合わない値を渡すと型エラーになる。弾のプレハブが持つ System が、アウトプットに弾のインスタンスがなくても、作った弾で動く。
- 駒のインターフェイスを書き、ポーンとクイーンのプレハブがそれを満たす。満たしていないプレハブは型エラーになる。
- KokoState のフィールドに `Prefab<Piece>` の型を書き、ポーンもクイーンも入れられる。インターフェイスを満たさないプレハブは入れられない。

## 決まっていること・決まっていないこと

- 決まっていること：
  - インターフェイスは TypeScript の型で書き、子の Entity の形も含める。
  - プレハブを、インターフェイスで型の付いた値として受け取れる。
  - 実行中にインスタンスを作るとき、第二引数で、型の付いた上書きの値を渡せる。この形はリストでも使う。
  - 切り替えは、リストで実行中に作ったインスタンスだけ。制作データに置いたインスタンスは切り替えない。
  - インターフェイスは、プレハブを指さずに構造だけを書く。KokoState と型の定義はプレハブの型を import でき、System はプレハブ・マテリアル・3D モデルの参照を import できる。
  - AI エージェントも同じことができる。
- 設計者・実装者に任せること：インターフェイスの書き方（型の定義のリソースに書くか）、`Prefab<I>` の型の名前。
- 計画者に聞くこと：
  - 上書きの値のデータの形（計画者がこれから考える）。
