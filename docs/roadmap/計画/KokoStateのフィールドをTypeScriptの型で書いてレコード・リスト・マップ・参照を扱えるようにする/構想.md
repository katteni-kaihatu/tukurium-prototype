# KokoStateのフィールドをTypeScriptの型で書いてレコード・リスト・マップ・参照を扱えるようにする

- 状態：完了
- 計画者：れにうむ
- 作成完了日：2026-11-10

## やりたいこと

KokoState のフィールドの型を、TypeScript の型の書き方で書けるようにする。これで、数や文字や `vec3` だけでなく、レコード（いくつかのフィールドの組）・リスト・マップ、Entity についた KokoState の参照、Entity についた KokoState のフィールドの参照を持てる。Inspector と System の両方で扱え、入れ子の値も型を確かめたうえで保存・復元できる。

たとえば、チェスの盤（マスの名前から駒へのマップ）、トランプの手札（カードのレコードのリスト）、「的 3 の `Health.hp`」を出すゲージを、フィールドを並べる工夫なしに作れる。スクリプトと同じ TypeScript の書き方なので、覚えることが一つで済む。

## 原則とのつながり

- 原則 2（入口は低く、奥は深い）：簡単な型は今のように選んで作り、込み入った型は TypeScript で書ける。
- 原則 4（一度作ったものを、何度でも、誰とでも使える）：名前を付けた型を、いくつもの KokoState で使い回せる。
- 原則 5（安心して作れる）：入れ子の値も型で確かめるので、壊れた値が保存されない。

## やること

### KokoState の定義の形

KokoState の定義は、今と同じ Tukurium の形式のままにする。フィールドごとに、ID・名前・型・初期値・「維持」の印などを持ち、**型だけを TypeScript の型の書き方で書く**。内部では、フィールドの型をつないで KokoState の宣言を作る。

```
KokoState「Hand」
  フィールド cards（ID f_cards）  型：Card[]                           初期値：[]
  フィールド owner（ID f_owner）  型：KokoStateRef<Player> | undefined  初期値：undefined
  フィールド hpRef（ID f_hp）     型：FieldRef<number>                 初期値：（必ず指す）   維持
```

（型の名前 `KokoStateRef`・`FieldRef` は例。決めるのは設計者）

- フィールドは今と同じく ID で結び付くので、名前を変えても、保存した値・「維持」・参照は切れない。
- 型エラーは、そのフィールドに出る。ほかのフィールドは使える。

### 書ける型

**TypeScript の型のとおりに決まる。ただし、保存できる型に限る。** 空にできるか、省略できるかも、型の書き方で決まる（例：`Card[]` は空でよい、`joker?: boolean` は省略できる、`| undefined` があれば「なし」にできる）。

| 種類 | 書き方の例 |
| --- | --- |
| 数・文字・真偽 | `number`、`string`、`boolean` |
| 選択肢 | `"pawn" \| "knight" \| "bishop"` |
| レコード | `{ suit: string; rank: number; joker?: boolean }` |
| リスト | `Card[]` |
| マップ | `Record<string, Piece>`、`Record<"white" \| "black", number>` |
| 入れ子 | `Record<string, Card[]>` など |
| 日時 | `Date` |
| `Map`・`Set` | `Map<EntityRef, number>`、`Set<string>`（キーや要素に、文字以外も使える） |
| 大きな整数 | `bigint` |
| Tukurium が用意する型 | 色、`vec3`、素材（テクスチャ・マテリアル・モデル・音声）の参照、Entity の参照、Entity についた KokoState の参照、Entity についた KokoState のフィールドの参照 |

- 「なし」は `undefined` で表す。`null` は使わない。
- `undefined`・`Date`・`Map`・`Set`・`bigint`・`NaN`・`Infinity`・`-Infinity` も保存できる（下の「保存の形」）。
- 関数・クラスなど、保存できない型は書けない。書いたときは型エラーとして出す。どの型が保存できるかは、TypeScript の型の確かめで調べる。
- 型を確かめるのは、ロードマップの「スクリプトをすべてTypeScriptで書く」で入れた TypeScript の本体（ブラウザの裏側と、サーバー）を使う。

### 保存の形

- 値は、JSON を広げた形で保存する。JSON では表せない `undefined`・`Date`・`Map`・`Set`・`bigint`・`NaN`・`Infinity`・`-Infinity` も、そのまま保存・復元できる。
- 形式は設計者が決める。候補：superjson、devalue などのすでにある形式、または Tukurium の独自の形式。

### 参照

- **Entity についた KokoState の参照**：Entity と KokoState の組（例：「的 3 の `Health`」）。指せる KokoState を型で決める（例：`Health` だけを指せる）。
- **Entity についた KokoState のフィールドの参照**：Entity・KokoState・フィールドの組（例：「的 3 の `Health.hp`」）。指せるフィールドの型を決める（例：数のフィールドだけを指せる）。
- どちらも名前ではなく ID で結び付ける。名前を変えても切れない。
- 参照している Entity・KokoState・フィールドが消えたときは、値を残して、問題として出す（今のリソースの参照が切れたときと同じ）。
- 参照からほかの Entity の値を読み書きするときも、今の `world.get()`・`world.set()` と同じ権限の決まりに従う。

### 名前を付けた型（型の定義）

- `Card` のような名前を付けた型を、**型の定義**のリソースに書く。中身は `.d.ts` と同じく、型と宣言だけ（`type` と `interface`）。Git には `.d.ts` のファイルとして、リソースの ID の名前で保存する。
- 保存できる型だけを書けるようにする（`declare function` などは型エラーにする）。
- フィールドの型から、型の定義の型を使える。型の定義のリソースの名前を変えたり動かしたりしても、使っている所が切れないようにする（スクリプトの import と同じ）。
- 型の定義を変えたとき、すでにある値は次のように扱う：足したフィールドは初期値で埋める、消したフィールドは捨てる、型が変わったフィールドは問題として出す。
- 型の定義は、まずエディタで TypeScript として書く。専用の画面は、ロードマップの「TypeScriptで書いた型を画面で作って直せるようにする」で作る。

### 初期値

- 初期値は、型とは別にフィールドに持つ。保存の形と同じ書き方で書き、型に合うかを TypeScript で確かめる。

### Inspector

- 型は、今のように一覧から選ぶか、TypeScript で直接書く（TypeScript で書くモード）。込み入った型は、まず TypeScript で書くモードで表す。
- 入れ子の値を、見る・足す・消す・並べ替える・直すことができる。参照は、Entity・KokoState・フィールドを選んで決める。
- 専用の画面がまだない型の値は、保存の形と同じ書き方の文字で直す。型に合わない値は、保存の前に型エラーとして出す。

### System

- 型の付いた値として読み書きできる。レコードのフィールドの名前の打ち間違いや、リストに違う型の値を入れたことは、型エラーとして出る。
- `Date`・`Map`・`Set`・`bigint`・`undefined` も、そのままの値として読み書きできる。
- 参照から、その KokoState やフィールドの値を読み書きできる。

### 保存・復元・共同編集

- 保存・復元のときに、入れ子の値の型を確かめる。合わない値は問題として出す。
- 共同編集は、フィールドごとの後勝ちにする。別のフィールドを 2 人が同時に変えれば両方の変更が残り、同じフィールドを同時に変えれば（入れ子の中の別の要素でも）あとから変えた人の変更が残る。KokoState の定義でも、フィールドごとに後勝ちにする。
- 「維持」を付けた入れ子のフィールドは、適用したあと、フィールドをまるごと引き継ぐ。

## やらないこと

- KokoState の定義そのものを `.ts` のファイルで書くこと（フィールドの ID・初期値・「維持」を持てず、画面での編集や共同編集とぶつかるため）。
- 型の引数を持つ KokoState（`Deck<T>` など）。ロードマップの「型を指定してKokoStateのテンプレートを使う」で扱う。
- Entity を決めない、KokoState とフィールドの組だけの参照。
- `null`。Host API に残っている `null`（拒んだときの値など）を `undefined` に直すことは、別の作業で行う。
- 入れ子の中の要素ごとに、共同編集の変更を残すこと。
- 入れ子の中の一部だけに「維持」を付けること。
- 込み入った型や型の定義を、TypeScript で書かずに画面で作ったり、その値を専用の画面で直したりすること。ロードマップの「TypeScriptで書いた型を画面で作って直せるようにする」で扱う。

## 完了の条件

- Inspector で、チェスの盤（`Record<string, Piece>`）とトランプの手札（`Card[]`）のフィールドを作り、値を直し、保存して開き直すと元どおりに戻る。
- `undefined`・`Date`・`Map`・`Set`・`bigint`・`NaN`・`Infinity` を値に持つフィールドが、保存して開き直しても元どおりに戻る。
- 型の定義に `Card` を書き、二つの KokoState のフィールドで使える。型の定義の名前を変えても、使っている所が切れない。
- System から盤と手札を読み書きでき、レコードのフィールドの名前の打ち間違いが型エラーとして出る。
- ゲージの KokoState に「的 3 の `Health.hp`」の参照を持たせ、System からその値を読める。数のフィールドだけを指せる参照に、文字のフィールドを選べない。参照先を消すと、問題として出る。
- 保存できない型（関数など）を書くと、型エラーとして出る。
- 型の合わない値を保存しようとしたとき、または読み込んだときに、問題として出る。
- 2 人が同じ KokoState の定義の別のフィールドを同時に変えても、両方の変更が残る。
- 「維持」を付けた入れ子のフィールドが、適用したあとも値を保つ。

## 決まっていること・決まっていないこと

- 決まっていること：
  - KokoState の定義は Tukurium の形式のままにし、フィールドごとに型を TypeScript の書き方で書く。
  - 書ける型は TypeScript の型のとおりで、保存できる型に限る。空にできるか、省略できるかも型で決まる。
  - 「なし」は `undefined` で表し、`null` は使わない。
  - `undefined`・`Date`・`Map`・`Set`・`bigint`・`NaN`・`Infinity`・`-Infinity` も保存できる。保存の形は、JSON を広げた形式にする（どの形式にするかは設計者が決める）。
  - 色・`vec3`・参照などは、Tukurium が用意する型で書く。
  - 型を確かめるのは、TypeScript の本体。
  - 名前を付けた型は、型の定義のリソースに `.d.ts` の形（`type` と `interface`）で書く。
  - 初期値は型とは別に持つ。
  - 参照は、Entity についた KokoState の参照と、Entity についた KokoState のフィールドの参照の 2 つ。どちらも指せるものを型で決める。参照先が消えたら、値を残して問題として出す。
  - 共同編集は、フィールドごとの後勝ち。KokoState の定義も同じ。
  - 「維持」は、フィールドをまるごと引き継ぐ。
  - 型の定義を変えたとき：足したフィールドは初期値で埋める、消したフィールドは捨てる、型が変わったフィールドは問題として出す。
  - 込み入った型と型の定義は、まず TypeScript で書く。専用の画面がない型の値は、保存の形と同じ書き方の文字で直す。画面で作れることは、別の項目で増やしていく。
- 設計者・実装者に任せること：
  - 保存の形に使う形式（候補：superjson・devalue などのすでにある形式、または独自の形式）。
  - Tukurium が用意する型の名前と書き方。
  - 省略できるフィールドの書き方（`?:` と `| undefined`）の扱い。
  - 入れ子の深さ、リストやマップの大きさの上限。
  - 今ある KokoState のフィールドの型（一覧から選んだもの）と、今の Entity・素材の参照の「なし」（今は `null`）を、新しい形でどう表すか。
  - スクリプトの実行環境との間で、`Date`・`Map`・`Set`・`bigint`・`undefined` をそのまま渡す方法。
- 計画者に聞くこと：なし。
