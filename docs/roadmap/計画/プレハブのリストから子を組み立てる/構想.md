# プレハブのリストから子を組み立てる

- 状態：完了
- 計画者：れにうむ
- 作成完了日：2026-11-16

## やりたいこと

プレハブのリストから、Entity の子を実行中に組み立てられる。チェスの駒や合法手のガイドのように、数や中身が状態で変わる子を、一つずつ置かずに作れる。

リストの一つずつには、どのプレハブを使うか（プレハブ型の値）と、そのプレハブのパラメータに渡す値を持つ。実行中に、リストの中のプレハブを替えると、同じ子のインスタンスのまま、別のプレハブに切り替わる。たとえば、チェスでは、駒のプレハブ「駒」と、そのバリアント「ポーン」「クイーン」を作り、リストの型を「駒」のプレハブ型にする。ポーンが成ってクイーンになるとき、駒を消して作り直さずに、同じ駒のまま切り替える。ここが Unity のプレハブと違う所。

## 原則とのつながり

- 原則 2（入口は低く、奥は深い）：盤面やリストの表示を、短い決まりで組み立てられる。状態に合わせて中身が変わるものを、作り直しの手間なしに作れる。
- 原則 4（一度作ったものを、何度でも、誰とでも使える）：駒などのプレハブを、リストで何度も使える。

## やること

### リスト

- リストで受け付けるプレハブを、プレハブ型で決める（例：「駒」のプレハブ型なら、「駒」と、パラメータの合うバリアント「ポーン」「クイーン」）。構造で当てはまるインターフェイス型は、ロードマップの「インターフェイス型でプレハブの構造を決めて入れ替えて使う」で、あとから使えるようにする。
- リストの一つずつは、次のものを持つ。
  - 使うプレハブ（リストの型に当てはまる、型の付いた値）
  - 置く場所・向き・大きさ
  - パラメータに渡す値（ロードマップの「プレハブを型で扱ってコードからインスタンスを作る」の、`Prefab.spawn` と同じ渡し方）。型で確かめられるので、安全に渡せる。
- **リストと子の関係**：リストが決めるのは、子があるか（キー）と、どのプレハブか。置き方とパラメータの値は、子を作るときと切り替えるときの初めの値として使う。そのあとは、子が自分の値を持ち、System が自由に変えられる。
- リストは、KokoState のフィールドの値（リスト）から、安定したキーで子を足す・直す・消す。チェスの駒と合法手のガイドは、これで作れる。
- リストを使うのは、データに合わせて切り替えたり、動的に変わったりするものを表すとき。同じものを並べて置くだけなら、制作データにインスタンスを置く（プレハブの編集中の役割）。

### 実行中の子

- リストから作った子は、実行中に作ったインスタンス。保存せず、再生のたびに作り直す。
- Inspector と Hierarchy では見えるだけで、直すことはできない。

### 切り替え

- 同じキーの子で、使うプレハブが替わったら、消して作り直さずに、同じインスタンスのまま別のプレハブに切り替える。切り替えは、リストが変わったその場ですぐ行う。System に Entity を渡す前に、実行環境が、まだ Query に合うかを確かめる（ロードマップの「プレハブを型で扱ってコードからインスタンスを作る」の実行の仕組み）。切り替えられるのは、リストの型に当てはまるプレハブどうし（そのプレハブと、パラメータの合うバリアント）。
- 切り替えたとき：
  - Entity（ID）と、キーは残る。ほかの Entity からの参照も切れない。
  - **切り替えは、バリアントの差分を入れ替えることで行う。** バリアントは、元のプレハブ（リストの型のプレハブ）との差分（上書きした値と、足した KokoState・子の Entity）を持つ。切り替えるときは、前のバリアントの差分を取り除いて元のプレハブの形に戻し、新しいバリアントの差分で上書きする。
    - バリアントが何段か重なっているときは、リストの型のプレハブから、そのバリアントまでの差分をまとめて一つの差分として扱う。
    - フィールドごとに、次の順で値を決める（上ほど強い）。
      1. **パラメータ**：リストでパラメータに渡しているフィールドは、リストの値にする。
      2. **「維持」**：「維持」を付けたフィールドは、差分にあっても、実行中の値を残す。「維持」を付けるかは、元のプレハブ（リストの型のプレハブ）で決まり、バリアントでは変えられない（ロードマップの「プレハブの一部を上書きしてバリアントを作る」）。
      3. **バリアント固有の値**：新しいバリアントの差分にあるフィールドは、新しいバリアントの値にする。前のバリアントの差分にだけあるフィールドは、実行中に値が変わっていても、差分として取り除いて元のプレハブの値にする。
      4. **どちらの差分にもないフィールド**（元のプレハブのままのもの。例：位置、「動いた回数」）は、実行中の値を残す。
    - 並び順と親の上書きも差分として扱い、前のバリアントのものを取り除いてから、新しいバリアントのもので上書きする。
    - 前のバリアントで足した KokoState と子の Entity は消し、新しいバリアントで足したものを、初めの値で足す。
    - 子の Entity の対応は、元のプレハブの中の Entity どうしで決まる。元のプレハブにあるものは、どのバリアントにも必ずある。
  - 参照を持つフィールドも、上の決まりで決まる。残した参照は、元のプレハブにあるもの（どのバリアントにもあるもの）を指すので、切り替えても壊れない。前のバリアントで足した子を指す参照は、壊れることがある（下の「型で守る」）。
  - System は、切り替えに合わせて足したり外したりする。新しいプレハブにしかない System は足し、前のプレハブにしかなかった System は、ほかにそれを使うインスタンスが残っていなければ外す。
- リストのキーと、子の Entity の対応も、ホストが抜けて別の人が再生を引き継ぐときの実行状態に含める。
- 切り替えで消えるものを指す参照は、途中では実行中に壊れることがある。型で守るのは、ロードマップの「実行中に現れるものをプレハブで決めて静的に安全にする」で行う（実行中に作ったインスタンスを指す参照を、いつでも消えうるものとして扱う）。

### 適用

- セッションに出した配置を「適用」で更新するときは、リストから作った子をすべて消し、新しい中身で作り直す（リストのデータは、「維持」の決まりで残る）。
- そのため、リストから作った子のフィールドに付けた「維持」は、適用では効かない（子を作り直すため）。適用で残したい値は、リストのデータに持たせる。いずれ、適用のときも子の「維持」を付けたフィールドの値を戻せるようにしたい。
- 将来は、適用のやり方を選べるようにしたい（今はこの一つだけ）。

### AI エージェント

- AI エージェントも、人と同じく、リストを書き、リストの中のプレハブを替えられる。

## やらないこと

- 入れ子の構成まで状態から組み立てる仕組み（仮想ツリー）。平らなリストで足りない用途が出たら、別に検討する。
- リストから作った子を、Inspector で直すこと。
- 制作データに置いたインスタンスを切り替えること。
- リストの型にインターフェイス型を使い、元の違うプレハブどうしを切り替えること（ロードマップの「インターフェイス型でプレハブの構造を決めて入れ替えて使う」で扱う）。
- 制作データに固定のリストを書き、再生を始めたときに子を作ること（使う場面が少ないため）。

## 完了の条件

チェスで確かめる。

- 「駒」のプレハブ型を受け付けるリストを、盤の KokoState のフィールドの値から作り、駒が並ぶ。合法手のガイドも、同じくリストから作る。
- リストの一つずつに書いたパラメータの値（駒の色など）が、型で確かめられてインスタンスに渡る。形に合わない値は型エラーになる。
- 切り替えで残ったフィールドの参照は、切り替えたあとも、元のプレハブにあるものを指している。
- ポーンが端まで進んで、リストの中のプレハブが、ポーンのバリアントからクイーンのバリアントに替わると、同じ駒のインスタンスのまま切り替わる。
  - Entity の ID とキーは残る。
  - 「駒」のままのもの（位置や「動いた回数」など）は、実行中の値のまま残る。
  - ポーンのバリアントが上書きしていた見た目は、取り除かれて、クイーンのバリアントの見た目になる。
  - クイーンのバリアントで足した KokoState と子の Entity は、クイーンの初期値で足され、ポーンのバリアントで足したものは消える。
  - 「駒」で「維持」を付けたフィールドは、実行中の値のまま残る。
  - クイーンのバリアントにしかない System が動き始め、ポーンが一つも残っていなければ、ポーンのバリアントにしかなかった System は止まる。
- リストから作った駒は、Inspector と Hierarchy で見えるが、直せない。保存されず、再生のたびに作り直される。
- 切り替えたとき、値はパラメータ → 「維持」 → バリアント固有の値 → 実行中の値の順に決まる（パラメータで渡した駒の色はリストの値になり、「維持」を付けたフィールドは実行中の値のまま）。バリアントで変えた並び順と親も入れ替わる。
- 「適用」で更新すると、リストから作った駒はすべて消えて、新しい中身で作り直される。

## 決まっていること・決まっていないこと

- 決まっていること：
  - リストで受け付けるプレハブは、プレハブ型で決める。チェスは、「駒」のバリアントとして「ポーン」「クイーン」を作れば、インターフェイス型なしで作れる。リストの一つずつは、プレハブ・置き方・パラメータの値を持つ。
  - リストから作った子は、実行中のインスタンス。保存せず、Inspector では見えるだけ。
  - 切り替えは、リストの中のプレハブを替えることで行う。切り替えたときの残し方・足し方・消し方・System の扱いは、上のとおり。
  - リストが決めるのは、子があるかと、どのプレハブか。置き方とパラメータの値は、作るときと切り替えるときの初めの値。
  - 切り替えは、前のバリアントの差分を取り除いて元のプレハブの形に戻し、新しいバリアントの差分で上書きする。どちらの差分にもないフィールドは実行中の値を残す。値は、パラメータ → 「維持」 → バリアント固有の値 → 実行中の値、の順に強い。並び順と親の上書きも差分として入れ替える。
  - 適用のときは、リストから作った子をすべて消して作り直す。
  - 途中で危険な所があってもよい。参照を型で守るのは、最後の項目で行う。
  - AI エージェントも同じことができる。
- 設計者・実装者に任せること：リストの書き方、キーの持ち方。
- 計画者に聞くこと：なし。
