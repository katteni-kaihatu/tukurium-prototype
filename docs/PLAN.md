# Tukurium プロトタイプ 実装計画 v0.1

作成日：2026-11-02
入力：[要件整理 v0.1](./requirements-v0.1.md)、デザイン「ツクリウム デザイン」（S3 ワークスペース／編集、プロジェクトページ、プロフィール、リポジトリ新規作成）

この文書は要件書の「11. 実装前に決めること」に対する**提案**であり、確定事項ではない。「提案」「要確認」と書いたものはレビューで変わりうる。

---

## 1. 方針

- **一周を早く回す。** 初版のゴールは「銃と的を共同制作 → 試す → 遊んでいる人がいるセッションへ適用 → コミット → 公開 → 他の人がフォーク／抽出」の一周。各マイルストーンは、その一周の一部を実際に触れる状態で終える。
- **専用実装を作らない。** 銃も的も、利用者が定義した KokoState と Lua の System だけで作る。アプリ側に「銃」のコードは置かない（サンプルは同梱データとして用意する）。
- **デザインは要件より範囲が広い。** デザインに描かれている Issues / Pull requests / Actions / Branches / Webhooks / GitHub リモート / ノードによる System / シェーダー編集 / Projects / スター・フォロワー・草（contribution graph）は**初版では作らない**か、表示だけの枠にとどめる（§7）。
- **後で差し替えやすく。** 実行環境（Lua）、実行の確定役、保存形式は差し替える可能性が高いので、境界にインターフェースを置く。

## 2. 技術選定（提案）

| 領域 | 選定 | 理由・備考 |
| --- | --- | --- |
| 言語 | TypeScript（strict） | 要件どおり |
| パッケージ管理 | pnpm workspaces（モノレポ） | クライアント・サーバー・共有ロジックで型を共有 |
| クライアントビルド | Vite | 起動・HMR が速い |
| 3D 表示 | Three.js（素の API、R3F は使わない） | シーンは EKS の描画 System から命令的に同期する。React の状態と二重管理しない |
| 2D UI（パネル・Web ページ） | React + Zustand | インスペクタ等の UI 量が多い。ページ遷移は React Router |
| 物理・衝突・レイキャスト | Rapier（`@dimforge/rapier3d-compat`、WASM） | 射撃の命中判定、衝突イベントに必要。決定論的でホスト移行時にも扱いやすい |
| ユーザースクリプト | **Lua**（wasmoon = Lua 5.4 の WASM 版。比較対象に fengari） | デザインが「Script (Lua)」を前提にしている。標準ライブラリを絞った専用 VM で動かし、ページの権限で任意 JS を動かさない。命令数フック（`debug.sethook` 相当）で暴走を止める。止まらない場合は Worker ごと停止 |
| コードエディタ | CodeMirror 6 + `y-codemirror.next` | 共同編集（カーソル共有含む）が既製品で済む。Monaco より軽い |
| 共同編集 | **Yjs**（CRDT）＋ 自前 WebSocket サーバー | 競合解決・再接続・プレゼンス（awareness）が既製。ワークスペース単位で Y.Doc を分ければ、権限のない人に**ドキュメントごと配信しない**ことでプライベート作業の非公開を担保できる |
| セッションの実行同期 | WebSocket リレー ＋ **ホスト権威**（提案） | セッションの実行（EKS＋物理＋Lua）はホストのブラウザで動かし、状態をスナップショット／差分で配信。参加者は入力を送る。デザインの「ホスト」「Host migration」と一致 |
| サーバー | Node.js（`ws`、Fastify） | 認証・権限・Yjs 同期・リレー・アセット配信・リポジトリ API |
| 永続化 | SQLite（`better-sqlite3`）＋ ハッシュ名のファイル置き場 | リポジトリ／コミット／作品／ユーザーのメタデータは SQLite、スナップショットとアセットは SHA-256 で内容アドレス化 |
| バージョン管理 | **自前のコミットモデル**（Git は内部で使わない、提案） | コミット＝スナップショット（JSON）＋ 親参照。フォーク／抽出／由来情報を自分たちの粒度で持てる。Git 形式へのエクスポートは将来課題 |
| 本人識別 | 表示名＋ランダムトークン（パスワードなし） | 「最小限の本人識別」。開発・試験用 |
| スキーマ検証 | zod | 通信メッセージ・スナップショット・Lua からの入力検証 |
| テスト | Vitest（単体）、Playwright（E2E、2 ブラウザコンテキストで共同編集を検証） | Playwright はこの環境に導入済み |
| Lint / Format | Biome | 設定が少なく速い |

### 主な判断と代替案

- **Lua ランタイム**：wasmoon は高速だが命令数フックの API 露出に技術検証が要る。fengari は純 JS で `sethook` が素直に使えるが遅い。M0 のスパイクで「無限ループを 50ms 以内に止められるか」「1 フレームあたりの呼び出しコスト」で決める。どちらも駄目なら QuickJS（`quickjs-emscripten`、割り込みハンドラあり）で制限付き JS にする。
- **実行の確定役**：サーバー権威（サーバーで Rapier＋Lua を動かす）はチート耐性・ホスト移行不要の点で優れるが、サーバー実装量と入力遅延が増える。ランタイムを DOM 非依存の共有パッケージにしておき、将来サーバーへ移せるようにする。
- **3D パネル**：
  - 自分のパネルを 3D 表示するとき：`CSS3DRenderer` で実 DOM をそのまま空間に置く（操作可能）。WebGL 物体との前後関係が崩れる制約はプロトタイプでは許容。
  - 他人のパネルの見え方：サーバーから届く**公開用の要約状態**（タイトル、開いている対象名、閲覧権限があれば内容の簡易表示）を Canvas 2D でテクスチャに描き、作業者の前に板として並べる。非公開内容はそもそもクライアントに届かないので漏れない。

## 3. アーキテクチャ概要

```
┌──────────────── ブラウザ（参加者） ────────────────┐
│ React UI（2D パネル / Web ページ）                  │
│   ├ Workspace 編集 ←→ Y.Doc（ワークスペースごと）    │
│ Three.js 描画  ← EKS World（セッション / 編集空間）  │
│ Runtime: EKS + Rapier + Lua VM（ホストのみ実行）     │
└──────────────┬────────────────────────────────────┘
               │ WebSocket（Yjs 同期 / セッションリレー / プレゼンス）
┌──────────────┴──────────── サーバー ───────────────┐
│ 認証・権限チェック（配信前に必ず通す）               │
│ Yjs ドキュメント保持（ワークスペース）               │
│ セッション：参加者・ホスト・配置された実体の台帳     │
│ リポジトリ API：コミット・履歴・作品・フォーク／抽出 │
│ SQLite ＋ 内容アドレスのファイル置き場               │
└────────────────────────────────────────────────────┘
```

### 3 つの「状態」を分ける

| 状態 | 置き場 | 保存 |
| --- | --- | --- |
| 制作データ（編集中） | ワークスペースの Y.Doc | 自動保存（作業途中の復元用。コミットとは別） |
| 制作データ（履歴） | リポジトリのコミット（スナップショット） | 利用者の「コミット」操作のみ |
| 実行状態 | セッションのランタイム World／ワークスペースの再生用 World | 保存しない（初版）。適用時にマーク付きフィールドだけ引き継ぐ |

### 適用（Apply）の流れ

1. ワークスペースで「適用」→ 現在の Y.Doc から対象アウトプットのスナップショットを作る。
2. セッション台帳から、このワークスペースにリンクしている配置された実体を列挙（メインパネルのリンク先一覧と同じもの）。
3. ホストのランタイムが各実体を新スナップショットで作り直す。その際、アウトプットの「状態維持マーク」に載っているフィールドのうち、**フィールド ID と型が一致**するものだけ現在値を引き継ぐ。
4. 失敗（Lua の読み込みエラー等）した実体は旧版のまま残し、エラーをパネルに出す（暫定）。

### 識別子の方針（状態維持のため）

- Entity・KokoState 定義・フィールドは**名前ではなく安定 ID**（作成時に発行）で識別。名前変更しても状態が引き継げる。
- 状態維持マークは `アウトプット ID × Entity ID × KokoState ID × フィールド ID` の組で、アウトプットごとに持つ（同じ KokoState を使う別アウトプットへ波及しない）。
- 互換性（初版）：型が同一なら互換。数値の範囲変更などは互換扱い。型が変わったら非互換で初期値に戻す。

## 4. EKS とスクリプト API（たたき台）

デザインの S3 画面（Query の With / Without、Events、Systems の有効化）に合わせる。

```lua
-- KokoState 定義はインスペクタで作る（データ）。スクリプトは System だけを書く。
-- Gun: { ammo: Number = 12, interval: Number = 0.2, cooldown: Number = 0 }   ← 利用者が定義

return system {
  query = { with = { "Gun", "Transform" }, without = { "Disabled" } },

  on_update = function(e, dt)
    local gun = e.Gun
    gun.cooldown = math.max(0, gun.cooldown - dt)
  end,

  on_input = function(e, ev)          -- ev.action == "fire" など
    local gun = e.Gun
    if ev.action == "fire" and gun.ammo > 0 and gun.cooldown == 0 then
      gun.ammo = gun.ammo - 1
      gun.cooldown = gun.interval
      local hit = world.raycast(e.Transform.position, e.Transform.forward, 100)
      if hit then world.emit(hit.entity, "hit", { damage = 1 }) end
      audio.play("shot.ogg", e)
    end
  end,
}
```

- 実行順：アウトプットの Systems 一覧の並び順（デザインの「SYSTEMS」設定）。
- イベント：`on_update` / `on_input` / `on_collision` / `on_event`（`world.emit` で送る利用者定義イベント） / `on_spawn` / `on_destroy`。
- 公開 API（初版）：KokoState の読み書き、`world.query` / `spawn` / `destroy` / `raycast` / `emit`、`audio.play`、`log`。これ以外（DOM、ネットワーク、ファイル）は出さない。
- 予算：1 System 呼び出しあたり命令数上限、超過したらその System を停止状態にしてパネルに表示。

組み込み KokoState（Built-in）：`Transform`、`Mesh`（プロシージャル形状＋パラメータ／GLB 参照）、`Material`、`Collider`、`RigidBody`、`AudioSource`、`Player`（入力を受け取る対象）。利用者定義 KokoState と同じ仕組みに載せる。

## 5. プロジェクト構造（提案）

```
tukurium-prototype/
├─ apps/
│  ├─ client/                 # Vite + React + Three.js
│  │  └─ src/
│  │     ├─ app/              # ルーティング、グローバルヘッダー（作る/探す/ライブラリ、セッション表示）
│  │     ├─ pages/            # Web ページ：プロフィール、リポジトリ、リポジトリ新規作成、作品
│  │     ├─ session/          # 3D 空間、FPS 操作、参加者の簡易表示、ポータル
│  │     ├─ panels/           # パネル基盤（2D/3D ピン切替、配置、他人向け要約表示）
│  │     │  ├─ main/          # ワークスペースのメインパネル（再生/一時停止/適用、リンク先一覧）
│  │     │  ├─ hierarchy/ inspector/ resources/ editor/ history/ members/ releases/
│  │     ├─ workspace/        # Y.Doc ⇔ 制作データ、編集空間（境界ボックス、ギズモ）
│  │     ├─ render/           # EKS World → Three.js 同期、アセット読み込み
│  │     └─ net/              # WebSocket クライアント、Yjs プロバイダ
│  └─ server/                 # Node.js
│     └─ src/
│        ├─ auth/ permissions/
│        ├─ sessions/         # 参加・ホスト管理・リレー・配置された実体の台帳
│        ├─ workspaces/       # Yjs ドキュメント、権限付き配信、自動保存
│        ├─ repos/            # コミット・履歴・作品・フォーク／抽出
│        ├─ assets/           # アップロード・内容アドレス保存
│        └─ db/               # SQLite スキーマ・マイグレーション
├─ packages/
│  ├─ shared/                 # 型、通信プロトコル（zod）、権限判定ロジック
│  ├─ eks/                    # EKS コア：World / Entity / KokoState レジストリ / Query / スケジューラ（DOM・Three 非依存）
│  ├─ script-lua/             # Lua VM サンドボックス、API バインディング、予算管理
│  ├─ runtime/                # eks + Rapier + script を束ねる。スナップショット⇔実行、適用と状態引き継ぎ
│  └─ repo-model/             # スナップショットのスキーマ、差分、フォーク／抽出、由来情報
├─ samples/                   # 同梱サンプル（銃・的・射撃場）をデータとして
├─ e2e/                       # Playwright
└─ docs/                      # 要件・計画・決定記録（ADR）
```

依存の向き：`apps/*` → `runtime` → `eks` / `script-lua`、全員 → `shared`。`eks` と `runtime` はブラウザ API を使わない（Node のテストで動かせる、将来サーバー権威へ移せる）。

## 6. ロードマップ

期間は目安（1 人＋エージェントでの順番を示すもので、約束ではない）。各マイルストーン末に要件書 §10 の確認シナリオのどれを満たすかを示す。

### M0：基盤と技術スパイク
- モノレポ、Vite / Node 雛形、Biome、Vitest、CI（GitHub Actions：lint・型・テスト）。
- スパイク（各 1 日程度、結果を `docs/adr/` に記録）：
  1. Lua：wasmoon / fengari で無限ループ停止・呼び出しコスト計測 → 採用決定。
  2. 3D パネル：CSS3DRenderer での操作感、他人向けテクスチャ表示。
  3. Yjs：ワークスペース単位の権限付き配信。
- 完了条件：`pnpm dev` でクライアントとサーバーが起動、空の 3D 空間を FPS 視点で歩ける。

### M1：一人で作って動かす
- EKS コア、Built-in KokoState、プロシージャル形状（球・箱・円柱・平面・カプセル）、マテリアル（色・粗さ・金属感・テクスチャ）。
- 2D パネル：Hierarchy / Inspector / Resources / コードエディタ（Lua）。利用者定義 KokoState の作成（フィールド名・型・初期値）。
- 編集空間（境界ボックス）とワークスペース内の再生・一時停止（Edit mode / Play mode）。
- Rapier によるレイキャスト・衝突イベント、入力アクション。
- 完了条件：一人で銃と的を作り、Play で撃って当てられる。→ シナリオ 4（部分 3）

### M2：みんなでいる・一緒に作る
- サーバー：本人識別、セッション参加、プレゼンス（位置・向きの簡易表示）。
- ワークスペースの Y.Doc 化、共同編集（コードのカーソル共有含む）、自動保存と再接続時の復元。
- パネルの 2D/3D ピン切替、他人の作業パネルが見える。
- 完了条件：2 人が同じワークスペースを編集し、相手のパネルが空間に見える。→ シナリオ 1, 5

### M3：セッションに出して適用する
- 配置された実体（アウトプットからセッションへ出す）、ホスト権威の実行と状態配信。
- メインパネルのリンク先一覧、「適用」、状態維持マーク（フィールド単位）、リセット。
- 1 セッションに複数ワークスペース（銃と射撃場を別リポジトリで）。
- アセット：GLB・画像・音声のアップロードと利用。
- 完了条件：遊んでいる人がいる横で銃を改造し、適用すると残弾だけ保ったまま新しい挙動になる。→ シナリオ 2, 3, 6, 7, 8

### M4：保存・公開・派生
- コミット（メッセージ、Co-author）、履歴表示、差分の一覧。
- 1 リポジトリ複数アウトプット、作品として公開（利用／元データ閲覧／フォーク・抽出の権限）。
- フォーク、抽出（新規リポジトリ／既存リポジトリへの取り込み）、由来情報。
- Web ページ：リポジトリ新規作成、リポジトリページ（ファイル・アウトプット・コミット・開いているワークスペース・リリース）、プロフィール（リポジトリ一覧）。
- 完了条件：作品を公開し、別の人がフォークして自分のワークスペースで作り始められる。→ シナリオ 10, 11

### M5：権限・プライベート作業・ワールド編集
- ワークスペース権限（閲覧・共同編集・管理）をパネル・実物・境界・ポータル・アセット取得すべてに適用。
- プライベート作業：「作業中」だけが見え、内容は配信されない。独立空間での表示・実行。
- ワールドの専用編集空間とポータル、ワールドの出力とセッションへの適用。
- 完了条件：→ シナリオ 9, 12

### M6：通しで試す
- 「銃と的のミニゲーム」で一周を 2〜3 人で通しテスト。E2E を一周シナリオで自動化。
- 使ってみて出た変更の反映、サンプル・テンプレート整備。

## 7. デザインと要件の対応・初版で作らないもの

| デザインの要素 | 初版の扱い |
| --- | --- |
| S3 ワークスペース／編集（メインパネル、Hierarchy、Inspector、Resources、エディタ、History、Releases、Members、ポータル） | **作る**（中心） |
| リポジトリ新規作成（Owner / Name / Kind / テンプレート / Visibility） | 作る。Remote（GitHub）・.gitignore・ライセンス選択は省略 |
| プロジェクトページ（Code、Workspaces、Commits、Releases、Settings の一部） | 作る（最小限） |
| プロジェクトページ（Issues、Pull requests、Actions、Branches、Pulse、Webhooks、Branch protection） | 作らない（タブは非表示） |
| プロフィール（リポジトリ一覧、Pinned） | 作る（最小限）。草・フォロワー・Projects は作らない |
| ノードによる System・カスタムノード・シェーダー編集 | 作らない（要件で対象外）。Resources の「New」から外す |
| ブランチ | 初版は main 1 本＋ワークスペース（ワークスペースが実質ブランチの役割）。要確認 |

用語の対応（要確認）：デザインの「Release／ワークショップ」＝ 要件の「公開／作品」、デザインの「Project」＝ 要件の「リポジトリ」として扱う。

## 8. 要確認事項（レビューで決めたいこと）

1. **スクリプト言語は Lua でよいか。**（デザイン準拠。スパイク結果で QuickJS に変える可能性あり）
2. **実行の確定役をホストのブラウザにするか、サーバーにするか。**（提案：ホスト権威で開始）
3. **バージョン管理を自前モデルにするか、Git（isomorphic-git 等）を内部で使うか。**（提案：自前）
4. **デザインにある GitHub 風機能（Issues・PR・Actions・ブランチ）を初版から外してよいか。**
5. **用語の対応**（Release＝公開、Project＝リポジトリ）。
6. **動かす場所**：初版はローカル（`pnpm dev`）のみでよいか、試験用にどこかへデプロイするか。
7. **検証規模の仮置き**：同時参加 4 人、1 セッションのオブジェクト 500 個、アセット 1 ファイル 20MB 程度で始めてよいか。

確定したら `docs/adr/` に決定記録として残し、M0 に着手する。
