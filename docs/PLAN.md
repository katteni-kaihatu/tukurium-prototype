# Tukurium プロトタイプ 実装計画 v0.2

作成日：2026-11-02
入力：[要件整理 v0.1](./requirements-v0.1.md)、デザイン「ツクリウム デザイン」（S3 ワークスペース／編集、プロジェクトページ、プロフィール、リポジトリ新規作成）

要件書の「11. 実装前に決めること」のうち、レビューで**決定したもの**は §2「決定事項」にまとめた。それ以外で「提案」と書いたものは変わりうる。

---

## 1. 方針

- **一周を早く回す。** 初版のゴールは「銃と的を共同制作 → 試す → 遊んでいる人がいるセッションへ適用 → コミット → 公開 → 他の人がフォーク／抽出」の一周。各マイルストーンは、その一周の一部を実際に触れる状態で終える。
- **専用実装を作らない。** 銃も的も、利用者が定義した KokoState とスクリプトの System だけで作る。アプリ側に「銃」のコードは置かない（サンプルは同梱データとして用意する）。
- **デザインは要件より範囲が広い。** GitHub 風の機能は「見た目だけ置く」（§7）。
- **後で差し替えやすく。** スクリプト実行環境、保存形式、アウトプットの種類は境界にインターフェースを置く。

## 2. 決定事項（2026-11-02 レビュー）

| 項目 | 決定 |
| --- | --- |
| スクリプト言語 | **制限付き JavaScript**（QuickJS の WASM 版で、ページとは別の制限された環境で動かす） |
| 実行の確定役 | **ホストのブラウザ**。ただしホストは 1 人ではない：**セッションのホスト**がセッション内に配置された実体すべての実行を確定し、**各ワークスペースのホスト**（ワークスペースごとに別）がそのワークスペースの再生（Play mode）を確定する。適用時はワークスペースの内容がセッションのホストへ渡り、セッションのホストが実体を更新する |
| ホストの引き継ぎ | **自動**。ホストが抜けたら、残った参加者のうち**引き継ぎ権限（Admin）を持つ人**が直前の実行状態から引き継ぐ（セッション・ワークスペースそれぞれ）。該当者がいなければ実行は止まる |
| セッションの持ち主 | セッションは**開いたユーザーの持ち物**。持ち主が閉じたらセッションはなくなる（実行状態も消える） |
| ワークスペースの権限 | 閲覧・共同編集・管理（Admin）。開いた人は管理。**参加者の初期値はホストが設定でき、既定は「共同編集」**。権限を変えられるのは**管理権限を持つ人** |
| ノードによる System・シェーダー編集の UI | **見た目だけ置く**（メニューには出すが選べない） |
| 履歴管理 | **内部で Git を使う** |
| GitHub 風の機能 | Issues・Pull requests・Actions・ブランチ・Webhooks・GitHub リモート・草グラフ・フォロワー等は**見た目だけ置く**（画面・タブは出すが動かない） |
| 用語 | **リポジトリ**＝開発の単位で、複数の**アウトプット**（ワールド、アイテム、将来はライブラリ）を持つ。**作品**はアウトプットにリンクし、**複数の Release** を持つ（Release ＝コミットからアウトプットをビルドしてバージョンを付けたもの。公開は特定コミットに固定される）。画面上の表記は**「プロジェクト」** |
| パッケージ（ライブラリの出力とインポート） | 初版では**作らないが設計で備える**（アウトプットの種類を増やせる構造、依存関係を持てるデータ形式） |
| 動作環境 | **VPS（Coolify）に docker compose で設置**。素材は **S3 互換ストレージ**、メタデータは **PostgreSQL** |

## 3. 技術選定

| 領域 | 選定 | 理由・備考 |
| --- | --- | --- |
| 言語 | TypeScript（strict） | 要件どおり |
| パッケージ管理 | pnpm workspaces（モノレポ） | クライアント・サーバー・共有ロジックで型を共有 |
| クライアントビルド | Vite | 起動・HMR が速い |
| 3D 表示 | Three.js（素の API、R3F は使わない） | シーンは EKS の描画 System から命令的に同期する。React の状態と二重管理しない |
| 2D UI（パネル・Web ページ） | React + Zustand、React Router | インスペクタ等の UI 量が多い |
| 物理・衝突・レイキャスト | Rapier（`@dimforge/rapier3d-compat`、WASM） | 命中判定・衝突イベント。スナップショットを取り出せるのでホスト引き継ぎにも使える |
| ユーザースクリプト | **QuickJS**（`quickjs-emscripten`） | 決定事項。ページの JS とは別の VM。割り込みハンドラで暴走を止め、メモリ上限も設定できる。公開 API 以外（DOM・ネットワーク等）は存在しない |
| コードエディタ | CodeMirror 6 + `y-codemirror.next` | 共同編集（カーソル共有含む）が既製品で済む |
| 共同編集 | Yjs（CRDT）＋ 自前 WebSocket サーバー | 競合解決・再接続・プレゼンスが既製。ワークスペースごとに Y.Doc を分け、権限のない人には**ドキュメントごと配信しない**ことでプライベート作業の非公開を担保する |
| セッションの実行同期 | WebSocket リレー ＋ ホスト権威 | ホストが EKS＋物理＋スクリプトを動かし状態を配信、参加者は入力を送る |
| サーバー | Node.js（Fastify ＋ `ws`） | 認証・権限・Yjs 同期・リレー・リポジトリ API・ビルド |
| DB | PostgreSQL（ORM は Drizzle、提案） | ユーザー・リポジトリ・アウトプット・作品・Release・セッション・権限 |
| 素材ストレージ | S3 互換（`@aws-sdk/client-s3`）。ローカル開発は SeaweedFS（`docker-compose.dev.yml`。MinIO は Docker Hub での配布が終了） | GLB・画像・音声を SHA-256 の内容アドレスで保存 |
| バージョン管理 | Git（サーバー上の bare リポジトリ、Docker ボリューム）。操作は isomorphic-git（提案） | 純 JS でシェル実行が不要。素材本体は Git に入れず、ハッシュ参照だけをコミットする（LFS に似た方式） |
| 本人識別 | 表示名＋ランダムトークン（パスワードなし、提案） | 「最小限の本人識別」。試験用 |
| スキーマ検証 | zod | 通信メッセージ・リポジトリ内データ・スクリプトからの入力 |
| テスト | Vitest（単体）、Playwright（E2E、複数ブラウザコンテキストで共同編集・ホスト引き継ぎを検証） | |
| Lint / Format | Biome | |
| デプロイ | Dockerfile（client は静的ファイルを server が配信、または nginx）＋ `docker-compose.yml`（app / postgres。S3 互換は外部） | Coolify で compose をそのまま使う |

### 3D パネルの表示方式（提案）

- 自分のパネルを 3D 表示するとき：`CSS3DRenderer` で実 DOM をそのまま空間に置く（操作可能）。WebGL 物体との前後関係が崩れる制約はプロトタイプでは許容。
- 他人のパネルの見え方：サーバーから届く**公開用の要約状態**（タイトル、開いている対象名、閲覧権限があれば内容の簡易表示）を Canvas 2D でテクスチャに描き、作業者の前に板として並べる。非公開内容はそもそもクライアントに届かない。

## 4. アーキテクチャ概要

```
┌──────────────────── ブラウザ（参加者） ────────────────────┐
│ React UI（2D パネル / Web ページ）                          │
│ Workspace 編集 ←→ Y.Doc（ワークスペースごと）                │
│ Three.js 描画 ← EKS World                                   │
│ Runtime（EKS + Rapier + QuickJS）                            │
│   ・セッションのホストなら：セッション World を実行          │
│   ・ワークスペースのホストなら：そのワークスペースの Play World を実行 │
└───────────────┬───────────────────────────────────────────┘
                │ WebSocket（Yjs 同期 / 実行状態リレー / 入力 / プレゼンス）
┌───────────────┴─────────────── サーバー ──────────────────┐
│ 認証・権限チェック（配信前に必ず通す）                       │
│ ホスト割り当て・自動引き継ぎ（セッション / ワークスペース別） │
│ Yjs ドキュメント保持・自動保存（ワークスペース）             │
│ セッション台帳：参加者・配置された実体・リンク               │
│ リポジトリ API：Git 操作・アウトプットのビルド・Release・作品 │
└──────┬──────────────────┬──────────────────┬──────────────┘
   PostgreSQL        Git（ボリューム）      S3 互換（素材）
```

### 3 つの「状態」を分ける

| 状態 | 置き場 | 保存 |
| --- | --- | --- |
| 制作データ（編集中） | ワークスペースの Y.Doc | 自動保存（作業途中の復元用。コミットとは別） |
| 制作データ（履歴） | Git コミット | 利用者の「コミット」操作のみ |
| 実行状態 | セッション World／ワークスペースの Play World（各ホストのメモリ） | 永続化しない。ホストは定期的にスナップショットをサーバーへ預け、引き継ぎに使う |

### ホストの自動引き継ぎ（提案）

1. 各ホストは一定間隔（例：1 秒）で実行状態のスナップショット（EKS の全 KokoState 値＋Rapier の状態）をサーバーへ送る。
2. サーバーはホストの切断を検知したら、残った参加者から次のホストを選ぶ（参加が古い順など）。
3. 新ホストは最新スナップショットから World を復元して実行を再開し、全員に通知する。数百 ms〜1 秒程度の巻き戻りは許容。
4. 参加者がいなくなったら実行は止め、最後のスナップショットを保持（次に誰かが来たら再開するかは要確認）。

### 適用（Apply）の流れ

1. ワークスペースで「適用」→ ワークスペースのホスト（または操作した人）が現在の Y.Doc から対象アウトプットのビルドを作り、サーバー経由でセッションのホストへ渡す。
2. セッション台帳から、このワークスペースにリンクしている配置された実体を列挙（メインパネルのリンク先一覧と同じもの）。
3. セッションのホストが各実体を新しいビルドで作り直す。アウトプットの「状態維持マーク」に載っているフィールドのうち、**フィールド ID と型が一致**するものだけ現在値を引き継ぐ。
4. 失敗（スクリプトの読み込みエラー等）した実体は旧版のまま残し、エラーをパネルに出す（暫定）。

### 識別子の方針（状態維持のため）

- Entity・KokoState 定義・フィールドは**名前ではなく安定 ID**（作成時に発行）で識別。名前変更しても状態が引き継げる。
- 状態維持マークは `アウトプット ID × Entity ID × KokoState ID × フィールド ID` の組で、アウトプットごとに持つ（同じ KokoState を使う別アウトプットへ波及しない）。
- 互換性（初版、提案）：型が同一なら互換。型が変わったら非互換で初期値に戻す。

## 5. データモデル

### リポジトリ（Git 管理）の中身（提案）

人が差分を読めるよう、1 要素 1 ファイルの JSON とスクリプトに分ける。

```
tukurium.json                 # リポジトリ設定（形式バージョン、依存パッケージ欄＝初版は空）
kokostates/<id>.json          # 利用者定義 KokoState（名前・フィールド ID・型・初期値）
systems/<id>.json             # System 定義（名前・Query・イベント）
systems/<id>.js               # System のスクリプト
materials/<id>.json
assets/<id>.json              # 素材のメタデータと S3 上のハッシュ参照（本体は Git に入れない）
outputs/<id>/output.json      # アウトプット（kind: world | item、将来 library）、有効な System、状態維持マーク
outputs/<id>/entities/<id>.json  # Entity（親子、KokoState の値）
provenance.json               # 抽出・取り込みの由来（元リポジトリ・コミット・対象）
```

- フォーク：Git のクローンとして作り、元リポジトリへの参照を DB に持つ。
- 抽出：アウトプットや Entity・KokoState・System・素材を依存関係ごと選び、新規または既存リポジトリにコミットする。由来は `provenance.json` とコミットメッセージのトレーラーに残す。
- パッケージへの備え：`outputs/*/output.json` の `kind` を拡張可能にし、`tukurium.json` に依存欄を予約しておく（初版は使わない）。

### DB（PostgreSQL）の主なテーブル（提案）

`users`、`repositories`（owner、名前、公開範囲、Git パス、フォーク元）、`outputs`（リポジトリ内アウトプットの索引）、`works`（作品：アウトプットへのリンク、権限＝利用／元データ閲覧／フォーク・抽出）、`releases`（作品ごと、コミット、バージョン、ビルド成果物の S3 参照）、`sessions`、`workspaces`（リポジトリ・ベースコミット・セッション・ホスト・プライベートか）、`workspace_members`（閲覧／共同編集／管理）、`placed_instances`（セッションに配置された実体と、リンク元ワークスペース or Release）、`assets`。

## 6. EKS とスクリプト API（たたき台）

デザインの S3 画面（Query の With / Without、Events、Systems の有効化）に合わせる。

```js
// KokoState 定義はインスペクタで作る（データ）。スクリプトは System の処理だけを書く。
// Gun: { ammo: Number = 12, interval: Number = 0.2, cooldown: Number = 0 }   ← 利用者が定義

export default system({
  query: { with: ["Gun", "Transform"], without: ["Disabled"] },

  onUpdate(e, dt) {
    e.Gun.cooldown = Math.max(0, e.Gun.cooldown - dt);
  },

  onInput(e, ev) {                       // ev.action === "fire" など
    const gun = e.Gun;
    if (ev.action === "fire" && gun.ammo > 0 && gun.cooldown === 0) {
      gun.ammo -= 1;
      gun.cooldown = gun.interval;
      const hit = world.raycast(e.Transform.position, e.Transform.forward, 100);
      if (hit) world.emit(hit.entity, "hit", { damage: 1 });
      audio.play("shot", e);
    }
  },
});
```

- 実行順：アウトプットの Systems 一覧の並び順（デザインの「SYSTEMS」設定）。
- イベント：`onUpdate` / `onInput` / `onCollision` / `onEvent`（`world.emit` で送る利用者定義イベント） / `onSpawn` / `onDestroy`。
- 公開 API（初版）：KokoState の読み書き、`world.query` / `spawn` / `destroy` / `raycast` / `emit`、`audio.play`、`log`。
- 予算：1 呼び出しあたりの時間上限（割り込みハンドラ）とメモリ上限。超過した System は停止状態にしてパネルに表示。
- 組み込み KokoState（Built-in）：`Transform`、`Mesh`（プロシージャル形状＋パラメータ／GLB 参照）、`Material`、`Collider`、`RigidBody`、`AudioSource`、`Player`。利用者定義と同じ仕組みに載せる。

## 7. プロジェクト構造（提案）

```
tukurium-prototype/
├─ apps/
│  ├─ client/                 # Vite + React + Three.js
│  │  └─ src/
│  │     ├─ app/              # ルーティング、グローバルヘッダー（作る/探す/ライブラリ、セッション表示）
│  │     ├─ pages/            # Web ページ：プロフィール、プロジェクト、プロジェクト新規作成、作品
│  │     ├─ session/          # 3D 空間、FPS 操作、参加者の簡易表示、ポータル
│  │     ├─ panels/           # パネル基盤（2D/3D ピン切替、配置、他人向け要約表示）
│  │     │  ├─ main/          # ワークスペースのメインパネル（再生/一時停止/適用、リンク先一覧）
│  │     │  └─ hierarchy/ inspector/ resources/ editor/ history/ members/ releases/
│  │     ├─ workspace/        # Y.Doc ⇔ 制作データ、編集空間（境界ボックス、ギズモ）
│  │     ├─ host/             # ホストとしての実行・スナップショット送信・引き継ぎ受け入れ
│  │     ├─ render/           # EKS World → Three.js 同期、素材読み込み
│  │     └─ net/              # WebSocket クライアント、Yjs プロバイダ
│  └─ server/                 # Node.js
│     └─ src/
│        ├─ auth/ permissions/
│        ├─ sessions/         # 参加・ホスト割り当てと引き継ぎ・リレー・配置された実体の台帳
│        ├─ workspaces/       # Yjs ドキュメント、権限付き配信、自動保存
│        ├─ repos/            # Git 操作、ビルド、Release、作品、フォーク／抽出
│        ├─ assets/           # アップロード、S3
│        └─ db/               # Drizzle スキーマ・マイグレーション
├─ packages/
│  ├─ shared/                 # 型、通信プロトコル（zod）、権限判定ロジック
│  ├─ eks/                    # EKS コア：World / Entity / KokoState レジストリ / Query / スケジューラ（DOM・Three 非依存）
│  ├─ script/                 # QuickJS サンドボックス、公開 API バインディング、予算管理
│  ├─ runtime/                # eks + Rapier + script。ビルド⇔実行、適用と状態引き継ぎ、スナップショット
│  └─ repo-model/             # リポジトリ内ファイル形式（zod）、Y.Doc ⇔ ファイル変換、差分、抽出、由来情報
├─ samples/                   # 同梱サンプル（銃・的・射撃場）をリポジトリ形式で
├─ e2e/                       # Playwright
├─ docker/                    # Dockerfile 等
├─ docker-compose.yml         # 本番（Coolify）：app / postgres（S3 互換は外部）
├─ docker-compose.dev.yml     # 開発用の周辺サービス：postgres / SeaweedFS
└─ docs/                      # 要件・計画・決定記録（ADR）
```

依存の向き：`apps/*` → `runtime` → `eks` / `script`、全員 → `shared`。`eks`・`runtime`・`repo-model` はブラウザ API に依存しない（Node でテストでき、サーバー側ビルドにも使える）。

### M0：基盤と技術スパイク
- モノレポ、Vite / Node 雛形、Biome、Vitest、CI（lint・型・テスト）、docker compose（app・postgres）。
- スパイク（結果を `docs/adr/` に記録）：

  3. Yjs：ワークスペース単位の権限付き配信。

### M1：一人で作って動かす
- EKS コア、Built-in KokoState、プロシージャル形状（球・箱・円柱・平面・カプセル）、マテリアル（色・粗さ・金属感・テクスチャ）。

- 編集空間（境界ボックス）とワークスペース内の再生・一時停止（Edit mode / Play mode）。
- Rapier によるレイキャスト・衝突、入力アクション。
- 完了条件：一人で銃と的を作り、Play で撃って当てられる。→ シナリオ 4（部分 3）

### M2：みんなでいる・一緒に作る
- 本人識別、セッション参加、プレゼンス（位置・向きの簡易表示）。
- ワークスペースの Y.Doc 化、共同編集、自動保存と再接続時の復元。
- ワークスペースのホスト（Play の実行を確定）と自動引き継ぎ。
- パネルの 2D/3D ピン切替、他人の作業パネルが見える。
- 完了条件：2 人が同じワークスペースを編集・再生し、相手のパネルが空間に見える。→ シナリオ 1, 5

### M3：セッションに出して適用する
- 配置された実体、セッションのホストによる実行と状態配信、自動引き継ぎ。
- メインパネルのリンク先一覧、「適用」、状態維持マーク（フィールド単位）、リセット。
- 1 セッションに複数ワークスペース（銃と射撃場を別リポジトリで）。
- 素材：GLB・画像・音声のアップロード（S3）と利用。
- 完了条件：遊んでいる人がいる横で銃を改造し、適用すると残弾だけ保ったまま新しい挙動になる。→ シナリオ 2, 3, 6, 7, 8

### M4：保存・公開・派生
- Git によるコミット（メッセージ、Co-author）、履歴表示、差分一覧。
- 1 リポジトリ複数アウトプット、作品の作成と Release（コミットからビルド）、権限。
- フォーク、抽出（新規／既存リポジトリへの取り込み）、由来情報。
- Web ページ：プロジェクト新規作成、プロジェクトページ、プロフィール。GitHub 風の機能は見た目だけ。
- 完了条件：作品を公開し、別の人がフォークして自分のワークスペースで作り始められる。→ シナリオ 10, 11

### M5：権限・プライベート作業・ワールド編集
- ワークスペース権限（閲覧・共同編集・管理）をパネル・実物・境界・ポータル・素材取得すべてに適用。
- プライベート作業：「作業中」だけが見え、内容は配信されない。独立空間での表示・実行。
- ワールドの専用編集空間とポータル、ワールドの出力とセッションへの適用。
- 完了条件：→ シナリオ 9, 12

### M6：通しで試す・VPS へ設置
- Coolify への docker compose デプロイ。
- 「銃と的のミニゲーム」で一周を 2〜3 人で通しテスト。E2E を一周シナリオで自動化。
- 使ってみて出た変更の反映、サンプル整備。

※ デプロイ自体は M2 以降いつでも試せるよう、M0 から compose を整えておく。

## 9. デザインと要件の対応

| デザインの要素 | 初版の扱い |
| --- | --- |
| S3 ワークスペース／編集（メインパネル、Hierarchy、Inspector、Resources、エディタ、History、Releases、Members、ポータル） | **作る**（中心） |
