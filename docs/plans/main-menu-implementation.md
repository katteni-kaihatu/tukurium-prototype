M0の初期範囲はADR 0022で確定。以下の「案」は同ADRの決定を優先し、実装した段階で実コードへの参照と確認結果を追記する。

左上の「ツクリウム」を押すとメインメニューを開く。中で次の五つの画面を切り替える。セッションに参加したまま使え、閉じると元の3D空間や制作へ戻る。

| 画面 | 最初に実現すること |
| --- | --- |
| ホーム | フレンドがいるセッション、所持アイテム、マーケットの新着へ進む |
| フレンド | 関係のある相手と、その状態・参加先を確認する。許された範囲で参加や招待へ進む |
| セッション | 開いている集まりと参加者を見て、参加・移動・作成・退出する |
| アイテム | 自分が入手したアイテムを検索し、参加中のセッションへ取り出す |
| マーケット | 公開アイテムを検索・比較し、詳細を見て入手する。所持済みなら取り出せる |

この計画で実装するのは、承認済みの画面構成を実データへつなぐためのメニューと必要な基盤である。2Dクライアント、通話、DM、ランキング、課金、制作ツールの刷新は含めない。モックの人物、作品、価格、説明はテスト用であり、本番の初期データにはしない。

## 2. 現行コードで使える部分と、追加が必要な部分

| 確認した箇所 | 現状 | 実装への影響 |
| --- | --- | --- |
| [Header](../../apps/client/src/app/Header.tsx)・[App](../../apps/client/src/app/App.tsx) | ブランドは `/` へのリンク。ホーム・探索・プロフィールは別ルート | 参加中のメニュー開閉をルート遷移にしない |
| [SessionView](../../apps/client/src/session/SessionView.tsx) | アンマウント時にワークスペースを閉じ、世界を破棄し、`session.leave` を送る | メニューを開いても、この画面とエンジンを維持する |
| [PanelLayer](../../apps/client/src/panels/PanelLayer.tsx) | パネルの移動・サイズ変更・2D固定／3D配置・前面化を扱う | 別のウィンドウ機構を増やさず、共通操作を使う |
| [WorkspacePanels](../../apps/client/src/workspace/WorkspacePanels.tsx) | ワークスペース未参加でもパネルを表示する。公開用の要約を他者へ送る | メニューを制作データから独立させ、公開用の送信から除外する |
| [Hub](../../apps/server/src/hub.ts)・[protocol](../../packages/shared/src/protocol.ts) | 一覧は名前・持ち主・人数のみ。更新の配信はセッション外の接続だけ | 参加中に一覧を受け取る経路と、参加者の要約が必要 |
| [LibraryPanel](../../apps/client/src/workspace/LibraryPanel.tsx) | 公開作品を `placeRelease` で配置する。成功に対応する要求IDはない | 配置処理を再利用しつつ、取り出し結果と再送を識別する |
| [作品API](../../apps/server/src/repos/routes.ts)・[api.ts](../../apps/client/src/net/api.ts) | 公開作品の一覧、作者、種類、最新リリースを返す。一般の検索・ページ送りはない | 既存作品を正本にして検索と表示を拡張する |
| [Store](../../apps/server/src/store/store.ts)・[PostgresStore](../../apps/server/src/store/postgres.ts) | 利用者・作品・リリースなどを保存する。フレンドと所持一覧はない | MemoryStoreとPostgreSQLの両方へ保存と取得を足す |

現行のセッションは、持ち主の接続がなくなると猶予後に閉じる。持ち主が別のセッションへ移る操作にも影響するため、一般参加者の退出と同じ説明で済ませない。閉じる条件自体はこの計画で変更しない。

## 3. メニューの状態を、ワークスペースから独立させる

以下の配置と名前は実装案。既存機能の移動範囲は、着手する段階で差分を確認する。

| 担当 | 配置案 | 持つ状態・責務 |
| --- | --- | --- |
| メニューの見た目 | `apps/client/src/main-menu/` | 共通枠と五つの画面、一覧・詳細・操作結果 |
| メニューの表示状態 | 同ディレクトリの専用store | 開閉、選択画面、検索・絞り込み、選択対象、一覧の位置、前面化の合図 |
| セッション・フレンドの情報 | app側のstoreと専用service | 取得状態、更新、再接続、参加先の変更 |
| 所持・マーケットの情報 | 専用serviceと既存作品API | 共通の作品情報、所持一覧、検索結果、入手・取り出しの結果 |
| 保存と判定 | server側のservice・Store | 本人確認、フレンド関係、所持、利用権限、重複要求の処理 |

メニューの表示先はワークスペースを開いているかに依存させない。たとえば制作中のリポジトリを閉じても、フレンド一覧やアイテム検索は残る。共有するEntityやKokoStateへ、メニューの検索語・選択・フレンド一覧を保存しない。

### ウィンドウの共通動作

- 左上のボタンで開閉する。最初はホームを表示し、開き直したときは最後に見ていた画面へ戻る。
- セッション内では、安定したIDを持つ一つのパネルとして登録する案とする。既存のパネル操作を使い、移動・サイズ変更・2D固定／3D配置に対応する。
- 閉じても表示状態を捨てない。検索語・選択・一覧の位置は専用store、位置・サイズ・固定状態は共通パネルの責務として保持する。
- 空間に置いた後で見失った場合も、左上から再表示できるようにする。既存の「画面に戻す」と前面化を使う経路を決める。
- 開くときはマウスロックを解除する。メニューの文字入力や操作を、移動・射撃・アイテム操作へ流さない。
- ダイアログがあればEscで先に閉じ、次にメニューを閉じる。Tabは入力・ボタン間の移動に使う。既存のパネル一括非表示との衝突を避ける。
- メニュー自体のタイトル・内容・選択・位置を、他者向けのパネル要約に含めない。3D配置中も同じ扱いにする。

現在のPanelLayerはSessionEngineを要求する。セッション外ではエンジンに依存しない共通ウィンドウ枠、セッション内では既存パネルへ同じ内容を載せる案とする。初期の共通化は必要な枠と状態にとどめ、パネル全体の再設計を前提にしない。

## 4. 実データにつなぐための追加

### セッション一覧と参加

既存のセッション一覧を参加中にも購読できるようにする。参加者はサーバーの本人情報から要約し、複数タブを同じ人として数える。まずは現行のセッションが見える範囲を維持し、紹介やプレビュー画像が未設定でも名前・持ち主・参加者で使えるようにする。

メニューを開くたびに参加し直さない。同じセッションを選んだ場合はメニューを閉じるだけとする。別のセッションへの移動は、確認後に既存の参加処理を一度だけ通す。ワークスペースの保存・終了処理が済む前に二つのセッションが混ざらないようにする。

初回取得、更新待ち、空一覧、参加先が消えた場合、接続断を別の状態として表示する。非同期の応答が遅れても、古い参加先や検索結果で現在の選択を上書きしない。

### 所持アイテムと入手

初期案では「入手」を、公開作品の使用したい版を自分の所持一覧へ登録する操作とする。無料の入手を対象にし、残高や決済は導入しない。ゲーム内のバッグとは別の、セッションをまたいで残る利用者の一覧にする。

記録候補は `userId / workId / releaseId / acquiredAt`。同じ利用者が同じ作品を入手し直しても重複させず、登録時のリリースを固定する。新しい版へ自動で変えず、更新の操作は別に設計する。この版の扱いはM0で確定する。

所持していることを、利用権限を上書きする根拠にしない。入手時と取り出し時に本人と対象作品を確かめ、取り出しでは現在の利用権限を再確認する。利用できなくなった作品は理由を表示し、古い取得結果だけで配置しない。

### マーケットの検索と詳細

既存の作品・リリースを使い、`item`を対象に、名前・作者の検索、新着順、取得件数の上限とページ送りを設ける。`/api/works`の拡張か、既存の作品serviceを使う専用の検索経路かをM0で決める。従来の呼び出しを壊さない。

モックのサムネイル・説明・カテゴリは、全作品に存在するデータではない。初期表示は既存情報と代替画像で成立させる。作者が設定する画像や説明を加える場合は、作品のメタデータと素材の閲覧権限に接続する。カテゴリ別の絞り込みは分類の持ち方を決めてから追加する。

所持済みの作品は「取り出す」、未所持なら「入手する」と表示する。自分の制作物をどう所持一覧へ含めるかもM0の判断対象とし、初期案では他の作品と同じ明示的な登録を使う。

### 取り出しの成功を、送った要求と結び付ける

配置は既存の`placeRelease`を再利用する。新しいメニューでは、要求IDと対象セッションを持たせ、サーバーからその要求に対応する成功・失敗を返す案とする。

成功は配置されたIDと対象セッションを受け取ってから表示する。他の人が物を出しても、自分の成功と取り違えない。同じ要求の再送で二重配置せず、完了後にもう一個出す場合は新しい要求とする。途中でセッションが変わった要求は、移動先へ勝手に配置しない。

重複判定は利用者・セッション・要求IDの組で行い、保持上限も決める。通信の変更は`protocol.ts`で定義し、互換性がなくなる場合はプロトコルの版を上げる。

### フレンド関係と状態

表示だけの架空フレンド一覧は本体へ入れない。関係の作成・確認・解除と、相手の状態・参加先を返す本人確認付きの経路が必要になる。

初期案は相互承認型のフレンド関係とする。Tonariumと同じ「相互フォローでフレンド」にするかはM0で確定する。識別には表示名でなく既存の利用者IDを使う。

オンライン状態は接続から集計し、複数タブのうち一つが切れただけではオフラインにしない。参加先はHubが持つ実際の参加状態から返す。関係のない相手や、閲覧できない場所の状態まで一覧に配らない。

「参加 OK」「声かけて」「取り込み中」とひとことを持たせる場合は、保存・更新・状態に応じた操作の規則を合わせて作る。「行ってもいい？」と招待は、送信・待機・承認／辞退・期限切れを扱い、承認されても受け手を自動で移動させない。DMやグループ機能はこの段階では足さない。

## 5. 作業はメニューの枠から始める

番号は実装の依存順を表す。各段階でコード・確認結果・残る範囲をレビューできる形にする。途中段階で未接続の操作を、完成した機能として公開しない。

### M0: データと操作の契約を確定する

- フレンドの成立方式、所持と版の扱い、状態・招待の初期範囲を決める。
- セッション参加者の公開範囲、一覧購読、入手・取り出しの要求と応答を定義する。
- 既存パネルを使う位置、メニューの状態の置き場、他者向け送信からの除外を決める。
- 未設定の画像・説明・カテゴリをどう表示するか決める。
- 採用した内容をADRへ残し、後続段階の受け入れ条件を更新する。

完了条件: 各段階が参照する型・状態遷移・担当箇所が説明できる。まずM1に必要な枠と状態を確定し、フレンドや所持の判断は該当段階の着手前までに決める。未確定の項目を、実装者がモックから推測して固定しない。

### M1: 左上から開く共通ウィンドウ

- Headerの左上操作と、共通のメニューstore・枠・ナビゲーションを作る。
- 参加前のウィンドウと、参加中のパネルで同じ内容を使う。
- 開閉、前面化、移動、サイズ変更、2D固定／3D配置、画面内へ戻す操作をつなぐ。
- 検索・選択・一覧の位置を閉じても保つ。非公開のローカルUIとして扱う。

完了条件: 制作中に開閉してもSessionView・SessionEngine・ワークスペースを作り直さず、位置・作業・再生が続く。ワークスペースがないときも開ける。

### M2: セッションと参加者を実データで表示する

- 参加中にも更新される一覧と、参加者の要約をつなぐ。
- 名前・参加者の検索、一覧・詳細、現在地、参加・復帰・移動・作成を実装する。
- 参加先の消失、切断、移動の失敗、持ち主の退出で閉じる場合を表示する。

完了条件: 別の人の入退室が、メニューを開き直さず反映される。同じ場所の選択では再参加せず、明示した移動だけで場所が変わる。

### M3: マーケットから入手し、所持一覧から取り出す

- Storeの保存・取得と、本人確認付きの入手・一覧の経路を作る。MemoryStoreとPostgreSQLで同じ振る舞いにする。
- 公開アイテムの検索・ページ送り・詳細を既存の作品情報へ接続する。
- 入手後に所持一覧と「所持済み」を更新する。入手と配置を別操作にする。
- 所持アイテムの検索と、要求ID付きの取り出し結果をつなぐ。
- 利用できない作品、リリースなし、取得失敗、未参加からの参加先選択を扱う。

完了条件: 入手した作品が再接続後も残り、選んだセッションに一度だけ取り出せる。入手しただけでは空間に配置されない。検索・選択は参加先を選ぶ間も保たれる。

### M4: フレンドと参加先への導線

- M0で決めた関係の成立・解除と、本人向けの一覧を実装する。
- オンライン状態と参加先を表示し、相手のセッションへ進める。
- 状態・ひとこと・招待・「行ってもいい？」を採用した範囲でつなぐ。
- 相手の退出、状態変更、関係解除、申請や招待の期限切れを反映する。

完了条件: 関係と状態を作る入口があり、一覧だけが先行しない。複数タブと再接続で相手の状態が矛盾せず、承認や招待だけで移動・編集権限が発生しない。

### M5: ホームへ集約し、一周を確認する

- フレンドがいるセッション、所持アイテム、マーケットの新着を同じデータから表示する。
- カードから各画面の対象を開き、同じ入手・参加・取り出し処理を使う。
- 未取得・空・オフライン・一部の取得失敗を表示し、再試行できるようにする。
- 既存のプロジェクト・探索・プロフィール・ライブラリ・バッグへの入口を確認し、使えなくなる機能を残さない。

完了条件: 「ホームからフレンドの場所へ参加 → マーケットで入手 → アイテムから取り出す → 閉じて制作へ戻る」を実データで通せる。

## 6. 保存・通信・既存機能との境界

- フレンド関係、状態の設定、所持一覧はサーバーの利用者に保存する。画面の開閉や検索はクライアントの表示状態とする。異なるアカウントへ表示状態を引き継がない。
- 所持一覧とゲーム内バッグは別の機能。所持した作品をEntityやバッグの種類へ自動変換しない。
- ワールドを開く、制作にライブラリを追加する、プロジェクトをフォークする処理は既存の担当箇所を使う。アイテムの取り出しへ混ぜない。
- セッションの参加や退出は一つの経路へまとめる。古いHeaderやHomePageにも、別実装の同じ操作を残さない。
- データ追加は既存データを読める形にし、新しい表が空でも起動する。MemoryStoreをテスト専用の別仕様にしない。
- UGC計画のU6とは、作品一覧・版・取得可能性・素材の権限を共有する。検索や所持の別カタログを作って作品の正本を分けない。

## 7. 確認すること

### ロジックのテスト

表示の細部を写したテストは増やさず、以下の壊れると困る振る舞いを対象にする。

- メニューの開閉で退出要求を出さず、検索・選択を保持すること。
- 他者向けのパネル要約にメニューを含めないこと。
- セッション一覧が参加中にも更新され、複数接続を人単位で集計すること。
- フレンド・所持操作の本人確認、重複要求、関係解除・権限変更を扱うこと。
- 入手が重複せず、取り出しの成功・失敗が要求と対象セッションへ結び付くこと。
- 検索の上限・ページ送り・フィルター、古い応答を反映しないこと。
- MemoryStoreとPostgreSQLで、再取得した関係・所持・版が一致すること。

### 画面と実データでの確認

既存の[verify-change手順](../../.claude/skills/verify-change/SKILL.md)を使う。新しい機能別E2Eを大量に常設せず、画面確認は使い捨てのスクリプトと画像で行う。

- 参加前／参加中／編集中／再生中に開閉し、入力と現在地が保たれる。
- メニューを移動・縮小・3D配置してから開き直せる。画面幅が狭くても主要操作が届く。
- メニュー入力中は移動やアイテム操作が起きず、EscとTabが意図どおり働く。
- 二人以上で参加者一覧、フレンドの状態、所持、取り出しを確認する。
- 接続断、再接続、連打、一覧取得後の対象消失、取り出し中の移動を確認する。
- 既存の「一人で作る・二人で編集・セッションに出して適用・三人で一周」のE2Eを、リポジトリの運用に従って確認する。

コード変更を実装した段階では、lint・型・単体テスト・ビルドを実行する。今回の計画作成では文書だけを変更し、リンク・差分・記述の整合性を確認する。

## 8. 実装前に確定する残りの判断

| 判断すること | 現時点の提案 | 確定する段階 |
| --- | --- | --- |
| フレンドの成立 | 相互承認型。相互フォロー方式も比較し、どちらか一つにする | M0、M4着手前 |
| 所持と版 | 無料の登録一覧として保存し、入手時のリリースを固定する | M0、M3着手前 |
| 状態と招待 | モックの四状態を対象候補とし、ひとこと・参加確認・招待の範囲を合わせて決める | M0、M4着手前 |
| 参加者の見せ方 | 現行の公開セッションの範囲で名前・持ち主を表示する | M0、M2着手前 |
| メニューの再表示 | 既存パネルの前面化・画面へ戻す操作を使い、見失わない入口を用意する | M0、M1着手前 |
| 画像とカテゴリ | 代替画像を初期対応に含める。作者による設定と分類は別に範囲を決める | M0、M3着手前 |

各項目を確定したら、判断と受け入れ条件を記録してから該当段階の実装に入る。UIモックが動くことを、サーバーの保存・同期・権限が完成している根拠にはしない。
