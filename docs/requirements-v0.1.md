# Tukurium プロトタイプ要件整理 v0.1

作成日：2026-11-03
位置づけ：実装エージェントへの引き継ぎ用初稿。確定した体験要件と、提案・未決定事項を分ける。

## 1. 目的と初版の到達点

ブラウザの3D空間で交流しながら、複数人でアイテムやワールドを制作できる環境を作る。完成品だけでなく、制作中の作業を見たり共同編集に参加したりできる体験を試す。プロトタイプを作り、試し、変更する速さを重視する。

初版の到達点は「複数人で銃と的などの小さなゲームを制作 → 動作確認 → セッションで遊ぶ人がいる状態で更新を適用 → メッセージ付きで保存 → 作品として公開 → 他の人がフォーク／抽出して制作を始める」の一周とする。

特定の銃やゲームだけが動く専用実装ではなく、利用者が独自のデータと処理を定義して制作できることを重視する。

## 2. 実行環境と範囲

- ブラウザで動作する。HTMLとTypeScriptで開発する。アプリケーションの実装言語はTypeScriptとする。利用者がSystemを記述するスクリプト言語・実行環境は、アプリケーションの実装言語とは別に選定する。Three.jsは3D表示の候補であり、バージョンや周辺構成は未選定。
- PCのマウス・キーボードによるFPS視点の操作を初版の対象とする。
- 制作対象はアイテムとワールド。アバター制作は対象外。共同作業者の位置・向きを示す簡易表示とは区別する。
- 将来のVR利用を想定した3Dパネルを設けるが、VR機器対応は初版の対象外。
- 独立したプロトタイプとする。外部コミュニケーションサービスとの統合は行わない。
- セッションへの参加と共同制作に必要な機能を用意する。SNSや本格的なコミュニケーションサービスの再実装は目的に含めない。

## 3. 基本概念

| 概念 | 定義 |
| --- | --- |
| セッション | ワールドが開かれ、参加者が交流・利用・制作する場所 |
| ワールド | セッションの空間を構成する制作物 |
| リポジトリ | 制作元データと履歴を管理し、複数のアウトプットを持つ単位。GitやGitHubを内部で使うかは未決定 |
| ワークスペース | リポジトリから作成する編集環境。セッションに紐づき、複数人で共同編集できる |
| アウトプット | リポジトリから出力するアイテムやワールドなどの単位 |
| 作品 | アウトプットに対応し、権限と元リポジトリへのリンクを持つ公開・利用の単位 |
| 配置された実体 | セッション内で利用・実行されるアイテムなど。制作元データとは状態を分ける |

1つのセッションに複数のワークスペースを開ける。同じワークスペースには複数人が参加できる。異なるリポジトリで作る銃と射撃場などを、セッションで組み合わせて試せる。

## 4. EKSによる制作

EKS（Entity / KokoState / System）は、ECSのComponentをKokoStateと呼び替えた設計であり、別のアーキテクチャではない。Component指向との用語の混同を避ける。

- EntityはKokoStateを持つ。
- KokoStateはデータを表す。利用者が独自のKokoStateを定義できることは必須。
- Systemは処理を担い、クエリ対象となるKokoStateを選択する。
- 例えば、利用者が残弾数や発射間隔のフィールドを定義し、それを対象とするSystemで射撃処理を書く。
- クエリ条件の具体的な表現、Systemの実行順序、入力や衝突イベントの受け渡しは未決定。

初版は実装量を抑えるため、スクリプトによるSystemを先行する方針案とする。将来はノードによるSystemとカスタムノード制作にも対応したいが、初版には含めない。

スクリプト言語・実行環境は未選定。ページの権限で任意のJavaScriptをそのまま動かす方式は避け、既存の制限された実行環境を優先して比較する。許可されたAPIからEKSや入力などを扱うこと、暴走した処理を停止できることを選定条件案とする。実装速度を重視し、独自言語の開発は前提にしない。

## 5. 素材・表示

初版で必要な素材・表現は以下。

- プロシージャルメッシュ：球体・ボックス・円柱など、用意した形状のパラメータを変更して形を作るもの。
- 画像。
- 音声。
- メッシュ：GLBモデル。
- マテリアル。

任意の頂点・面を自由に生成するAPIや、頂点を直接編集するモデリングツールは、プロシージャルメッシュ要件に含めない。シェーダーは固定とし、独自シェーダー制作は対象外。マテリアルの編集項目、対応する画像・音声形式、容量制限は未決定。

## 6. 共同編集UI

### ワークスペースのメインパネル

セッション内にワークスペースの起点となるメインパネルを置く。権限に応じて閲覧・編集参加を行い、インスペクタなどの編集パネルを開く。再生・一時停止・適用などの操作や、リンク先一覧もここから扱う。

パネルの存在が見えることと、内容を閲覧できることは別に扱う。

### 2D／3Dパネル

- パネルごとにピン操作で2D表示と3D表示を切り替える。
- 2D表示ではUnityのような編集操作感を目指す。ただし空間内の基本移動はFPS視点とする。
- 3D表示では空間内のパネルとして操作する。将来のVR利用を想定する。
- 本人が2D表示している場合でも、閲覧権限を持つ他の参加者からは、その人の前にパネルが並んでいる様子が見える。
- 非公開内容が他人向けのパネル表示から漏れないようにする。
- 他人のパネルを直接操作できる範囲や、スクロール・選択・入力途中の文字の共有範囲は未決定。

### 編集対象の表示

アイテムはセッション内に実物として表示し、バウンディングボックスのような境界で制作領域を示す。論理上の編集空間と実行中のセッション状態は分離する。編集対象の表示はメインパネルから切り替えられるようにするが、具体的な切り替え項目は未決定。

ワールドは専用の編集空間を用意し、ポータルから入る。プライベート作業ではアイテムも独立した空間内で扱う。

## 7. 再生・適用・状態維持

### 編集と実行を分ける

ワークスペースの編集内容は、セッション内の実行状態と分離する。編集中の変更はセッションへ自動反映しない。ワークスペース側で再生・一時停止を行い、セッションへの適用とは独立して試せる。

「適用」を押すと、対応するセッション内の実体を更新する。参加者が遊び続けている横で制作し、変更を反映できることが重要。

初版は、そのセッションでワークスペースにリンクしている対象すべてへ適用する。個別対象だけの更新は扱わない。リンクしている対象を一覧表示する。ワールド全体への適用方法や、適用失敗時の扱いは未決定。

### 状態を引き継ぐマーク

- 状態維持のマークはKokoStateの型全体には付けない。
- アウトプット内の特定のフィールドに限定して設定する。
- 適用時には、マークがあり、更新後と互換性のあるフィールドだけ現在の実行値を引き継ぐ。
- 同じKokoStateを使っていても、別のアウトプットへ設定が波及しない。
- 実行状態を簡単にリセットする操作を用意する。

互換性の判定、フィールドの識別方法、維持しない値の初期化方法、リセットの対象範囲は実装前に決める。編集データの保存と実行中の状態の保存は混同しない。

## 8. 権限とプライベート作業

ワークスペースの権限は閲覧・共同編集・管理を区分する。作品は利用・元データ閲覧・フォーク／抽出の権限を分ける。

完全なプライベート作業にも対応する。権限のない参加者には「作業している」ことだけが分かり、内容は見えない。この状態では制作物をセッションへ出すことはできず、独立した空間内で表示・実行する。

メインパネルだけでなく、編集対象の実物、境界、パネル表示、ポータルの入室、素材やコードの取得にも権限を適用する。誰が権限を変更できるか、権限の初期値、派生物の公開条件は未決定。

## 9. 保存・公開・派生

- コミットは利用者が意図的に行う「保存」とし、メッセージを記入できる。更新履歴を残す。
- 作業途中の自動保存・再接続時の復元は未決定。自動保存を設けても、意図的なコミットと区別する。
- 1つのリポジトリから複数のアイテム・ワールドを出力し、作品へリンクできる。
- 権限が許せば、作品にリンクしたリポジトリからフォークまたは抽出して制作を始められる。
- 抽出したものは、新しいリポジトリだけでなく、既存リポジトリにも取り込める。
- 元のリポジトリやコミットを後から追える由来情報を残す方向。ただし追跡単位は未決定。
- 由来を追えることと、元の更新を自動で取り込めることは別。後者は初版要件として確定していない。
- PRは将来要件。初版の対象から外す。

「適用」はセッション内の実体の更新、「コミット」は制作データの履歴保存、「公開」は作品を利用可能にする操作として区別する方針案とする。公開を特定のコミットに固定するかは未決定。

## 10. 初版の確認シナリオ案

以下は要件から作成した受け入れ確認案であり、具体的な人数・規模・性能目標は未決定。

1. 2人が同じセッションに参加し、同じワークスペースを共同編集できる。
2. 複数のワークスペースを開き、銃と的などを別々に制作して組み合わせられる。
3. 基本図形のパラメータ・マテリアルを編集し、GLB・画像・音声を利用できる。
4. 独自KokoStateと、それをクエリ対象にするSystemを作り、射撃と命中などの動作を実装できる。
5. パネル単位で2D／3Dを切り替え、他の閲覧可能な参加者からも作業パネルが見える。
6. 編集空間の再生・一時停止がセッションの実行を止めない。
7. リンク先一覧を確認し、適用操作でリンク先すべてが更新される。
8. 互換性のある維持対象フィールドだけが実行値を保ち、リセット操作もできる。
9. 権限のない人にはプライベート作業の内容が表示・配信されず、専用空間にも入れない。
10. メッセージ付きコミットを保存し、履歴を確認できる。
11. 複数アウトプットを作品として公開し、権限に応じてフォーク・抽出・既存リポジトリへの取り込みを試せる。
12. ワールドの編集空間へポータルで入り、制作・出力できる。

## 11. 実装前に決めること

体験要件を変えず、以下は小さな技術検証と実装提案で埋める。

- スクリプト先行方針の最終確認と、言語・実行環境・公開API。
- 共同編集の競合処理、実行結果の確定役、再接続、同時編集と実行の同期方式。
- EKSのクエリ条件、Systemの実行順、入力・衝突・生成・削除のAPI。
- Entityの親子関係、アウトプット境界、外部参照・素材・Systemの依存関係と抽出範囲。
- 再生・一時停止・停止・リセットの共有範囲と、編集データとの関係。
- 状態維持の互換性、マーク対象の識別、更新失敗時の扱い。
- ワールド更新時のセッションへの影響、制作領域と利用中の実体の見分け方。
- コミット・公開の関係、作業途中の保存、履歴復元、派生元情報の保持範囲。
- 最小限の本人識別と権限管理、公開・非公開の初期値。
- 同時参加人数、オブジェクト数、素材容量などの検証規模。

実装エージェントは、未決定事項を確定済みと扱わない。初版の対象外機能を先回りして作り込まず、上記の一周を短く試せる構成を提案する。
