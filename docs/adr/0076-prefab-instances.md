# ADR 0076：プレハブをリソースにし、インスタンスは使う所の手前で中身に展開する

- 状態: 採用・一部実装済み（P1 まで。プレハブのリソース・インスタンスを置く・展開・再生。残りは実装計画の段階で進める）
- 関連：ADR 0004（ワークスペースの同期）、ADR 0010（リソースの同一性・参照・診断）、ADR 0012（権限と判定の場所）、ADR 0037（フィールドごとの共同編集）、ADR 0057（動作上の親）、ADR 0065（フィールドの型と値）
- ロードマップ：「プレハブを作ってインスタンスをアウトプットに置く」。原則 4 のため

## 背景

的や駒のように、同じものを何個も置いて、まとめて直したい。今は、Entity をアウトプットごとに一つずつ持っていて、同じものを置くには複製するしかない。複製したものは、あとから一緒に直せない。

構想で、Entity・KokoState・System のまとまりを「プレハブ」としてリソースに登録し、アウトプットの中に「インスタンス」として置くことを決めた。プレハブを直すと、すべてのインスタンスに反映される。

## 決定（構想で決まっていること）

- プレハブは部品で、リソースとして作る。それだけをセッションに出すことはない。
- プレハブは Entity（子を含む）・KokoState・System を含められる。別のプレハブのインスタンスも置ける。自分を含むことはできない。
- インスタンスはアウトプットの中に置き、場所・向き・大きさを決められる。
- インスタンスでは、フィールドの値を変え、Entity・KokoState・System を足し、並べ替えと親の付け替えができる。プレハブから来たものは消せない。
- プレハブの変更は、ワークスペースの中のインスタンスにはすぐ反映し、セッションに出した配置には「適用」で届く。

## 作り方（設計者・実装者が決めたこと）

### 1. プレハブは新しい種類のリソース

- 定義（`PrefabDef`）：ID・名前・いちばん上の Entity（`root`）・System の並び（`systems`）・「維持」の印（`keep`）・編集する場所（`editIn`。ないときは「その場」）。
- 論理パスと ID は、ほかのリソースと同じ扱い（ADR 0010）。拡張子は `.prefab`。名前を変えても動かしても、インスタンスは ID で結び付いているので切れない。
- Git には、`prefabs/<ID>.json`（定義）と `prefabs/<ID>/entities/<Entity の ID>.json`（中の Entity）で保存する。
- 制作データが増えるので、`PROTOCOL_VERSION` を 14 に上げる。

### 2. プレハブの中の Entity は、アウトプットの Entity とは別に持つ

実装計画の二つの案のうち、(b)「`output` はそのままにし、プレハブの Entity を別に持つ」を選んだ。

- 制作データ：`ProjectSnapshot.prefabEntities`（`PrefabEntityDef`。`output` の代わりに、属するプレハブの ID `prefab` を持つ）。
- 共同編集（Y.Doc）：`prefabEntities` という別の `Y.Map`。中の形は `entities` と同じで、値はフィールドごとの後勝ち（ADR 0037）。
- Entity の ID は、アウトプットのものとプレハブのものを通して一つ。フィールドの値を変えるなどの操作は、ID だけで、どちらの Entity にも届く。

選んだ理由：

- (a)「`output` を `owner` に置き換え、同じ `entities` に入れる」だと、`e.output` を読んでいる所（テストを除いて 90 か所ほど）を、すべて持ち主の種類で分けることになる。
- それより大きいのは、取りこぼしたときの壊れ方。依存グラフ・参照の診断・抽出・差分は「`entities` にあるものは、どれかのアウトプットの Entity」という前提で書かれている。同じ並びにプレハブの中の Entity（展開する前の、ひな形）が混ざると、直し忘れた所で、ひな形が実体として扱われる。
- (b) なら、今のコードはプレハブの中の Entity を目にしない。展開したあとの並びは、プレハブがなかったころと同じ形なので、そのまま読める。プレハブの中身を扱う所だけが、新しい並びを読む。

### 3. インスタンスの Entity が、プレハブのいちばん上の Entity に当たる

- プレハブは、いちばん上の Entity（`root`）を一つだけ持つ。プレハブの中のほかの Entity は、すべてその下に入る。空のプレハブは、いちばん上の Entity だけを持つ。
- インスタンスは、アウトプット（または別のプレハブ）の中の一つの Entity で、`instanceOf: { prefab: <プレハブの ID> }` を持つ。
- インスタンスの Entity の ID・名前・親・並び順は、インスタンスのもの。KokoState は、プレハブのいちばん上の Entity のものに、インスタンスが持っている KokoState を重ねる（同じ KokoState は、インスタンスのものが勝つ）。
- 場所・向き・大きさは、インスタンスが持つ Transform。置くときに、プレハブのいちばん上の Entity の向きと大きさを写す。あとでプレハブ側の Transform を変えても、インスタンスには届かない（「変えた所」には数えない）。

選んだ理由：アウトプットの Entity からプレハブを作る（P3）とき、選んだ親の Entity はインスタンスになり、元の ID を引き継ぐ。ほかの Entity が「親の Entity を指す参照」を持っていても、そのまま使える。インスタンスを「入れ物」にして中身を子にする形だと、その参照は KokoState のない入れ物を指してしまう。

### 4. 使う所の手前で展開する（`expandPrefabs()`）

制作データのインスタンスを、プレハブの中身に置き換えた並びを作る関数を、repo-model に置く。

- **ID**：インスタンスの Entity は、そのままの ID。中の Entity は「インスタンスの ID `/` プレハブの中の Entity の ID」。入れ子は、順につなげる（`盤のインスタンス/駒1/芯`）。決まった作り方なので、開き直しても、別の人の画面でも同じ ID になる。区切りに使うので、Entity の ID に `/` は使えない。
- **参照**：プレハブの中の Entity どうしの参照（フィールドの値。入れ子の値の中も）は、展開のときに、そのインスタンスの中の ID に付け替える。プレハブの外を指す参照は、そのまま。
- **入れ子**：プレハブの中のインスタンスも、たどって展開する。自分を含むプレハブ（輪）は、そこで展開を止め、問題として出す。プレハブがないインスタンスは、中身のない Entity として残し、問題として出す。
- **結果の形**：アウトプットの Entity の並び（`EntityDef`）。プレハブから来たものには、どのインスタンスの、どのプレハブの、どの Entity かが付く（`origin`）。展開したあとは `instanceOf` を持たないので、もう一度展開しても変わらない。アウトプットの `systems` と `keep` は、足し合わせたあとのもの（6・7）。
- **読む所**：再生（`buildWorld()`・`Simulation` の配置と適用）、空間の表示、Hierarchy、Inspector、参照の診断の「指す先があるか」。依存グラフは、展開せずに「インスタンス → プレハブ → プレハブが使うもの」の辺で持つ（インスタンスの数だけ節を増やさない）。
- **問題を出す相手**：制作データにある Entity とプレハブ。展開で作った Entity は、利用者がそこでは直せないので、問題の相手にしない。

### 5. 展開の結果を取っておく

- プレハブごとに、入れ子まで開いた形（ひな形）を覚えておく。そのプレハブと、中で使っているプレハブの中身が変わるまで使い回す。
- インスタンスごとの展開した Entity も覚えておく。インスタンスも、ひな形も変わっていなければ、そのまま使う。
- フィールドの型が変わると、参照の付け替えが変わるので、すべて作り直す。
- 取っておいた結果は、次の展開でも使う。展開したあとの制作データは、読むだけにする。
- 計測（`pnpm bench:prefab`。3 段の入れ子、インスタンス 1 個が Entity 69 個）：インスタンス 100 個（Entity 6,900 個）で、初めの展開は 4 ms、何も変わっていなければ 0.4 ms、インスタンスを一つ動かすと 0.4 ms、いちばん内側のプレハブを変えると 4.5 ms。

### 6. System は、並びと「入・切」だけを足し合わせる

- アウトプットで動かす System は、アウトプットのものと、中のインスタンスのプレハブのもの（入れ子の中のものも）を合わせたもの。
- **並び順**：アウトプットのものが先。プレハブのものは、そのあとに、Hierarchy の並びで先に出てくるインスタンスのものから足す。一つのプレハブの中では、プレハブの並びのとおり。入れ子では、外のプレハブのものが先で、中のプレハブのものは、中のインスタンスが出てくる順。
- **同じ System**：一つにまとめる（先に出てきた所に置く）。どれかのプレハブで「入」なら「入」。
- **アウトプットが勝つ**：アウトプットにも同じ System があれば、場所も「入・切」もアウトプットのもの。アウトプットの画面で、プレハブの System を「切」にすると、アウトプットの並びに「切」で入る。
- 権限は、今と同じく System のコードから読み取る（ADR 0012）。

### 7. 「維持」の印

- アウトプットの印は、展開した Entity の ID とフィールドの組を指せる。
- プレハブの中で付けた印は、プレハブが持つ（Entity は、プレハブの中の ID）。展開のときに、インスタンスごとの ID にして、アウトプットの印に足し合わせる。
- インスタンスを消したら、その中を指すアウトプットの印も一緒に外す。

### 8. インスタンスで変えた所（上書き）の持ち方

P4 で作る。作りながら変えたら、ここを直す。

- **フィールドの値**：インスタンスの Entity が、上書きの入れ物（`Y.Map`）を持つ。キーは「プレハブの中の Entity の ID（いちばん上からの ID）・KokoState・フィールド」、値はフィールドの値。リストの一つの要素だけを変えても、フィールドまるごとを持つ（フィールドごとの後勝ちに合わせる）。
- **足した KokoState**：いちばん上の Entity（インスタンスそのもの）に足すものは、インスタンスの `states` に持つ（3 の重ね方が、そのまま使える）。中の Entity に足すものは、上書きの入れ物に、KokoState まるごとで持つ。
- **足した Entity**：アウトプットのふつうの Entity として持ち、親に、展開した Entity の ID を指す。ID が決まった作り方なので、開き直しても親を見失わない。
- **並び順と親**：プレハブから来た Entity ごとに、変えた親と並び順だけを持つ。
- **親が消えたとき**：プレハブは、消した Entity の「元の親」を覚えておく。展開のとき、親が見つからなければ、これをたどって、さらに上の親に付ける。
- **足した System**：インスタンスが、System の並びを持つ。プレハブの System と同じ扱いで足し合わせる。
- **入れ子で何段も重なったとき**：内側から順に重ね、外側が勝つ。

### 9. 編集する場所

P2 で作る。プレハブの設定（`editIn`）で、「その場」（初め）と「離れた空間」を選ぶ。「離れた空間」は、ワールドと同じ置き場所の決め方を使う。

## 影響

- 制作データに `prefabs` と `prefabEntities`、Entity に `instanceOf` が増える。古いデータ（これらがない）は、そのまま読める。
- Entity を使う所は、展開した並びを読む。展開せずに `entities` を読むと、インスタンスは Transform だけの Entity に見える。
- 抽出・ライブラリ・エージェントの道具は、まだプレハブを持っていかない（P7・P8）。プレハブを使っているアウトプットを抽出すると、インスタンスは「プレハブがありません」の問題になる。
- 参照の付け替えは、フィールドの型（スキーマ）が分かるフィールドだけに届く。型エラーで読めないフィールドの中の参照は、付け替わらない。
