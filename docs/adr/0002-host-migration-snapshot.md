# ADR 0002：ホスト引き継ぎ用の実行状態スナップショット

- 状態：採用（2026-11-02）
- 関連：計画 §2「ホストの引き継ぎ：自動」、§4「ホストの自動引き継ぎ」

## 決めたこと

セッションとワークスペースのホストは、一定間隔（初期値 1 秒）で次の 2 つをサーバーへ預ける。ホストが抜けたら、新しいホストがこれらから実行を再開する。

1. **EKS のスナップショット**（`World.snapshot()`、JSON）：すべての Entity と KokoState の値。
2. **Rapier のスナップショット**（`World.takeSnapshot()`、バイナリを gzip 圧縮）：剛体の位置・速度、接触の情報。

Entity と剛体の対応表（Entity ID → 剛体ハンドル）は EKS 側に持つ。Rapier の復元ではハンドルが保たれるので、対応表はそのまま使える。

## 技術検証の結果（`packages/runtime/src/rapier.spike.test.ts`）

| 確認したこと | 結果 |
| --- | --- |
| 復元後のハンドル | 保たれる。全剛体の位置が元のワールドと一致 |
| 復元後の計算 | 元のワールドと同じ入力で 120 ステップ進めて、位置が完全に一致（決定的） |
| 大きさ（100 剛体、60 ステップ後） | 238 KiB、gzip で 76 KiB |
| 大きさ（100 剛体、計算前） | 65 KiB |
| 取得時間 | 0.1ms 程度 |

接触の情報が入るので、計算が進むと大きくなる。1 秒ごとに送ると 100 剛体で約 76 KiB/秒。初版の検証規模（同時参加 4 人程度、1 セッションあたり剛体は数十〜百）では許容できると判断した。

## 重くなった場合の代替案

Rapier のスナップショットは送らず、EKS のスナップショット（`Transform` と `RigidBody` の速度を含む）から物理ワールドを作り直す。接触の情報（ウォームスタート）が失われるので引き継ぎ直後に少し揺れうるが、データは数分の一になる。どちらでも復元できるよう、EKS のスナップショットは常に送る。

## 巻き戻り

最後のスナップショットから引き継ぐため、最大 1 秒程度の巻き戻りが起きる。その間に起きた出来事（命中など）は失われうる。初版では許容する。
