# ADR 0065：KokoState のフィールドの型を TypeScript の型の文で書き、値の形を広げる

- 状態: 採用（実装中。T3 まで実装済み）
- 関連：ADR 0010（リソースの同一性・参照・診断）、ADR 0012（権限と判定の場所）、ADR 0051（リソースを指すフィールドの型。T2 で置き換える）、ADR 0058（スクリプトはすべて TypeScript で書く）
- ロードマップ：「KokoStateのフィールドをTypeScriptの型で書いてレコード・リスト・マップ・参照を扱えるようにする」。原則 2・4・5 のため

## 背景

フィールドの型は決まった名前の一覧から選ぶ形で、レコード・リスト・マップ・参照を持てない。値はどこでもふつうの JSON で、`undefined`・`Date`・`Map` などを保存できない。構想で、フィールドの型を TypeScript の型の文で書くこと、「なし」は `undefined` にすること、`Date`・`Map`・`Set`・`bigint`・`NaN`・`Infinity` も保存することを決めた。

## 決定（計画者と決めたこと）

- KokoState の定義は Tukurium の形式のまま、フィールドごとに型を TypeScript の型の文で書く。書ける型は保存できる型に限る。
- 「なし」は `undefined`。`null` は使わない。
- `undefined`・`Date`・`Map`・`Set`・`bigint`・`NaN`・`Infinity`・`-Infinity` も保存する。
- 型は TypeScript で読み解いて「値の形の決まり」（スキーマ）に変え、値の確かめはスキーマで行う。
- 共同編集は、KokoState の定義もフィールドごとの後勝ち。

## 作り方（設計者が決めたこと）

### 1. 値の形式：タグ付きの JSON（独自の形式）

JSON で表せない値だけを、`"$t"` のキーを持つオブジェクトにする。ほかはふつうの JSON のまま。

| 値 | 書き方 |
| --- | --- |
| `undefined` | `{"$t":"undefined"}` |
| `NaN`・`Infinity`・`-Infinity` | `{"$t":"number","v":"NaN"}` など |
| `bigint` | `{"$t":"bigint","v":"12345678901234567890"}` |
| `Date` | `{"$t":"Date","v":"2026-11-10T00:00:00.000Z"}` |
| `Map` | `{"$t":"Map","v":[[キー, 値], ...]}`（キーも値の形式） |
| `Set` | `{"$t":"Set","v":[値, ...]}` |
| `"$t"` のキーを持つふつうのオブジェクト | `{"$t":"object","v":{...}}`（取り違えないように包む） |

- 書き出しと読み込みは、一つの関数にまとめる。スクリプトの実行環境（QuickJS）には、その関数の文（`toString()`）を prelude に入れる。ホストと QuickJS で、同じ処理を二つ書かない。
- Git・Yjs・通信・QuickJS との受け渡しのすべてで、この形式を使う。
- 選んだ理由：
  - 入れ子の形がそのまま残るので、Git の差分も Yjs の中身も、ふつうの JSON と同じ形で読める。
  - 依存がなく、数十行で、QuickJS でもそのまま動く。
- 試したこと：
  - superjson は値を正しく戻せる。ただ、型の情報を値と別の場所（パスの一覧）に持つので、Yjs や差分で値の一部だけを扱いにくい。依存もある。
  - devalue も値を正しく戻せる。ただ、値を番号で参照し合う平らな形になり、入れ子の形が残らない。
  - タグ付きの JSON は、Node と QuickJS の両方で、`Map`（数のキーを含む）・`Set`・`Date`・`bigint`・`NaN`・`Infinity`・`undefined` と、`"$t"` のキーを持つオブジェクトを書き出して戻せた。QuickJS の中で `Map` を足し、`bigint` を計算して戻しても崩れなかった。Yjs に入れても、別の Doc で元どおりに戻った。

### 2. 型の文からスキーマを作る

- `packages/typecheck` で、TypeScript の型の確かめ（TypeChecker）を使って、フィールドの型の文をスキーマに変える。
- スキーマの種類：
  - 数・文字・真偽・`bigint`・`undefined`
  - 選択肢（文字・数・真偽のリテラル）・組み合わせ（union）
  - タプル・リスト
  - レコード（フィールドと、省略できるか）
  - マップ（`Record<K, V>`）・`Map`・`Set`・`Date`
  - Tukurium が用意する型（下の 3）
- 呼び出せる型（関数）・クラスのインスタンス・`Promise` など、標準ライブラリのほかの型はスキーマに変えられないので、型エラーにする。
- 試したこと：レコードのリスト・省略できるフィールド・選択肢・`Date`・`Set<string>`・`Map<EntityRef, bigint>`・タプル・参照の型をスキーマに変えられた。関数・関数を持つレコード・`Promise` は型エラーにできた。気をつける点として、`Record<string, T>` は標準ライブラリの型（mapped type）なので、標準ライブラリの型を断る判定より先に、添え字（index signature）で見分ける。11 個の型で、TypeScript の準備を含めて 0.5 秒ほどだった。
- **スキーマは保存しない。** 制作データから作る、問題の一覧と同じ扱いにする。
  - ワークスペースでは、型を確かめる Worker が、型エラーと一緒にスキーマを作り、画面と再生のホストに渡す。
  - サーバーでは、`packages/typecheck` で作る。
  - 公開したリリース（中身が変わらない）には、作ったスキーマを入れておく。セッションに置いたアイテムの再生で、TypeScript を読み込まずに済む。
- **スキーマがまだないとき、または型エラーでスキーマを作れないとき**：再生は止めない（ADR 0010）。そのフィールドは、値の形式で表せる値ならそのまま通し、型の確かめをしない。保存のときに確かめられなかったフィールドは、問題として出す。

### 3. Tukurium が用意する型

Host API の宣言に足す。値の持ち方も決める。

| 型 | 値の持ち方 | 今の型 |
| --- | --- | --- |
| `Vec3` | `[number, number, number]` | `vec3` |
| `Color` | `"#rrggbb"` の文字 | `color` |
| `EntityRef` | Entity の ID の文字（型の上では区別する） | `entity` |
| `TextureRef`・`MaterialRef`・`ModelRef`・`AudioRef` | リソースの ID の文字（型の上では区別する） | `texture`・`material`・`model`・`audio` |
| `KokoStateRef<K>` | `{ entity, koko }`（Entity と KokoState の ID） | なし |
| `FieldRef<T>` | `{ entity, koko, field }`（Entity・KokoState・フィールドの ID） | なし |

- `KokoStateRef<K>` の `K` は import した KokoState。`FieldRef<T>` の `T` は、指せるフィールドの型。
- 今の参照の「なし」（`null`）は、`EntityRef | undefined` のように型で書き、値は `undefined` にする。

### 4. 型の定義のリソース

- 新しいリソースの種類にする。中身は `.d.ts`（`type` と `interface` と `export`）。Git には `types/<ID>.d.ts` で保存する。論理パスと ID の扱いはほかのリソースと同じ（ADR 0010）。
- KokoState の定義は、使う型の定義を ID の一覧で持つ。宣言を作るときに、その論理パスから `import type` を作る。名前を変えたり動かしたりしても、ID で結び付いているので切れない。

### 5. 定義のフィールドごとの後勝ち

- Yjs の `kokostates` を、KokoState ごとの `Y.Map` にし、フィールドをフィールドの ID ごとの `Y.Map` で持つ。
- フィールドの並びは、フィールドごとに並べ替え用のキー（間に入れられる文字）で持つ。2 人が同時に足しても並びが壊れない。

### 6. 通信

値の形式が変わるので、T1 で `PROTOCOL_VERSION` を上げる。

## T1 で決めたこと（値の形を広げる）

- **メモリの上では、ふつうの JavaScript の値で持つ。** 制作データ（`ProjectSnapshot`）・実行の世界（`World`）・状態の配信（`WorldSnapshot`）の値は、`undefined`・`Date`・`Map` などをそのまま持つ。タグ付きの JSON にするのは、外へ出す境目だけ。
  - Git：フィールドの値と初期値の所だけを書き出す（`packages/repo-model/src/storedValues.ts`）。ほかのプロパティは、今までどおりのふつうの JSON。
  - Yjs：Entity の値はフィールドごとに、KokoState の定義は初期値を、書き出した形で入れる。
  - 通信（WebSocket）：メッセージをまるごと書き出す（`stringifyValue`・`parseValue`）。値がどこに入っていても欠けない。値が `undefined` のプロパティも、タグになって届く。
  - REST の返事と、エージェント（MCP）に見せる値も同じ形式。エージェントが渡す値は、同じ形式か、参照の「なし」なら `null` でも受け取る（JSON には `undefined` がないため。説明と受け渡しを整えるのは T7）。
- **値が `undefined` のフィールドと、キーがないフィールドは別のもの。** KokoState の値では、キーがなければ初期値、`undefined` なら「なし」。あるかどうかは `in` で確かめる（`?? 初期値` と書かない）。
- **content hash（`stableStringify`）**：オブジェクトの、値が `undefined` のプロパティは書かない（ないのと同じ。作り方で hash が変わらないように）。配列の中の `undefined` と、JSON で表せない値は、タグ付きの JSON で書く。
- **書き出しの細かい決まり**：`toJSON()` を持つオブジェクトは、その結果を書き出す（JSON と同じ。import した KokoState が ID になる）。関数と symbol は書き出さない。`bigint` は 4096 桁まで（大きすぎる数の読み込みで、サーバーや実行が止まらないように）。形式に合わないタグは、読み込みでエラーにする（通信では、そのメッセージを受け付けない）。
- **スクリプトとの受け渡しは、JSON で表せない値を持ちうるフィールドだけを、値の形式で運ぶ。** 全 Entity の値を毎回 QuickJS の中でたどると、1 ステップが 2 倍ほど重くなった（200 Entity で 7〜10 ms が 15〜20 ms）。ホストが、フィールドの型から「持ちうるフィールド」を決めて渡し、ほかのフィールドは QuickJS の `JSON.parse`・`JSON.stringify` に任せる（main との差は 1 割ほどに収まった）。いまの型では、参照の「なし」の `undefined` だけが当てはまる。
  - 指定していないフィールドにスクリプトが JSON で表せない値を書いたときは、`JSON.stringify` のとおりになる（`undefined` は書かなかったのと同じ、`NaN`・`bigint` は `null`、`Date` は文字）。型が合わない値として、ホストが受け入れない。ただし、文字のフィールドに `Date` を書くと、文字（ISO の形）として入る。型エラーとしては、型の確かめで出る。
  - Host API の引数と戻り値、イベントのデータは、まるごと値の形式で運ぶ（小さいので）。
  - 指定していないフィールドの値は、ホストもタグとして読まない（スクリプトが `"$t"` を持つオブジェクトを書いても、ふつうのオブジェクトのまま）。
  - T2 でフィールドの型を広げるときは、スキーマから「JSON で表せる値しか持たず、`"$t"` のキーも持ちえないフィールド」を決めて、同じ道に乗せる。
- **書き出しと読み込みの関数の書き方**：関数の文を QuickJS に入れるので、外の変数を使わず、中に名前の付く関数を作らない（tsx が補助の関数で包み、QuickJS で動かなくなる。詳しくは `docs/DEVELOPMENT.md`）。

## T2 で決めたこと（型を TypeScript の型の文にする）

- **フィールドの型は、型の文の文字で持つ**（`FieldDef.type`）。今までの型は、`number`・`boolean`・`string`・`Vec3`・`Color`・`EntityRef | undefined`・`TextureRef | undefined`・`MaterialRef | undefined`・`ModelRef | undefined`・`AudioRef | undefined` と書く（`FIELD_TYPE`）。古い名前（`vec3`・`entity` など）で保存したデータは移さない。
- **Tukurium が用意する型**（Host API の宣言に足した）
  - `Color` は `` `#${string}` ``。`"#ff0000"` のような文字はそのまま入れられ、ただの `string` は入れられない。
  - 参照は `string & { readonly __tukurium: "EntityRef" }` の形で、文字と区別する。`e.id`・`world.find()`・`world.spawn()`・`hit.entity`・ぶつかった相手は `EntityRef` を返す。
- **スキーマ**（`packages/eks/src/schema.ts` の `ValueSchema`）：数・文字・真偽・`bigint`・`undefined`・選択肢・色・参照・組み合わせ・タプル・リスト・レコード・マップ（`Record<string, V>`）・`Map`・`Set`・`Date`。
  - `Record<"a" | "b", V>` のようにキーが決まっているものは、レコードになる。
  - 組み合わせの中の `undefined` は、最後に置く（作り方で並びが変わらないように）。
- **スキーマの作り方は二つあり、同じ結果になる**（テストが検査する）。
  - TypeScript の型の確かめ（`packages/typecheck` の `TypeChecker.checkAll()`）：どんな型の文でも読める。ワークスペースでは Worker、サーバーではそのまま動かす。
  - 型の文からじかに読む（`knownSchema()`）：Tukurium が用意する型の名前と、それに `| undefined` を付けたものだけ。TypeScript を読み込まずに済むので、Built-in と、一覧から選んだ型のフィールドは、いつでも確かめられる。
- **型エラーの出し方**：型の文は、まず 1 つずつ「型 1 つとして読めるか」を確かめ、読めたものを KokoState ごとの仮想のファイルに並べて、TypeScript に読ませる。型エラー（読めない・知らない名前・保存できない型）は、その KokoState のフィールド（`property` の場所 `[フィールドの ID, "type"]`）に出す。型エラーのあるフィールドは、KokoState の宣言で `unknown` にするので、ほかのフィールドとスクリプトはそのまま確かめられる。
- **保存できない型**：関数・クラス・`Promise` などの標準ライブラリの型・`null`・`any`・`unknown`・`symbol`・enum・省略できる要素のあるタプル・文字でないキーの添え字。理由を付けて断る。
- **値の確かめ**（`validateValue()`）
  - 実行での書き込み・エージェントの値・「値が型に合っているか」の診断（`checkFieldValues()`。Entity の値と初期値）で使う。
  - 数は `NaN`・`Infinity` も受け入れる。Built-in の KokoState の数（位置・速度など）だけは、描画と物理がそのまま使うので、有限の数に限る。
  - スキーマが分からないフィールドは、確かめずに通す。
- **入れ子の中の参照**は、スキーマでたどる（`visitRefs()`・`mapRefs()`）。依存グラフ・参照の診断・抽出・セッションでの Entity の ID の付け替えが、これを使う。
- **スキーマの受け渡し**
  - ワークスペース：Worker が作り、画面（Inspector・診断）と再生に渡す。
  - セッション：ワークスペースから出す・適用するときは、出した人の画面のスキーマを一緒に送る。リリースを置くときは、サーバーが作って付ける（リリースごとに一度）。ホストは、届いたスキーマの形を確かめてから使う（`parseFieldSchemas()`）。
  - 取り込み（抽出）：取り出し元のスキーマは、サーバーが作って渡す。
- **スクリプトとの受け渡し**：JSON だけで運べるか（`isJsonSafe()`）を、スキーマから決める。自作の KokoState の数は `NaN` を持ちうるので、値の形式で運ぶ。
- **Inspector とエージェント**：数・文字・真偽・色・`Vec3`・参照・文字の選択肢は、専用の入力で直せる。ほかの型の値は、Inspector では値の形式の文字で見せるだけ（直すのは T6）。エージェントは、型を一覧の名前か TypeScript の型の文で書き、値を値の形式で渡す。

## T3 で決めたこと（定義のフィールドごとの後勝ち）

- Yjs の `kokostates` は、KokoState ごとの `Y.Map`（`id`・`name`・`role`・`fields`）。`fields` は、フィールドの ID ごとの `Y.Map`（`name`・`type`・`default`・`order`）。
- 定義を書き換えるとき（`ProjectDoc.updateKokoState()`）は、変わった所だけを書く。別のフィールドを同時に変えた人の変更も、同じフィールドの別の所（名前と初期値など）を変えた人の変更も残る。同じ所を同時に変えたときは、どちらかに揃う。
- フィールドを消すと、同時に変えられていても消える。
- 並びは、フィールドごとの並べ替え用のキー（`order`。`packages/repo-model/src/orderKey.ts`）の小さい順。足したフィールドと動かしたフィールドにだけ、前後の間のキーを作る。2 人が同時に足して同じキーになったときは、ID の順で並べる。
- Entity が持つ値は、消えたフィールドを削除し、足したフィールドと型が変わったフィールドを初期値にする。ほかのフィールドの値には触れない（今までは、定義を変えるたびに全部の値を書き直していたので、同時に変えた値を上書きすることがあった）。
- Git のファイル（`kokostates/<ID>.json`）は変えていない（フィールドは並びの順の配列。キーは保存しない）。
- 前の形（定義まるごとが一つの値）で入っている編集中のデータも読める。書き換えたときに新しい形になる。

## 影響

- ADR 0051 の「リソースを指すフィールドの型」は、T2 で `TextureRef` などの型に置き換わる。
- 型ごとの `switch` で作っていた所（型の宣言・実行での確かめ・Inspector・エージェント・依存グラフ・抽出・参照の診断）は、スキーマを見る形に変わる。

## 制約・残課題

- スキーマを作るには TypeScript の本体が要る。ワークスペースを開いた直後で Worker の準備ができていない間は、型の確かめをしない。
- 保存できる型かどうかは、標準ライブラリの型の名前（`Date`・`Map`・`Set`）で見分ける。利用者が同じ名前の型を作ったときに取り違えないよう、宣言の出どころも見る。
