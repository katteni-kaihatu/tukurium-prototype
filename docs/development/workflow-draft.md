# 開発の進め方（案）

設計を考える仕事と、今の仕組みで修正を進める仕事を行き来できるようにする。まだ運用を決める前の草案。

## メインとサブ

- **メイン**：共通の仕組みや役割分担を考え直す仕事。
- **サブ**：今の仕組みで、修正・改善・ライブラリ追加を進める仕事。

一つの作業に両方があってよい。最初は仮に分け、途中で必要になった判断を見つける。

## 進め方

1. 何を直す・作るかと、分からないことを短く書く。
2. 調べて試す。新しい設計判断が必要なら、その部分をメインへ移す。
3. 考え方が決まったら、実装をサブへ切り出せる。メインで始めても、今の仕組みで足りると分かればサブへ移す。
4. 変更と確認結果を残す。設計の確認・更新は[design-review](../../.claude/skills/design-review/SKILL.md)に従う。
5. PRで分類と資料への反映を確認する役を固定する案とする。担当や確認の範囲は未定。

切り替える理由は一行でよい。調査や試作は引き継ぐ。サブでは、毎回詳しい設計書を書くことは求めない。

例えば、修正済みの[複数の配置へ適用できない不具合](https://github.com/katteni-kaihatu/tukurium-prototype/issues/63)を直すのはサブ。「適用後に何を残すか」を変えたくなれば、その判断はメインで考える。詳しい背景は[試し再生と適用](../design/creation/README.md#試し再生と適用)へ。

## 次に相談すること

メイン／サブの分け方と、設計を採用する人、固定レビュー役の担当を詰める。ADRの残し方も合わせて考える。

確定したフローは、開発者・エージェントの入口から参照できるようにする。設計の確認・更新については、CLAUDE.mdからdesign-reviewスキルを参照する。
